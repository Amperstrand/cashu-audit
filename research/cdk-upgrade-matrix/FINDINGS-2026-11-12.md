# cdk-mintd upgrade matrix — FINDINGS (2026-11-12, internal)

**Question:** is the 0.17→0.18 (→0.18.3) in-place upgrade path (`config migrate`
→ `validate` → `config init --existing-mint`) generally buggy, given the
vps-mint ghost-keyset refusal?

**Method:** docker-isolated mints, one fixed mnemonic per run; sources
0.15.0 / 0.17.0 / 0.17.2 / 0.17.6 / 0.17.7 (env-config era: migrate path) and
0.18.0 / 0.18.1 / 0.18.2 (DB-config era: binary swap, auto-migrations); shapes
A = fresh-idle, B = rotated keysets (boot plain, restart with
`CDK_MINTD_FAKE_WALLET_KEYSET_ROTATIONS` expiring the first keyset + adding a
new active one). Verdicts compare version, pubkey, and full keyset-ID sets
pre/post. Harness: `upgrade-matrix.sh` (same dir); raw: `results-*.tsv`.

**Result: 16/16 PASS.** Every source upgrades to 0.18.3 in place with identity
and complete keyset history preserved. Rotated mints on 0.17.0/.2/.6/.7 carry
all three keysets (base + expired + new-active) through intact.

**Refinements:**
- The vps-mint `HistoricalKeysetMismatch` was NOT reproduced by any documented
  rotation flow — the fake-wallet rotations always leave DB rows for rotated
  keysets. The vps failure required a derived-history keyset with NO database
  row (damaged/early history), a rarer shape than "mint that rotated keys".
  Conclusion: not a general upgrade defect; no upstream issue (owner call).
- Shape B does not exercise 0.18.x sources: the rotations env belongs to the
  env-var config surface that 0.18 removed (single keyset observed pre/post on
  0.18.0/.1/.2 shape-B runs — they are effectively shape A). Testing rotation
  on 0.18.x needs the native mechanism (management RPC / config).
- Harness lessons (three iterations): legacy boots need the workdir passed
  through to the binary (`cdk-mintd -w /data` — env-config era ignores mounts
  otherwise, and init then refuses an empty DB); `mnemonic = "env:…"` configs
  need the env var on BOTH init and daemon; fixed mnemonics must be
  BIP39-checksum-valid (generate, don't invent).

**Not yet measured (open cells):** spent-set preservation across upgrade
(mint + spend on source, verify double-spend still refused post-upgrade);
0.18.x-native rotation; multi-unit mints. Matrix is cheap to extend.

## CORRECTION (2026-11-12 evening): the "vps ghost-keyset" is resolved — and it was not a cdk defect

The vps-mint `HistoricalKeysetMismatch` had nothing to do with the surviving
mint's history. The failing `config init --existing-mint` was invoked without
the global workdir flag and therefore defaulted to `$HOME/.cdk-mintd` — an
abandoned June-era NOK-unit mint with a different signing source. Its one
keyset (`0161d13a…`, slot `1008782418'/1'`, 6 signatures ever) is exactly the
id the error cited. Proof: `config init --existing-mint` **with the correct
workdir** against a copy of the real pre-migration backup completes cleanly
(`/opt/vps-mint/ghostlab/`, vps) — the in-place upgrade was possible all
along, consistent with this matrix's 16/16. A targeted split-brain repro
(same seed, era-1 unit `nok`, era-2 unit `sat`) also upgrades clean.

Lessons: (1) `config init` accepts the workdir ONLY as a global before the
subcommand — omit it and it silently validates whatever `$HOME/.cdk-mintd`
contains; (2) when an error names an identity your target provably lacks
(exhaustive table grep), suspect you are looking at the wrong target before
theorizing about hidden state; (3) the no-external-filing rule saved us from
reporting our own CLI invocation mistake upstream as a cdk bug.
