## 1. Spec MUSTs extracted and compliance

### MUST-1 — Mint MUST error if quote has `pubkey` but mint request lacks valid `signature`

> 20.md:199 — "If the wallet user `Alice` does not include a signature on the
> `PostMintBolt11Request` but did include a `pubkey` in the
> `PostMintBolt11QuoteRequest` then `Bob` **MUST** respond with an error."

**PASS.** Two enforcement paths:

- **Regular mint** (`ledger.py:528-529`): `mint()` calls
  `_verify_mint_quote_witness(quote, outputs, signature)` → returns `False` when
  `quote.pubkey` is set but `signature` is `None` or invalid → raises
  `QuoteSignatureInvalidError` (code `20008`).

- **Batch mint** (`ledger.py:631-641`): `mint_batch()` iterates each quote, extracts
  per-quote signature from `payload.signatures[i]`, rejects signatures on pubkey-less
  quotes (`if not quote.pubkey and sig: raise`), then calls the same
  `_verify_mint_quote_witness` per quote.

The gatekeeper logic in `verification.py:345-356`:
```python
def _verify_mint_quote_witness(self, quote, outputs, signature) -> bool:
    if not quote.pubkey:    # no NUT-20 lock → skip
        return True
    if not signature:       # pubkey set but no signature → reject
        return False
    return nut20.verify_mint_quote(quote.quote, outputs, quote.pubkey, signature)
```

### MUST-6 (implicit) — BIP340 Schnorr signature on SHA-256 hash

> 20.md:127 — "We use a BIP340 Schnorr signature on the SHA-256 hash of the message
> to sign as defined above."

**PASS.** `construct_message()` returns `sha256(msg).digest()` (32-byte hash).
`sign_mint_quote()` calls `privkey.sign_schnorr(msgbytes)` (coincurve BIP340).
`verify_mint_quote()` calls `pubkey_xonly.verify(sig, msgbytes)` (coincurve BIP340).
The x-only public key is extracted from the 33-byte compressed key via
`PublicKeyXOnly(bytes.fromhex(public_key)[1:])` (`nut20.py:59`), which is correct
for BIP340 (strips the parity prefix, uses the 32-byte x-coordinate).

## 4. Findings

### FINDING-1 (LOW) — Legacy signature fallback still active

**Location:** `cashu/core/nuts/nut20.py:62-79`

`verify_mint_quote()` attempts spec-compliant verification first, then falls back to
`construct_message_legacy()` which uses a non-spec format: hex-encoded `B_` strings
(no raw-byte decode), no domain-separation tag, no length prefixes. This fallback is
deprecated since v0.20.2 and logs a warning, but it still **accepts** legacy signatures.

**Effect:** A signature over the old non-spec message format will pass verification.
This is a backward-compatibility measure for wallets that signed with the pre-spec
format.

**Severity rationale:** Low. The legacy format is structurally incompatible with the
spec format (different hash), so there is no confusion or downgrade attack vector —
an attacker cannot craft a message that satisfies both formats simultaneously. The
fallback only affects quotes where the wallet intentionally used the old signing path.

### FINDING-2 (LOW) — Deprecation warning emitted on every failed verification

**Location:** `cashu/core/nuts/nut20.py:72-74`

The `logger.warning("Using legacy NUT-20 signature verification…")` is emitted **before**
attempting legacy verification, meaning it fires on every path where spec-compliant
verification fails — including legitimate rejections (wrong quote ID, attack attempts,
malformed signatures). In production, this could cause log spam proportional to the
attack/invalid-request rate.

**Fix:** Move the warning inside the legacy-success branch, or gate it behind a
`logger.debug` and only warn when the legacy method succeeds.

**Severity rationale:** Low. Operational/observability concern only; no impact on
security or correctness.

### FINDING-3 (INFO) — Error code `20009` defined but never raised

**Location:** `cashu/core/errors.py:219-224`

`QuoteRequiresPubkeyError` (code `20009`) is defined but never imported or raised
anywhere in the codebase. The spec lists it as: "Mint quote requires `pubkey` but
none given or invalid `pubkey`." In NUT-20's design, the `pubkey` is wallet-optional
—the mint never *requires* it — so this error code has no applicable scenario in the
current spec. Its presence in `errors.py` is preemptive/reserved. **Not a violation.**

### FINDING-4 (INFO) — Signatures are non-deterministic

BIP340 Schnorr signatures generated by coincurve's `sign_schnorr()` use a random
auxiliary nonce (not the BIP340 deterministic nonce `r = HMAC-SHA256(x, msg)`). This
means `sign_mint_quote()` called twice with the same inputs produces different (but
equally valid) signatures. The spec does not mandate deterministic signatures. The
expected test-vector signature verifies correctly even though a freshly generated
signature differs. **Not a violation.**

## 5. Verdict

**PASS.** Nutshell's NUT-20 implementation is conformant with the specification.

- The single explicit spec MUST (error when quote has `pubkey` but mint request lacks
  valid `signature`) is enforced on both the regular mint and batch-mint paths via
  `QuoteSignatureInvalidError` (code `20008`).
- The message aggregation format matches byte-for-byte, confirmed by test-vector hash
  reproduction.
- BIP340 Schnorr signatures are produced and verified correctly using coincurve.
- The `pubkey` field is accepted in quote requests, echoed in responses, persisted, and
  round-tripped through the wallet.
- NUT-06 advertises `{"20":{"supported":true}}`.
- The wallet generates a fresh keypair per mint quote (satisfying the spec's privacy
  SHOULD).
- All official test vectors and negative tests pass.

The two LOW findings (legacy fallback still active; deprecation warning log spam) are
operational hardening items that do not affect correctness or spec compliance.
