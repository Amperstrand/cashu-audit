**Overall verdict: PASS** — NUT-09 is a short, optional spec with one explicit `must` and several implicit normative requirements. Nutshell satisfies all of them. The storage-before-sign invariant is enforced by `update_blind_signature` raising `ValueError` if the blinded-message row does not yet exist; the restore path queries `WHERE b_ = :b_ AND c_ IS NOT NULL` so only previously-signed messages are returned; and output/signature arrays are appended in lockstep inside the restore loop, guaranteeing length equality and index correlation. One non-blocking warning: the `/v1/restore` route is registered unconditionally rather than being guarded by `is_nut_supported(RESTORE_NUT)` — harmless because the feature is hardcoded supported in `features.py`, but it means the endpoint cannot be disabled independently of the NUT-06 advertisement.

## Per-Requirement Verdicts

### N09-R1 — Storage invariant (spec L11) — PASS

**Claim:** Every `BlindSignature` issuance stores both the `BlindedMessage` and the resulting `BlindSignature` in the database.

**Evidence:** Nutshell splits storage into two phases that are always paired at every issuance call site:

1. `_store_blinded_messages()` (ledger.py:1408-1445) inserts a row into `promises` with `b_`, `amount`, `id` (keyset id) and `c_ = NULL` (unsigned placeholder). Delegates to `crud.store_blinded_message` (crud.py:338-367).
2. `_sign_blinded_messages()` (ledger.py:1447-1513) computes the blind signature, then calls `crud.update_blinded_message_signature` (crud.py:423-454) which `UPDATE … SET amount, c_, signed_at WHERE b_ = :b_`. It first verifies the row exists and raises `ValueError("blinded message does not exist")` if not — this **enforces the store-before-sign invariant at runtime**.

All four issuance paths pair the two calls:
- **Mint** (single): ledger.py:530-531 — `_store_blinded_messages(outputs, mint_id=quote_id)` → `_sign_blinded_messages(outputs)`.
- **Mint** (batch): ledger.py:652-655 — `_store_blinded_messages(payload.outputs, mint_id=…)` → `_sign_blinded_messages(payload.outputs)`.
- **Swap**: ledger.py:1346,1362 — `_store_blinded_messages(outputs, keyset=…, conn)` → `_sign_blinded_messages(outputs, conn)`.
- **Melt change**: `_store_blinded_messages(outputs, melt_id=…)` at ledger.py:1146 stores outputs first; `_construct_melt_change` (ledger.py:280-305) then calls `_sign_blinded_messages` over the subset kept for change, and `delete_blinded_messages_melt_id` (crud.py:405-421) removes the unsigned remainder. The signed subset therefore always has a pre-stored row.

DDL guarantees idempotent lookup: `promises.b_` has a `UNIQUE` constraint (migrations.py:33), so a given blinded message is stored at most once and restore resolves to a single row.

The ledger source comment at ledger.py:1454-1457 explicitly acknowledges the binding semantic: *"When a promises is once created it should be considered issued to the user since the user will always be able to restore promises later … Only call this function if the transaction is fully validated!"* — confirming the design intent that every signature is durably restorable.

### N09-R2 — Restore matching (spec L11) — PASS

**Claim:** The mint returns a `BlindSignature` only for `BlindedMessage`s it has previously signed.

**Evidence:** `Ledger.restore()` (ledger.py:1373-1389) loops over the supplied `outputs` and for each calls `crud.get_blind_signature(b_=output.B_)` (crud.py:456-470), whose SQL is:

```sql
SELECT * FROM promises WHERE b_ = :b_ AND c_ IS NOT NULL
```

The `c_ IS NOT NULL` predicate is the gate: a row is returned only if a signature (`c_`) has been written. Rows that were stored but never signed (e.g. melt-change leftovers not yet deleted) are excluded. Unmatched outputs are silently skipped — they are added to neither `return_outputs` nor `signatures`. This matches the spec wording "only respond … if they have previously signed".

### N09-R3 — Response fields (spec L11) — PASS

**Claim:** Each returned `BlindSignature` carries `amount` and keyset `id` (plus `C_`).

**Evidence:** `BlindedSignature.from_row` (base.py:271-277) constructs `cls(id=row["id"], amount=row["amount"], C_=row["c_"])`. The `id` column holds the keyset id (written by `store_blinded_message` parameter `id=keyset.id`, ledger.py:1435). The `amount` column is set both at insert time and refreshed by `update_blinded_message_signature` (crud.py:445). Both spec-required fields are therefore populated on every restored signature.

### N09-R4 — Request shape (spec L13-25) — PASS

**Claim:** `POST /v1/restore` with `{ "outputs": [<BlindedMessage>…] }`.

**Evidence:** Route declared `@router.post("/v1/restore", …, response_model=PostRestoreResponse)` (router.py:652-661). Handler `restore(payload: PostRestoreRequest)` (router.py:662). `PostRestoreRequest` (restore.py:9-12) defines `outputs: List[BlindedMessage] = Field(..., max_length=settings.mint_max_request_length)`. The `assert payload.outputs` guard (router.py:663) rejects empty input. `BlindedMessage` is the NUT-00 model, matching the spec's `Array[BlindedMessages]`.

### N09-R5 — Response shape (spec L27-36) — PASS

**Claim:** Response `{ "outputs": […], "signatures": […] }`.

**Evidence:** `PostRestoreResponse` (restore.py:21-23) defines `outputs: List[BlindedMessage] = []` and `signatures: List[BlindedSignature] = []`. Router returns `PostRestoreResponse(outputs=outputs, signatures=signatures)` (router.py:665). Field names exactly match the spec JSON keys.

### N09-R6 — Output/signature correlation (spec L38) — PASS

**Claim:** `outputs` and `signatures` have equal length and are index-aligned.

**Evidence:** In `Ledger.restore()` the two lists are appended together inside the same `if promise is not None:` branch (ledger.py:1384-1387):

```python
if promise is not None:
    promise.dleq = self._generate_dleq(output, promise)
    signatures.append(promise)
    return_outputs.append(output)
```

Because each appended pair shares one loop iteration and no entry is appended to one list without a matching entry in the other, length equality and `outputs[i] ↔ signatures[i]` correlation hold by construction. The returned `outputs` is the **filtered** subset of the request that has matching signatures — the correct interpretation of the spec (unmatched request entries are omitted from both arrays).

### N09-R7 — NUT-06 advertisement (spec L40-49) — PASS

**Claim:** Mint info exposes `{ "9": { "supported": true } }`.

**Evidence:** `features.py:126` sets `mint_features[RESTORE_NUT] = dict(supported=True)` inside `add_supported_features()`. `RESTORE_NUT` resolves to the integer key `9` (features.py:25 import). Serialised JSON is `{"supported": true}` keyed under `"9"`, matching the spec example exactly. The router also surfaces the feature string in the human-readable capabilities list at router.py:146-147 (`is_nut_supported(RESTORE_NUT)` → "Signature restore").

## Warnings

### W1 — Restore endpoint registered unconditionally (non-blocking)
**Location:** router.py:652-665.
**Observation:** The `POST /v1/restore` route is registered at import time with no guard on `is_nut_supported(RESTORE_NUT)`. Other features (e.g. the capabilities list at router.py:146) do check `is_nut_supported`. Because `features.py:126` hardcodes `RESTORE_NUT` as always supported, the endpoint is always both advertised and served — internally consistent. However, this means there is no configuration switch to disable NUT-09 independently of the advertisement: if a future deployment wanted to turn restore off, it would also have to edit `features.py` to avoid advertising a feature it no longer serves. No spec violation: the spec only requires that *if* supported is advertised the behaviour is correct, which it is.
**Risk:** None under current code paths. Cosmetic coupling only.

## Additional Observations (out of scope for MUSTs, noted for completeness)

1. **DLEQ on restore (bonus).** `restore()` regenerates a NUT-12 DLEQ proof for each restored signature via `_generate_dleq` (ledger.py:1385, 1393-1406). This is not required by NUT-09 but is harmless and有益: it also re-derives the signature (`b_dhke.step2_bob`) and asserts `C_.format().hex() == promise.C_` (ledger.py:1404-1405), raising `TransactionError("restored signature does not match promise")` on mismatch. This is a defensive integrity check that guards against a corrupted/tampered `promises.c_` column — strictly stronger than the spec demands.

2. **Deprecated v0 route.** `router_deprecated.py:363-384` exposes `/restore` (no `/v1/` prefix) using `PostRestoreRequest_Deprecated` for legacy clients. Delegates to the same `ledger.restore()`. Backward-compat shim; does not affect NUT-09 (v1) compliance.

3. **No pagination / batch size limit beyond `mint_max_request_length`.** The restore request is capped by `PostRestoreRequest.outputs` `max_length` (restore.py:11). A wallet requesting a large batch is bounded by the same global used for swap/mint. Reasonable; spec is silent on limits.

4. **No authentication.** Restore is unauthenticated by design (the wallet proves ownership by presenting the `BlindedMessage` whose secret it knows). Consistent with NUT-09, which specifies no auth. NUT-21/22 (clear/blind auth) are separate, optional, and not referenced here.

## Conclusion

NUT-09 is **fully and correctly implemented** in Nutshell. All seven normative requirements (one explicit `must` plus six implicit behavioural/shape requirements) are satisfied with direct code evidence. The storage model (store-placeholder-then-update-with-signature, guarded by a `UNIQUE(b_)` constraint and a runtime existence check) robustly upholds the "every issued signature is restorable" guarantee. The only flagged item (W1) is a non-blocking coupling between endpoint registration and feature advertisement with no observable impact under the current always-on configuration.

**Sign-off: PASS** (7 PASS / 0 FAIL / 1 non-blocking WARN).
