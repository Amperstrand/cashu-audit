## Findings

No blocking findings. No warnings. Three non-blocking observations recorded for completeness.

### Observation 1: Legacy `GET /info` endpoint returns deprecated format
- **Severity**: Informational (backwards compatibility)
- **Location**: router_deprecated.py:37-54
- **Description**: A deprecated `GET /info` endpoint (no `/v1/` prefix) returns `GetInfoResponse_deprecated` with the pre-NUT-06-PR-117 contact format (`contact: List[List[str]]` instead of `List[{method, info}]`). It is explicitly marked `deprecated=True`.
- **Impact**: None for spec compliance. The spec-compliant `/v1/info` endpoint is the canonical path. Legacy endpoint serves pre-0.15 clients only.

### Observation 2: `MintInfo` wallet-side model (mint_info.py) duplicates `GetInfoResponse` fields
- **Severity**: Informational (design note, not a violation)
- **Location**: cashu/core/mint_info.py:30-42
- **Description**: `MintInfo` (the wallet-side model for parsing a mint's `/v1/info` response) has the same fields as `GetInfoResponse` (the mint-side response model in models/info.py). They are separate classes with different helper methods. This is a deliberate separation: `MintInfo` carries query helpers (`supports_mpp`, `requires_clear_auth_path`, etc.) used by the wallet; `GetInfoResponse` carries a `model_validator` for backwards-compat contact parsing.
- **Impact**: None. Both models agree on field names and types. No schema drift observed.

### Observation 3: NUT-04/05 method settings include extension fields beyond NUT-06 example
- **Severity**: Informational (explicitly allowed by spec)
- **Location**: models/info.py:10-16, features.py:87-96
- **Description**: `MintMethodSetting` includes `method_name` and `options` (with `description: bool`) fields not shown in the NUT-06 example (L50-56). These are legitimate extensions defined in NUT-04/NUT-05 sub-specs. NUT-06 L101 explicitly states: "The settings are defined in each NUT separately."
- **Impact**: None. NUT-06 delegates nested NUT settings to their respective specs. Extension fields are additive and do not break the base schema.
