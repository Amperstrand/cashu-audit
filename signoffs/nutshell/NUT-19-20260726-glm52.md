## 0. Spec status & framing

NUT-19 is **`optional`**. The spec uses lowercase "should" / declarative language
throughout (no uppercase MUST tokens). Requirements are treated below as the
defining behavior of the feature (REQ-N). Nutshell advertises NUT-19 support as a
mint only (per `nuts/README.md`), which is the correct scope — caching is a
mint-side concern.

---

## 1. Spec requirements extracted and compliance

### REQ-1 — Elect a data structure `D` fit for fast insert / look-up / delete (eviction)
> 19.md:11 — "Any Mint implementation **should** elect a data structure `D` that maps request objects to their respective responses. `D` should be fit for fast insertion, look-up and deletion (eviction) operations. This could be ... Redis."

**PASS.** `RedisCache` (`cache.py:16-73`) backs `D` with Redis (`redis.asyncio`),
which the spec explicitly names as an acceptable choice. Redis provides O(1)
`EXISTS` / `GET` / `SET` / `SETEX` and native TTL eviction. A non-cluster and a
cluster mode are supported (`settings.mint_redis_cache_cluster` →
`RedisCluster.from_url`). The data structure satisfies all three operations.

### REQ-2 — Derive a unique key `k` from method, path, and payload
> 19.md:15 — "the mint derives a unique key `k` for it which **should** depend on the method, path, and the payload of `request`."

**PASS (negligible deviation).** `cache.py:53`:
```python
key = request.url.path + payload.model_dump_json()
```
The key incorporates **path** and **payload**. The **method** is not in the string.
This is mitigated structurally: all three cached routes are registered POST-only
(`router.py:494, 572, 604`), so FastAPI routing guarantees only POST reaches the
decorator — a GET/PUT to the same path never enters this handler. The key is
therefore unique per (method, path, payload) in practice. The deviation is
theoretical only; no collision is reachable through the registered routes.
Pydantic's `model_dump_json()` serializes fields in model-declaration order, so
key derivation is deterministic across retries for a given payload model version.

### REQ-3 — On cache miss, process the request as per usual
> 19.md:19 — "If no cached `response` is found ... The mint processes `request` as per usual."

**PASS.** `cache.py:56-65` — when `self.redis.exists(key)` is falsy, control falls
through to `result = await func(request, payload)` and the underlying handler
(`mint` / `melt` / `swap`) runs in full, unchanged. When Redis caching is disabled
(`settings.mint_redis_cache_enabled == False`), `cache()` returns a `passthrough`
wrapper (`cache.py:40-47`) that simply calls the handler — no caching, no overhead.

### REQ-4 — On cache hit, return the cached response
> 19.md:20 — "If a cached `response` is found ... The mint returns the cached `response`."

**PASS.** `cache.py:56-62` — on hit, `resp = await self.redis.get(key)` and the
decorator returns `json.loads(resp)`. The stored body is the handler's response
model serialized via `model_dump_json()`; on replay it is returned as a parsed
dict and FastAPI re-serializes it to JSON. The response body is byte-identical to
the original (deterministic Pydantic serialization), which the test suite asserts
via `response.text == response1.text` (`test_mint_api_cache.py:54, 89, 128`).

Note (low): the cached artifact is the JSON body only; the original HTTP status
code is not stored. Since only successful returns reach the store path (see
REQ-5), the replayed status is always 200, matching the original. No spec
violation.

### REQ-5 — Store each successful (`status_code == 200`) response under `k`
> 19.md:24 — "For each successful response on a cached endpoint (`status_code == 200`), the mint stores the response in `D` under key `k` (`D[k] = response`)."

**PASS (low-severity robustness note).** `cache.py:63-64`:
```python
result = await func(request, payload)
await self.redis.set(name=key, value=result.model_dump_json(), ex=settings.mint_redis_cache_ttl)
```
There is **no explicit `status_code == 200` guard**. The store runs unconditionally
on the success return path of `func`. Compliance holds *in practice* because the
three decorated handlers (`mint`, `melt`, `swap`) never return a non-200 body —
they either return their success response model (→ FastAPI 200) or raise
(`HTTPException` / ledger errors → non-200), and a raised exception skips the
`redis.set` line entirely (it propagates out of the decorator). Hence only
responses that FastAPI will serialize as 200 are ever cached.

This is a fragile adherence: it depends on the handler contract "return model or
raise." A future handler that returned an error-shaped model with a 4xx status
would cache it. Low severity today; a defensive `if status == 200` (or caching at
the HTTP-response layer rather than the model-return layer) would harden it.

### REQ-6 — TTL-based eviction
> 19.md:28 — "The mint decides the `ttl` (Time To Live) of cached response, after which it can evict the entry from `D`."

**PASS.** Eviction is delegated to Redis native expiry via `ex=
settings.mint_redis_cache_ttl` on every `SET` (`cache.py:64`). Default TTL is
`60 * 60 * 24 * 7` = 604800 s (1 week) (`settings.py:366`), configurable via
`MINT_REDIS_CACHE_TTL`. Redis auto-evicts at expiry; no manual cleanup needed.

### REQ-7 — Announce support via NUT-06 `nuts.19` with `ttl` + `cached_endpoints`
> 19.md:30-62 — `nuts.19 = {"ttl": <int|null>, "cached_endpoints": [{"method","path"}, ...]}`; `ttl: null` ⇒ cache indefinitely.

**PASS (minor edge-case note).** `features.py:223-247` (`add_cache_features`)
emits, only when `settings.mint_redis_cache_enabled`:
```json
"19": {
  "cached_endpoints": [
    {"method": "POST", "path": "/v1/mint/bolt11"},
    {"method": "POST", "path": "/v1/melt/bolt11"},
    {"method": "POST", "path": "/v1/swap"}
  ],
  "ttl": 604800
}
```
The schema matches the spec exactly (`method`/`path` objects, integer `ttl`).
The three advertised endpoints are **precisely** the three `@redis.cache()`-
decorated routes, in both directions:

| Advertised (features.py) | Decorated (router.py) | Match |
|---|---|---|
| POST `/v1/mint/bolt11` | `@redis.cache()` line 504 | ✅ |
| POST `/v1/melt/bolt11` | `@redis.cache()` line 586 | ✅ |
| POST `/v1/swap`         | `@redis.cache()` line 614 | ✅ |

No decorated endpoint is unannounced; no announced endpoint is undecorated.
Conditional advertisement (only when cache enabled) is correct: deployments
without Redis do not claim NUT-19 support, so wallets won't attempt replays
expecting a cache that isn't there.

Minor edge case: `ttl` is added only `if settings.mint_redis_cache_ttl:` (truthy
check). If an operator explicitly sets `MINT_REDIS_CACHE_TTL=None` to request
indefinite caching, the `ttl` key is **omitted** from the announcement rather
than emitted as `null`. The spec signals indefinite caching with `"ttl": null`;
omitting the field is arguably non-conformant for that edge configuration.
Default config (604800) is unaffected. Low severity; fix is a one-line change to
emit `ttl: None` explicitly when the setting is falsy.

## 2. Additional findings (non-blocking)

### F-1 — Redis outage at runtime fails cached endpoints open (operational, medium)
If Redis becomes unreachable *after* startup (e.g., network partition, Redis
restart), `self.redis.exists(key)` raises `ConnectionError` inside the decorator
(`cache.py:56`). This propagates as HTTP 500 — the request does **not** fall
through to normal processing. A cached endpoint thus takes a hard dependency on
Redis availability. The spec does not mandate fallthrough-on-cache-failure, so
this is not a spec violation, but it is an availability concern: a Redis blip
makes mint/melt/swap unusable even though the ledger itself is healthy.
`test_connection()` at least fails closed at startup (`app.py:39-40`) so a mint
with a misconfigured Redis never starts. A `try/except` around the `exists`/`get`
calls falling through to `func` on Redis error would make this robust.

### F-2 — TOCTOU window between `EXISTS` and `SET` (acceptable)
Two concurrent identical requests can both observe `exists(key) == False` and
both execute `func` before either `SET` lands. For NUT-19 this is acceptable
because (a) the feature targets *retry* after network drop, not concurrent
forking, and (b) the ledger enforces real correctness independently (quote
idempotency for mint/melt, input-spent checks for swap). The cache is a
performance/replay optimization layered on top, not the source of truth. No fix
required.

### F-3 — Tests are conditionally skipped without Redis (coverage gap)
`tests/mint/test_mint_api_cache.py` validates all three endpoints (mint, swap,
melt) end-to-end asserting `response.text == response1.text` on replay. All
three are guarded by `@pytest.mark.skipif(not settings.mint_redis_cache_enabled)`,
so CI without a live Redis never exercises the cache path. When enabled, the
tests prove the core NUT-19 contract. Adequate for an optional feature; the gap
is environmental, not a code defect.

### F-4 — `RedisCache()` instantiated at import time (safe)
`router.py:57` constructs `RedisCache()` unconditionally at module import. This
is safe: `__init__` (`cache.py:20-27`) only touches Redis if
`mint_redis_cache_enabled`, otherwise it is an inert object and `cache()` returns
the `passthrough` wrapper. Deployments with caching disabled incur no Redis
dependency.

## 3. Verdict

**PASS.** Nutshell's NUT-19 implementation is conformant. All seven spec
requirements are met:

- ✅ Redis-backed `D` with fast insert/lookup/delete and native TTL eviction
- ✅ Key derivation from path + payload (method omitted but routing-discriminated; negligible)
- ✅ Correct cache-miss → process / cache-hit → return-cached discrimination
- ✅ Successful (200) responses stored; error paths skip storage via exception propagation (low-severity robustness note: no explicit status guard)
- ✅ TTL-based eviction via Redis `EX`, default 1 week, configurable
- ✅ NUT-06 `nuts.19` announcement with correct schema; advertised endpoints exactly match decorated endpoints; conditionally emitted only when cache enabled
- ✅ Integration tests cover mint/swap/melt replay idempotency

Non-blocking notes (none affect conformance):
1. **Low** — no explicit `status_code == 200` guard before store (REQ-5); relies on handler raise-or-return contract.
2. **Low** — `ttl` field omitted (rather than `null`) when operator sets TTL to None for indefinite caching (REQ-7 edge case).
3. **Medium (operational)** — runtime Redis outage 500s cached endpoints rather than falling through (F-1); spec-permitting but an availability concern.

No blocking issues. Sign off.
