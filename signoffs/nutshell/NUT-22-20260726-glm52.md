## Summary

NUT-22 (Blind Authentication) is **fully implemented** in Nutshell across both mint and wallet. All four `/v1/auth/blind/` endpoints exist and function. BAT serialization (`authA` prefix, base64url), DLEQ generation/validation, protected-endpoint matching, and NUT-06 signaling are all present. Two deviations from the spec were found: incorrect error codes (81001–81004 vs spec's 31001–31004), and BATs are consumed even when the protected endpoint returns an error HTTP response.

## Deviations

### Deviation 1: Error codes use 81xxx instead of spec-mandated 31xxx (CRITICAL)

**Spec:** `error_codes.md` lines 37–40 define codes 31001–31004 for NUT-22.
**Code:** `core/errors.py` lines 243–272 define codes 81001–81004.

All four error classes exist with correct names and detail strings, but the numeric codes are wrong. A wallet conforming to the spec would not recognize these error codes. The 81xxx range appears to be an internal Nutshell convention (NUT-21 clear auth uses 80xxx instead of 30xxx — same pattern).

Additionally, `BlindAuthRequiredError` (81001) is **never actually raised** by the middleware. When a BAT is missing, the middleware raises a generic `Exception("Missing blind auth token.")` instead (`mint/middleware.py:90`). The error class is dead code for its primary use case.

**Fix:** Change error codes to 31001–31004. Use `BlindAuthRequiredError` in the middleware for missing tokens.

### Deviation 2: BATs consumed on error responses (MODERATE)

**Spec:** Line 19: "The BAT is not marked as spent if the request results in an error."

**Code:** `mint/auth/server.py:242–248` — The `verify_blind_auth` context manager calls `invalidate_proofs` after `yield` completes without exception. In Starlette's `BaseHTTPMiddleware`, `call_next` does not raise for HTTP error responses (4xx/5xx) — it returns a `Response` object. Therefore `invalidate_proofs` runs unconditionally, spending the BAT even when the protected endpoint returns an error.

The only scenario where the BAT is NOT spent is when `call_next` itself raises an exception (which is uncommon in FastAPI's normal request lifecycle). In that case, the original exception is caught and masked as `BlindAuthFailedError`, losing the original error details.

**Impact:** Wallets lose BATs on failed requests (e.g., validation errors, insufficient funds). The wallet also pre-deletes the BAT before the request (`v1_api.py:188`), so a network error also loses the BAT. This is spec-compliant for the wallet side ("SHOULD delete even on error") but the mint should not mark it as spent.

**Fix:** After `yield`, inspect the response status code. Only call `invalidate_proofs` if status < 400. This requires restructuring the context manager to receive the response object or switching from context manager to an explicit begin/commit/rollback pattern.

## Implementation Architecture

### Mint Side

- **AuthLedger** (`mint/auth/server.py`): Extends `Ledger` with a separate database, seed, and keyset (unit=auth, amount=1). Handles CAT verification via OIDC/JWT and BAT minting/spending.
- **Auth Router** (`mint/auth/router.py`): Four endpoints under `/v1/auth/blind/`.
- **Middleware** (`mint/middleware.py`): `ClearAuthMiddleware` (NUT-21) and `BlindAuthMiddleware` (NUT-22) activated when `mint_require_auth=True`.
- **Features** (`mint/features.py`): NUT-06 info response includes key `22` with `bat_max_mint` and `protected_endpoints`.
- **Keyset**: Separate auth keyset with derivation path `m/0'/999'/0'`, seed `"auth seed here"`, amounts `[1]`.

### Wallet Side

- **WalletAuth** (`wallet/auth/auth.py`): Extends `Wallet` with OIDC authentication flow, CAT management, and BAT minting.
- **Header injection** (`wallet/v1_api.py:163–188`): `_request()` method checks `requires_blind_auth_path` and attaches `Blind-auth` header. Proof is invalidated locally before the request is sent.
- **BAT minting** (`wallet/auth/auth.py:219–240`): Mints `bat_max_mint` tokens of amount 1, constructs proofs with DLEQ validation.

## Items Checked and Verified Correct

1. **BAT keyset isolation**: Auth keyset uses separate DB, seed, derivation path — no cross-contamination with ecash keysets.
2. **DLEQ in mint response**: `BlindedSignature` model includes `dleq: Optional[DLEQ]` field; `_sign_blinded_messages` populates it for every signature.
3. **DLEQ validation on wallet**: `_construct_proofs` calls `verify_proofs_dleq` which uses `b_dhke.carol_verify_dleq`.
4. **Base64url padding**: `from_base64` correctly re-adds stripped padding.
5. **DLEQ stripped from BAT header**: `AuthProof` model has no `dleq` field; `from_proof()` copies only `id`, `secret`, `C`.
6. **Path matching**: Uses `==` (exact) and `startswith` (prefix) — no regex, no injection risk.
7. **Rate limiting**: `mint_auth_rate_limit_per_minute` enforced in `verify_clear_auth` (NUT-21 side, gates BAT minting).
8. **`bat_max_mint` enforcement**: `len(outputs) > settings.mint_auth_max_blind_tokens` check before signing.
9. **Single-use BATs**: Mint sets proof pending before request, invalidates after success, unsets pending in finally.
10. **OIDC validation**: JWT signature verification via JWKS, issuer check, `azp` (authorized party) binding to mint client_id.

## Verdict

**IMPLEMENTED** with two deviations:

1. **Error codes 81001–81004 should be 31001–31004** (spec violation, easy fix).
2. **BATs spent on error responses** (spec violation, requires middleware refactor).

Neither deviation prevents the protocol from functioning — BATs are minted, validated, and consumed correctly in the happy path. The error code mismatch would cause conformant wallets to fail to recognize specific error conditions. The BAT-on-error spending causes minor user-visible resource waste.
