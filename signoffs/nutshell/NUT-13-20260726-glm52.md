**Overall verdict: PASS (SIGNED OFF)** — All five NUT-13 MUSTs are satisfied. The HMAC-SHA256 derivation matches the official V2 test vectors **byte-for-byte** and the legacy BIP32 derivation matches the V1 vectors (incl. `keyset_id_int = 864559728`). The wallet produces secrets and blinding factors that are interop-compatible with the reference test vectors, which is the property that matters for cross-wallet restore. Three non-blocking warnings: (1) `r` is not reduced `% N` per the spec's literal algorithm — a no-op for all published vectors and all practical inputs (diverges only at probability ≈ 2⁻¹²⁸, where Nutshell crashes rather than produces a wrong value), (2) no explicit `r == 0` rejection, and (3) restore defaults deviate from the spec's *recommended* batch size / empty-batch threshold.

#### Detail on the R10 warning (severity: Low / theoretical)

Empirically determined that `coincurve.PrivateKey` (libsecp256k1) **does not reduce mod N — it rejects** out-of-range scalars:
- scalar `= N + 1` → `ValueError: Secret scalar must be greater than 0 and less than <N>`
- scalar `= 0`     → `ValueError`
- scalar `= N - 1` → accepted unchanged
- 2000 random 32-byte digests → all accepted (P[digest ≥ N] ≈ 2⁻¹²⁸)

Consequences:
1. **No silent-wrong-result risk.** In the only case where `raw != raw % N` (digest ≥ N, probability ≈ 2⁻¹²⁸), Nutshell raises rather than producing a divergent `r`. There is no value of `seed`/`keyset_id`/`counter` for which Nutshell silently derives a different `r` from a reducing reference wallet *and* continues.
2. **Interop is preserved.** A digest is < N with probability 1 − 2⁻¹²⁸, so Nutshell's `r` equals the spec-reduced `r` for all practical inputs. Confirmed against the official V2 vectors below.
3. **It is still a real, if cosmetic, spec-deviation.** The spec algorithm (L40) and both reference code examples (L93 `r = x % SECP256K1_N`; L173 `r = x % SECP256K1_N`) explicitly reduce. Nutshell relies on libsecp256k1's validator instead. A one-line `int.from_bytes(r, "big") % N` fix would make this literal-conformant with zero behaviour change for any in-range input.
4. The unit test `test_nut13_spec_compliance` (test_wallet_keysets_v2.py:204-228) codifies Nutshell's non-reducing behaviour (`expected_r = hmac.digest(...)` with no `% N`), so it self-consistently passes but would not catch a regression that broke reduction if reduction were later added. This is a test-codifies-the-deviation smell.

## Findings (non-blocking)

1. **[Low] `r` not reduced `% N` (R10).** secrets.py:186. Theoretical-only divergence at P ≈ 2⁻¹²⁸; manifests as a `ValueError` crash, never a wrong `r`. Fix is one line:
   ```python
   r_int = int.from_bytes(hmac.new(self.seed, base + b"\x01", hashlib.sha256).digest(), "big") % SECP256K1_N
   r = r_int.to_bytes(32, "big")
   ```
   Note: applying this fix requires updating `test_nut13_spec_compliance` (which currently asserts the unreduced digest) so the test reflects the spec rather than the old implementation.

2. **[Low] No explicit `r == 0` rejection.** secrets.py:186 / 226. Spec example raises `RuntimeError("Derived invalid blinding scalar r == 0")`. Nutshell instead relies on coincurve to reject the zero scalar (which it does, as `ValueError`). Same outcome, less informative error. Combined with (1), an `r == 0` would surface as an opaque coincurve `ValueError` deep in `generate_n_secrets` rather than a named NUT-13 error.

3. **[Low] Restore defaults deviate from recommendation (R13/R14).** batch=25 (rec 100), to=2 (rec 3). Both are CLI-overridable and are recommendations, not MUSTs. Worth a one-line docstring/`--help` note that the spec recommends 100/3 so users can opt into the conservative value.

4. **[Info] No published V2 test vector exercises the `r ≥ N` boundary.** All five published V2 `r` values are `< N`, so they cannot distinguish a reducing from a non-reducing implementation. Nutshell matches them either way. Filing an upstream request for a boundary vector (or a vector with `r_raw > N`) would close the only remaining conformance ambiguity.

5. **[Info] `_generate_random_secret` (secrets.py:99-107) is non-deterministic** and explicitly documented as unrestorable ("We won't be able to restore any ecash generated with these secrets"). It is only used by `generate_locked_secrets` for P2PK/HTLC *send* outputs whose secret is the receiver's lock, not a wallet-derived counter secret — so it does not undermine NUT-13 restore for the wallet's own balance. No action required; flagged for completeness.

## Positive observations
- Mnemonic handling is robust: BIP39 validity checked (`mnemo.check`, secrets.py:74), seed stored alongside mnemonic, three init paths (new/given/load) handled explicitly and idempotently (secrets.py:28-97).
- Counter operations are atomic: `bump_secret_derivation` runs inside `db.get_connection(lock_table="keysets")` with `skip` flag for optimistic flows like `POST /mint` where success isn't guaranteed (secrets.py:190-211). This correctly avoids burning counter slots on failed mints.
- Restore counter rollback (wallet.py:1473-1483) reverts the counter to `last_restore_count` after probing past the end, so an exploratory restore doesn't leave the counter pointing into empty space.
- Version dispatch is exhaustive: unknown versions raise `ValueError("Unsupported keyset version")` (secrets.py:134), tested by `test_error_handling`.

## Recommendation
**Sign off.** NUT-13 is correctly and interop-compatibly implemented. The derivation matches the official V1 and V2 test vectors exactly, all five MUSTs hold, and the counter/restore machinery is sound. The three Low/Info findings are non-blocking polish items; the only one I'd prioritise is the one-line `% N` reduction (finding 1) plus updating its test, purely for literal spec conformance — it changes no observable behaviour on any realistic input.
