## Observations (non-blocking, no spec impact)

1. **Backward compatibility shim**: `router_deprecated.py:285-314` exposes legacy `POST /v1/split` mapping old `{proofs, amount, outputs}` → `Ledger.swap`. Not a spec violation; NUT-03 does not forbid deprecated endpoints. Old `amount`-split response shape (`{fst, snd}`) is preserved for clients < 0.13.

2. **`swap_id` not populated**: In `swap()`, `_store_blinded_messages(outputs, keyset=keyset, conn=conn)` (ledger.py:1346) is called without `swap_id`, so swap-originated blinded messages are not tagged with a swap identifier in the DB. NUT-03 does not require swap tracking, so this is not a deviation. It only affects internal traceability/mint accounting granularity.

3. **`@redis.cache()` on swap endpoint**: router.py:614 applies a cache decorator to the mutating `/v1/swap` endpoint. This is a NUT-19 (Cached Responses) feature keyed on client cache-control headers; absent those headers it does not cache mutating responses. Out of scope for NUT-03 and does not affect swap correctness. Flagged only for awareness.

4. **Rate limiting**: `@limiter.limit("{mint_transaction_rate_limit_per_minute}/minute")` (router.py:613) protects against swap flooding. Not required by NUT-03 but a sound operational guard.

5. **DLEQ included**: Signatures returned by swap include NUT-12 DLEQ proofs (`_sign_blinded_messages` L1504). This is a superset of NUT-03 (which only requires `BlindSignature {amount, id, C_}`) and is harmless for clients that ignore the optional `dleq` field.

## Verdict

**PASS.** Nutshell's NUT-03 swap implementation satisfies every MUST in the specification:

- Correct endpoint (`POST /v1/swap`) and wire format (`PostSwapRequest`/`PostSwapResponse`).
- Inputs are fully verified (BDHKE signatures, spendability, spending conditions, duplicates, secret/witness criteria).
- Inputs are invalidated (spent) and new blind signatures issued.
- The entire verify→invalidate→sign sequence executes atomically inside a single row-locked DB transaction.
- Concurrent-swap double-spend is prevented by a two-layer pending-set + table-lock mechanism.
- Value conservation is enforced with a balance equation that is strictly stronger than the spec (accounts for NUT-02 input fees).

No FAILs. No WARNs. No spec deviations.
