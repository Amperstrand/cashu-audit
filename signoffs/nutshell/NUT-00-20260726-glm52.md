## Findings

### Finding 1: Mint URL trailing-slash normalization not enforced at serialization layer
- **Severity**: Low (non-blocking)
- **Location**: base.py:1223-1231 (TokenV3Token), base.py:1392,1404-1405 (TokenV4.m/set_mint)
- **Description**: NUT-00 spec L195 (V3) says "The mint URL must be stripped of any trailing slashes" and L281 (V4) says "The mint URL **MUST** be normalized by stripping any trailing slashes (`/`)". Neither `TokenV3Token` nor `TokenV4` applies `rstrip("/")` during serialization or deserialization. The mint URL is stored and emitted as-is.
- **Impact**: In practice, Nutshell normalizes mint URLs when they are first stored in the wallet's mint list (upstream of token serialization), so tokens produced by Nutshell typically have clean URLs. However, a token received from an external source with trailing slashes would be stored verbatim without normalization, potentially causing URL-matching mismatches during swap operations.
- **Recommendation**: Add `self.m = mint.rstrip("/")` in `TokenV4.set_mint()` and `TokenV3Token.__init__`, or apply `rstrip("/")` in `serialize_to_dict` for both V3 and V4.

### Finding 2: Short keyset ID resolution not implemented in model layer
- **Severity**: Low (informational)
- **Location**: base.py:1432-1453 (TokenV4.proofs property)
- **Description**: NUT-00 spec L298 says "When a short keyset ID is encountered, the wallet **MUST** resolve it to the corresponding full keyset ID before processing the contained `Proof` objects." The `TokenV4` model accepts short IDs (8-byte `i` field) and passes `token.i.hex()` through as the proof `id` without resolution. The resolution logic (looking up known keysets by short ID prefix) would need to live in the wallet layer that consumes these models, which is outside the 4 audited files.
- **Impact**: The models correctly accept both short and full representations (no rejection), but downstream consumers must handle resolution. If a wallet constructs a `Proof` directly from `TokenV4.proofs` without resolving a short ID, the proof will carry a short ID that the mint doesn't recognize (spec L302: "All API endpoints exposed by the mint use the full keyset ID").
- **Recommendation**: Verify that wallet-layer code (outside audited scope) resolves short IDs before sending proofs to the mint. Consider adding a resolution step in `TokenV4.proofs` or a validation method on the model.

### Finding 3: hash_to_curve only tries `0x02` prefix (correct per spec, worth documenting)
- **Severity**: Informational (no action needed)
- **Location**: b_dhke.py:87
- **Description**: The spec formula (L36) is `Y = PublicKey('02' || SHA256(msg_hash || counter))` — only the `0x02` prefix is used. Nutshell matches this exactly: `PublicKey(b"\x02" + _hash)` (L87). Standard try-and-increment schemes sometimes alternate between `0x02` and `0x03` prefixes, but the Cashu spec explicitly mandates `0x02` only, incrementing the counter instead. Nutshell is spec-compliant. This is documented here to preempt confusion.
- **Impact**: None — implementation matches spec.
