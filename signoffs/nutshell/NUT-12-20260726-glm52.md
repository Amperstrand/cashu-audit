## 1. Spec MUSTs extracted and compliance

### MUST-1 — Wallets MUST verify DLEQ in a mint `BlindSignature` response (Alice)
> 12.md:128 — "If a DLEQ proof is included in the mint's `BlindSignature` response, wallets **MUST** verify the DLEQ proof."

**PASS.** `Wallet._construct_proofs()` (`wallet/wallet.py:1052-1118`) attaches the
mint-returned `(e, s)` plus the wallet's blinding factor `r` into a `DLEQWallet`
(line 1097-1100), then unconditionally calls `self.verify_proofs_dleq(proofs)`
(line 1109) before storing/returning the proofs. `verify_proofs_dleq` runs
`b_dhke.carol_verify_dleq(...)` and raises on failure. This path is reached on
every mint (NUT-04) and swap (NUT-03).

### MUST-2 — Wallets MUST verify DLEQ in a received token (Carol)
> 12.md:150 — "If a DLEQ proof is included in a received token, wallets **MUST** verify the proof."

**PASS.** `Wallet.redeem()` (`wallet/wallet.py:716-726`) — the entry point for
redeeming/receiving a token from another user — calls `self.verify_proofs_dleq(proofs)`
(line 725) before the split. Verification reconstructs `B'`/`C'` from the included
blinding factor `r` exactly as the spec's Carol equations prescribe.

### MUST-3 — Random nonces (if used) MUST come from a CSPRNG
> 12.md:46 (CAUTION) — "Mints that use random nonces **MUST** source them from a cryptographically secure RNG."

**PASS (stronger than required).** Nutshell does not use a random nonce at all.
`derive_dleq_nonce()` (`b_dhke.py:129-157`) derives the nonce deterministically via
`HMAC-SHA256(key=a, "Cashu_DLEQ_R_v1" || A || B' || C' || ctr)` with rejection sampling,
matching the spec's recommended deterministic scheme (12.md:42-44 "Mints **SHOULD** use
a rejection-sampled deterministic nonce"). This removes all RNG-failure risk.

### MUST-4 — Implementation MUST reproduce the deterministic-nonce `e` and `s` exactly
> `tests/12-tests.md:18` — "an implementation **MUST** reproduce `e` and `s` exactly."

**PASS.** Executed the official vector (`a=0x02`, fixed `B_`) against Nutshell's

### MUST-5 — Verification `e == hash(R1, R2, A, C_)` MUST pass
> `tests/12-tests.md:32`

**PASS.** `alice_verify_dleq()` returns `True` for the deterministic vector and for the

## 4. Findings

### FINDING-1 (LOW) — `verify_proofs_dleq` early-`return` skips rest of batch
**Location:** `cashu/wallet/wallet.py:1031-1033`
```python
def verify_proofs_dleq(self, proofs: List[Proof]):
    for proof in proofs:
        if not proof.dleq:
            logger.trace("No DLEQ proof in proof.")
            return          # <-- should be `continue`
```
**Effect:** If the first proof in a batch lacks a DLEQ, the function returns
immediately and never inspects the remaining proofs. In a *mixed* batch
`[no-dleq, has-dleq-but-invalid]`, the invalid proof would not be caught.
**Severity rationale:** Low. Proofs in a single receive/mint batch normally share
uniform DLEQ presence (all from the same mint response or the same sender's token),
so the mixed case is atypical. The spec's MUST ("if a DLEQ proof is included … MUST
verify") is satisfied for the common paths. **Fix:** change `return` → `continue`.
No impact on the signoff verdict.

No other deviations found. No HIGH/CRITICAL findings.

## 5. Verdict

**PASS.** Nutshell's NUT-12 DLEQ implementation is conformant with the specification.
All five spec MUSTs are satisfied, all official test vectors reproduce exactly, the
deterministic rejection-sampled nonce matches the spec's recommended (stronger-than-MUST)
scheme, DLEQ is produced on every signing path (mint/swap/melt-change/restore) and
verified on both the Alice (mint-response) and Carol (received-token) wallet paths, and
the NUT-06 feature flag is advertised correctly. The single LOW finding (early-`return`
in batch verification) does not affect correctness on real-world usage and is a one-line
hardening fix.
