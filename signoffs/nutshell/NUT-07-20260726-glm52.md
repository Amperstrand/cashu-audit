## 1. Spec MUSTs extracted and compliance

### MUST-1 — Response `states` array MUST preserve request `Ys` order

> 07.md:68 — "The elements of the `states` array **MUST** be returned in the same order as the corresponding `Ys` checked in the request."

**PASS.** `DbReadHelper.get_proofs_states()` (`db/read.py:43-77`) iterates over the input `Ys` list sequentially in a `for Y in Ys:` loop (line 64) and appends each result to `states` in the same iteration order. The spent/pending lookups are batched into dictionaries (`_get_proofs_spent`, `_get_proofs_pending`) keyed by Y-value, then the loop preserves the original ordering. No sort, no dict iteration, no async gather that could reorder — the mapping is strictly positional.

```python
    proofs_pending = await self._get_proofs_pending(Ys, conn)
    for Y in Ys:                          # ← iterates request order
        ...
        states.append(ProofState(...))    # ← appends in same order
return states
```

### MUST-2 — Mints MUST remember PENDING proofs to avoid reuse

> 07.md:21 — "Mints **MUST** remember which proofs are currently `PENDING` to avoid reuse of the same token in multiple concurrent transactions. This can be achieved with for example mutex lock whose key is the `Proof`'s `Y`."

**PASS (robust implementation).** Nutshell uses a dedicated `proofs_pending` database table backed by table-level locks in a transaction. The full lifecycle:

1. **Set PENDING** (`db/write.py:55-100`): `_verify_spent_proofs_and_set_pending()` acquires a connection with `lock_table="proofs_pending"`, `lock_timeout=1` (lines 74-77). Inside the lock it: (a) verifies proofs aren't already spent (`_verify_proofs_spendable`), (b) verifies proofs aren't already pending (`_validate_proofs_pending`, raises `ProofsArePendingError` if any duplicate), (c) inserts each proof into `proofs_pending` via `crud.set_proof_pending`. The entire check-then-insert is atomic within the locked connection.

2. **Validate no double-pending** (`db/write.py:137-153`): `_validate_proofs_pending()` queries `get_proofs_pending` for the input Ys and raises if any match exists. This runs *inside* the lock, preventing TOCTOU races.

3. **Unset PENDING** (`db/write.py:102-135`): `_unset_proofs_pending()` removes proofs from the `proofs_pending` table, either marking them spent (via `invalidate_proofs` which moves them to `proofs_used`) or returning them to unspent (on transaction failure).

The spec says mutex "whose key is the Proof's Y" as an example. Nutshell achieves equivalent safety via DB table locking: two concurrent transactions cannot both set the same Y as pending because the first one's lock blocks the second's `_validate_proofs_pending` check. This is correct and arguably more durable than an in-memory mutex (survives crashes).

## 4. Concurrency analysis

The spec's critical MUST is preventing concurrent reuse of the same token. The attack scenario: two simultaneous swap/melt requests using the same proof. Nutshell's defense:

| Layer | Mechanism | File:line |
|---|---|---|
| DB lock | `lock_table="proofs_pending"`, `lock_timeout=1` on set-pending connection | `db/write.py:75-76` |
| Spent check | `_verify_proofs_spendable` (raises `ProofsAlreadySpentError`) | `db/write.py:80` |
| Pending check | `_validate_proofs_pending` (raises `ProofsArePendingError`) | `db/write.py:82` |
| Atomic insert | `set_proof_pending` per proof inside locked txn | `db/write.py:85-87` |

Two concurrent transactions T1 and T2 with the same proof Y:
1. T1 acquires `proofs_pending` lock → validates (not spent, not pending) → inserts Y as pending → commits → releases lock.
2. T2 blocks on `proofs_pending` lock until T1 releases (or times out after 1s).
3. T2 acquires lock → validates → finds Y in `proofs_pending` → raises `ProofsArePendingError`.

This is a correct mutex-style exclusion. The table-level lock is appropriate for SQLite (database-level locking anyway) and safe for PostgreSQL (table-level advisory lock within the transaction). The spec's "mutex lock whose key is the Proof's Y" is listed as an example ("for example"), not a strict requirement on the locking granularity.
