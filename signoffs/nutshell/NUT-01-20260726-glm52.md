## Findings

No blocking findings. No warnings. Three non-blocking observations recorded for completeness.

### Observation 1: Legacy `/keys` endpoint returns pre-spec flat format
- **Severity**: Informational (not a violation — backwards compatibility)
- **Location**: router_deprecated.py:58-76
- **Description**: A deprecated `GET /keys` endpoint (no `/v1/` prefix) returns a flat `{amount: pubkey}` dict for the current keyset only (no `keysets` wrapper). This predates the NUT-01 `GetKeysResponse` schema. It is marked `deprecated=True` in FastAPI (router_deprecated.py:67).
- **Impact**: None for spec compliance. Wallets using the spec-compliant `/v1/keys` endpoint are unaffected. The legacy endpoint exists solely for backwards compatibility with pre-0.15 clients.

### Observation 2: `/v1/keys/{keyset_id}` base64→hex sanitization for legacy IDs
- **Severity**: Informational (backwards compatibility shim)
- **Location**: router.py:305-311
- **Description**: Before lookup, the endpoint attempts `int(keyset_id, 16)`; on `ValueError` it sanitizes base64-urlsafe IDs (`-`→`+`, `_`→`/`) for pre-0.15 keyset IDs. This is a transparent compatibility shim, not a spec deviation.
- **Impact**: None. Modern hex keyset IDs (`00`/`01` prefix) pass through unchanged.

### Observation 3: Keyset ID derivation spans three versions (v0/v1/v2)
- **Severity**: Informational
- **Location**: base.py:1116-1180, keys.py:55-103
- **Description**: `MintKeyset.generate_keys()` selects keyset ID derivation by `version_tuple`: base64 (<0.12), `derive_keyset_id_deprecated` (<0.15), `derive_keyset_id` v1 `00`-prefix (<0.20), `derive_keyset_id_v2` `01`-prefix (≥0.20). NUT-01 does not mandate a specific keyset ID format (that is NUT-02's domain), so all versions are acceptable here. The `id` field is returned verbatim regardless of version.
- **Impact**: None for NUT-01. The variety of ID formats is a NUT-02 concern.
