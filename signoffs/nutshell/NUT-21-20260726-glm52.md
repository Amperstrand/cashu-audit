**Overall verdict: PARTIAL PASS** — The core clear-authentication mechanism is functional and spec-aligned for the happy path: the mint advertises `MintClearAuthSetting` in NUT-06, performs exact/prefix path matching without regex (satisfying the security CAUTION), verifies JWT signatures via JWKS with RS256/ES256, checks expiry, and reads the CAT from the `Clear-auth` header. The wallet injects the header correctly and uses the spec-mandated `http://localhost:33388/callback` redirect. **However, 3 spec MUSTs FAIL:** (1) error code `30001` is never returned — the mint raises a generic `Exception` (→ code `0`) for missing tokens and `ClearAuthRequiredError` (code `80001`) is dead code; (2) error code `30002` is returned as `80002` (`ClearAuthFailedError`); (3) the wallet's authorization-code flow does not implement PKCE (`code_challenge`/`code_verifier` absent), contradicting the spec's "MUST enable the authorization code flow with PKCE for public clients" (L20).

## Deviations & Findings

### FAIL-1: Error code `30001` never returned (spec L106)
**Location**: `middleware.py:67`; `errors.py:227-232`
**Spec ref**: L106 (`30001`: Endpoint requires clear auth)

`ClearAuthRequiredError` (code `80001`) is dead code — defined but never imported or raised anywhere in the codebase. When a request to a protected endpoint lacks a `Clear-auth` header, `ClearAuthMiddleware.dispatch` raises `Exception("Missing clear auth token.")` — a bare Python exception. The `catch_exceptions` handler in `app.py:107-114` catches this as a non-`CashuError`, returning HTTP 400 with `{"detail": "Missing clear auth token.", "code": 0}`.

**Impact**: A wallet checking for error code `30001` to detect "auth required, initiate OIDC login" will never see it. The wallet receives code `0` (ambiguous generic error) instead of the spec-defined `30001`. Interop with spec-compliant wallets is broken for this error path.

**Fix**: Replace `raise Exception("Missing clear auth token.")` (middleware.py:67) with `raise ClearAuthRequiredError()`, and change `ClearAuthRequiredError.code` from `80001` to `30001`.

### FAIL-2: Error code `30002` returned as `80002` (spec L107)
**Location**: `errors.py:235-240`; `server.py:175`
**Spec ref**: L107 (`30002`: Clear authentication failed)

`ClearAuthFailedError` uses code `80002`. The spec and `error_codes.md` (L36) mandate `30002`. The error IS raised correctly (on JWT verification failure), but the numeric code is wrong.

**Impact**: A wallet checking for `30002` to distinguish auth-failure from other errors will not match. The `8xxxx` code range is non-standard and undocumented in the spec.

**Fix**: Change `ClearAuthFailedError.code` from `80002` to `30002`.

### FAIL-3: Authorization Code flow lacks PKCE (spec L20)
**Location**: `openid_client.py:258-301` (auth URL), `openid_client.py:161-188` (token exchange)
**Spec ref**: L20 ("MUST enable the authorization code flow with PKCE for public clients")

The wallet's `authenticate_with_authorization_code` does not generate a PKCE code verifier/challenge pair. The authorization request (L268-274) omits `code_challenge` and `code_challenge_method`. The token exchange (L163-167) omits `code_verifier`. Without PKCE, a intercepted authorization code can be exchanged by an attacker — the exact attack PKCE prevents (RFC 7636). Nutshell is a public client (default `client_secret=""`), making PKCE essential.

**Impact**: Authorization-code interception attacks are not mitigated. If an attacker intercepts the `code` parameter from the `localhost:33388/callback` redirect (e.g. via a malicious local process or browser extension), they can redeem it for tokens.

**Fix**: Generate `code_verifier = secrets.token_urlsafe(64)`, compute `code_challenge = base64url(sha256(code_verifier))`, send `code_challenge` + `code_challenge_method=S256` in the auth URL, and send `code_verifier` in the token exchange.

### WARN-1: Wildcard `*` position not validated (spec L54)
**Location**: `mint_info.py:21`
**Spec ref**: L54 ("The `*` wildcard, if present, MUST be the final character only.")

`_match_protected_endpoint` checks `endpoint_path.endswith("*")` but does not reject paths where `*` appears in a non-final position (e.g. `/v1/mint/bolt*/extra`). Such a path would be treated as prefix `/v1/mint/bolt*/extr` — semantically incorrect. This is a mint-operator config validation gap, not a wallet-input vulnerability (the CAUTION at L66 is satisfied). **Low severity**: only affects self-misconfigured mints.

### INFO-1: `azp` (authorized party) binding — security hardening beyond spec
**Location**: `server.py:116-124`

After JWT verification, the mint checks the `azp` claim (Keycloak-specific) against `settings.mint_auth_oicd_client_id`, rejecting tokens issued to a different client in the same OIDC realm. This is not required by NUT-21 but is a thoughtful defense against cross-client token confusion in multi-client Keycloak deployments. **No action required.**

### INFO-2: Redundant issuer pre-check
**Location**: `server.py:71-89`

`_verify_oicd_issuer` decodes the JWT without signature verification to check `iss`, then `_verify_decode_jwt` decodes again WITH signature verification and `issuer=self.issuer` (which already validates `iss`). The pre-check is redundant — the signed decode at L108-114 already rejects mismatched issuers via PyJWT's `issuer=` parameter. Harmless but doubles the decode work. **No action required.**

### INFO-3: Per-user rate limiting
**Location**: `server.py:178-181`

After successful JWT verification, `verify_clear_auth` calls `assert_limit(user.id, settings.mint_auth_rate_limit_per_minute)`. This rate-limits authenticated users by their OIDC `sub` identifier — exactly the use case the spec suggests at L72 ("The `sub` identifier can, for example, be used to rate limit the user"). **No action required.**

### INFO-4: Wallet supports all three recommended auth flows
**Location**: `openid_client.py:20-23, 202-226, 323-349, 358-450`

The wallet implements Authorization Code (L258-301), Password/ROPC (L323-349), and Device Code (L358-450) flows, matching the spec's L84 recommendations ("mobile → auth code, CLI → device code, headless → ROPC"). Flow selection auto-detects from `grant_types_supported` (L76-110). The Device Code flow handles `authorization_pending`, `slow_down`, `access_denied`, and `expired_token` polling errors correctly. **No action required** (other than the PKCE gap in FAIL-3).

### INFO-5: Password/ROPC flow offered despite spec SHOULD NOT
**Location**: `openid_client.py:323-349`; `wallet/auth/auth.py:57-60`
**Spec ref**: L24 ("The `password` flow SHOULD NOT be used")

The wallet offers the ROPC password flow when `username` is set (auth.py:57-60). The spec (L24) says ROPC "SHOULD NOT be used as it requires handling the user's credentials in the wallet application." This is a `SHOULD NOT` (not MUST), so it is not a hard violation, and the spec itself acknowledges ROPC as an option for "headless wallets" (L84). The wallet stores credentials in its database (auth.py:190-199). **Acceptable for CLI/headless use case; document the risk.**

## Verdict

**PARTIAL PASS** — Nutshell's NUT-21 implementation correctly handles the core clear-authentication mechanism: NUT-06 capability advertisement, exact/prefix path matching without regex (satisfying the security-critical CAUTION at L66), JWT signature verification via JWKS with the spec-mandated RS256/ES256 algorithms, expiry checking, `Clear-auth` header injection/extraction, the `localhost:33388/callback` redirect, and per-user rate limiting via the `sub` claim.

**Three spec MUSTs FAIL and should be fixed before claiming full NUT-21 compliance:**

1. **Error code `30001` is never returned** (FAIL-1): `ClearAuthRequiredError` is dead code; missing tokens produce generic code `0`. Wallets cannot detect "auth required" programmatically.
2. **Error code `30002` is returned as `80002`** (FAIL-2): the numeric code contradicts the spec and `error_codes.md`.
3. **Authorization Code flow lacks PKCE** (FAIL-3): the wallet sends no `code_challenge`/`code_verifier`, leaving the public client vulnerable to authorization-code interception (RFC 7636). The spec explicitly mandates PKCE for public clients (L20).

The error-code fixes (1, 2) are trivial one-line changes. The PKCE fix (3) requires adding verifier/challenge generation to `OpenIDClient.authenticate_with_authorization_code` and `exchange_code_for_token` — approximately 10 lines. All three are low-effort, high-value corrections.
