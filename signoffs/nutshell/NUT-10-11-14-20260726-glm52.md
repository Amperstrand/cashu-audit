## Findings

### Finding 1: Divergence table (divergences/NUT-10-11-14.md) is outdated for Nutshell
- **Severity**: Medium (documentation accuracy)
- **Description**: 5 of 8 divergence entries mischaracterize Nutshell's behavior:
  - DIV-2: Claims "rejected as malformed" → actually only pubkey dupes caught
  - DIV-3: Claims "rejected upfront (blocks refund too)" → actually rejected at verification, refund not blocked
  - DIV-4: Claims "rejected" → actually accepted
  - DIV-5: Claims "lowercase only" → actually accepts mixed case
  - DIV-7: Claims "ignores extra signature" → actually rejects (conditions.py:148-149)
  - DIV-8: Claims "accepts and ignores" witness → actually rejects (conditions.py:210-213)
- **Impact**: The divergence table is used to guide cross-implementation compatibility. Inaccurate entries could lead to wrong alignment decisions. cashu-cf's signoff claims alignment with Nutshell on DIV-7 and DIV-8, but Nutshell actually behaves like CDK (rejects) on both.
- **Recommendation**: Update the divergence table to reflect actual Nutshell behavior. Reclassify DIV-7 and DIV-8 as "all implementations agree" (CDK and Nutshell both reject).

### Finding 2: Unknown kind fails via unhandled ValueError (not explicit validation)
- **Severity**: Low
- **Location**: conditions.py:217 (`SecretKind(secret.kind)`)
- **Description**: When a valid NUT-10 JSON secret has an unknown `kind` (e.g., `"FOO"`), `SecretKind(secret.kind)` raises `ValueError` which is not caught by the `except Exception` at L206 (it's outside the try block). The error propagates as an unhandled exception rather than a clean `TransactionError`.
- **Impact**: The transaction is still rejected (fail-closed), but the error response may be a 500 Internal Server Error instead of a clean 4xx with a descriptive message.
- **Recommendation**: Wrap the kind check in a try/except or add explicit validation: `if secret.kind not in [k.value for k in SecretKind]: raise TransactionError(...)`.

### Finding 3: No tag structure validation (NUT-10)
- **Severity**: Low
- **Location**: secret.py:16-56 (`Tags` class)
- **Description**: NUT-10 L54-68 specifies tags must be "array of arrays of non-empty strings" with each tag having "ONE or more strings". The `Tags` pydantic model (`List[List[str]]`) doesn't validate:
  - Tags with zero elements (`[]`)
  - Tags with empty strings (`["locktime", ""]`)
  - Non-string tag values (`["locktime", 123]`)
- **Impact**: Malformed tags are silently accepted. In practice, downstream code would likely fail on malformed data, but the spec's explicit validation requirements are not met.
- **Recommendation**: Add a pydantic validator on the `Tags` model to enforce non-empty arrays of non-empty strings.

### Finding 4: SIG_ALL melt message omits quote_id
- **Severity**: Medium
- **Location**: nut11.py:6-16 (`sigall_message_to_sign`)
- **Description**: NUT-11 L153-161 specifies that for melt transactions, the SIG_ALL message must include the `quote_id`: `msg = secret_0 || C_0 || ... || quote_id`. Nutshell's `sigall_message_to_sign()` only concatenates inputs (secret+C) and outputs (amount+B_), without appending the quote_id. The `message_to_sign` parameter in `_verify_sigall_spending_conditions` (conditions.py:338) could override this, but the default code path for melts via `verify_inputs_and_outputs` (verification.py:42-74) does not pass a quote_id-enriched message.
- **Impact**: SIG_ALL signatures on melt transactions may not match the spec-defined message format. Wallets following the spec strictly would produce signatures that Nutshell cannot verify (and vice versa).
- **Recommendation**: Pass `quote_id` through the verification pipeline and append it to the SIG_ALL message for melt operations.

### Finding 5: HTLC hash length not explicitly validated
- **Severity**: Low
- **Location**: nut14.py:29-34
- **Description**: The preimage length is checked (`len(preimage) != 64`), but the hash (`htlc_secret.data`) length is not explicitly validated. NUT-14 L86 specifies the hash should be "64-character lowercase hexadecimal string". An invalid-length hash would cause `bytes.fromhex()` to produce wrong-length bytes, and the comparison would fail — but the error message would be confusing ("HTLC preimage does not match" rather than "invalid hash length").
- **Impact**: Low — invalid hashes are rejected, just with a misleading error message.
- **Recommendation**: Add `if len(htlc_secret.data) != 64: raise TransactionError("HTLC hash must be 64 characters.")` before the comparison.
