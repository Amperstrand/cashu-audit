## Spec → Implementation Cross-Reference

NUT-08 contains exactly **two explicit MUST clauses**, both on L43. The remainder of the spec is descriptive (mechanism, examples, NUT-06 setting). MUSTs are extracted verbatim and each checked.

### MUST clauses (spec L43)

> "`Bob` **MUST** return the all blank signatures with a value greater than 0 in the same order as the blank outputs were received and should omit all blind signatures with value 0."

This sentence contains two distinct mandates:

#### N08-R1 — Return all >0 signatures in same order as received
- **Verdict**: PASS
- **Code**: `ledger.py:284-301`
- **Trace** (`_generate_change_promises`):
  ```python
  return_amounts = amount_split(overpaid_fee)         # ascending: e.g. [4, 128, 256, 512]
  n_return_outputs = min(len(outputs), len(return_amounts))
  outputs = outputs[:n_return_outputs]                 # take FIRST n outputs, in order
  return_amounts_sorted = sorted(return_amounts, reverse=True)
  for i in range(len(outputs)):
      outputs[i].amount = return_amounts_sorted[i]     # imprint, preserving outputs order
  return_promises = await self._sign_blinded_messages(outputs)
  ```
- **Analysis**: The returned `return_promises` list is index-aligned with `outputs[:n_return_outputs]` — i.e. the wallet's first `n` blank outputs in the order they were sent. The wallet can map `return_promises[i] → my_outputs[i]` and apply the correct unblinding operation. The amounts themselves are assigned largest-first (a Nutshell implementation choice the spec does not constrain), but the *signature-to-output* mapping is preserved, which is what the spec requires for correct unblinding.
- **Spec example cross-check** (spec L29, "split 900 into 4, 128, 256, 512, return 4 promises"): `amount_split(900)` → bits set in `0b1110000100` → `[4, 128, 256, 512]`. ✓ Four non-zero promises returned in the order of the first 4 blank outputs.

#### N08-R2 — Omit all value-0 signatures
- **Verdict**: PASS
- **Code**: `ledger.py:288-291, 302-304`
- **Analysis**: Value-0 signatures are never produced. `n_return_outputs = min(len(outputs), len(return_amounts))` is the count of non-zero amounts from `amount_split` (which never returns 0-valued summands — `split.py:6-11` only appends `1 << i` for set bits). `outputs = outputs[:n_return_outputs]` truncates the wallet's output list to exactly the non-zero count. The remaining `len(outputs_wallet) - n_return_outputs` blank outputs are never signed. Additionally, any persisted unsigned blank outputs are deleted from the DB (L302-304: `delete_blinded_messages_melt_id`), so they cannot be reused.
- **Spec example cross-check** (spec L43, "10 blank outputs but only 4 used → return 4, omit 6"): with 10 outputs and `overpaid_fee=900`, `n_return_outputs = min(10, 4) = 4`. Only the first 4 outputs are signed; the other 6 are dropped + scrubbed. ✓

### Descriptive requirements (mechanism)

#### N08-R3 — Decompose overpaid fee into 2^n summands
- **Verdict**: PASS
- **Spec** (L39): "If `overpaid_fees = input_amount - fees - total_paid` is positive, `Bob` decomposes it to amounts supported by the keyset, typically `2^n`."
- **Code**: `split.py:4-11` — iterates `range(amount.bit_length())`, appends `1 << i` for each set bit. Pure 2^n decomposition (binary representation). For amount=900 (`0b1110000100`), returns `[4, 128, 256, 512]`, summing to 900.
- **Note**: The spec says "amounts supported by the keyset, typically 2^n". Nutshell always uses 2^n and does not consult per-keyset amount tables. Since all Nutshell keysets use the canonical 2^n denomination scheme, this is correct in practice.

#### N08-R4 — Amount field in blank `BlindedMessage`s is ignored by the mint
- **Verdict**: PASS
- **Spec** (L115): "The `amount` field in the `BlindedMessage`s here are ignored by `Bob` so they can be set to any arbitrary value by `Alice`."
- **Code**:
  - `ledger.py:1110-1112`: `_prepare_melt` calls `_verify_outputs(outputs, skip_amount_check=True, ...)` — explicitly skips amount validation for the change outputs.
  - `verification.py:144-147`: `# we skip the amount check for NUT-8 change outputs (which can have amount 0)` / `if not skip_amount_check: if not all([self._verify_amount(o.amount) ...])`.
  - `ledger.py:297-298`: `_generate_change_promises` overwrites `outputs[i].amount = return_amounts_sorted[i]` — the wallet's original amount is discarded and replaced with the mint-computed value.
- **Trace**: Wallet can send `amount=1` (or anything); the value is never validated and is overwritten before signing. ✓

#### N08-R5 — `change` returned ONLY IF outputs provided AND inputs > total_paid − fees
- **Verdict**: WARN (functionally equivalent; serialization differs from spec wording)
- **Spec** (L37): "`Bob` returns … the field `change` **ONLY IF** `Alice` has previously provided `outputs` for the change **AND** if the `inputs` provided were greater than the `total_amount_paid - fees`."
- **Code** (`_execute_melt_payment`, L1281-1291):
  ```python
  return_promises: List[BlindedSignature] = []
  if outputs:
      return_promises = await self._generate_change_promises(
          fee_provided=fee_reserve_provided,
          fee_paid=melt_quote.fee_paid,
          outputs=outputs, ...)
  melt_quote.change = return_promises
  ```
  `_generate_change_promises` returns `[]` when `overpaid_fee <= 0` (L267-277).
- **Analysis**:
  - *Logical condition*: ✓ Correctly evaluated. If no outputs are provided OR `overpaid_fee ≤ 0`, `return_promises = []` and no value reaches the wallet.
  - *Serialization divergence*: The `change` field is always set to `[]` (or `[sigs]`) on the `MeltQuote` object after melt; it is never left as `None`. `response_model_exclude_none=True` (router.py:240) strips `None` but not empty lists. As a result, the response JSON contains `"change": []` whenever the wallet provided outputs but no overpaid fee was due (or even when no outputs were provided — because `return_promises` defaults to `[]`). The spec's "ONLY IF" wording suggests the field should be absent (or `null`) in those cases. Functionally, every known wallet treats `change: []`, `change: null`, and a missing field as equivalent ("no change to claim"), so this is a stylistic divergence, not a functional bug.
- **Impact**: None observed. Wallets (cashu-ts, cdk) handle empty/null/absent uniformly via null-coalescing.

#### N08-R6 — Async / late-settlement also returns change
- **Verdict**: PASS
- **Spec**: L37-43 do not distinguish sync vs. async settlement; the same `change` contract applies to both melt paths.
- **Code**: `get_melt_quote` (L858-917) re-runs `_generate_change_promises` when a pending quote is later detected as SETTLED by the backend. The wallet polls `GET /v1/melt/quote/bolt11/{quote}` and receives the same `change` array on the post-settlement response. The persisted unsigned blank outputs (`_store_blinded_messages`, L1146) are re-read via `get_blinded_messages_melt_id` (L901-903) so they survive across requests. ✓

#### N08-R7 — NUT-06 advertises `{"8": {"supported": true}}`
- **Verdict**: PASS
- **Spec** (L139-147):
  ```json
  { "8": { "supported": true } }
  ```
- **Code**:
  - `nuts.py:6`: `FEE_RETURN_NUT = 8`
  - `features.py:18`: imports `FEE_RETURN_NUT`
  - `features.py:123-125`:

### Edge cases / additional observations

#### N08-R8 — Backend does not report a fee (`fee_paid` stays 0)
- **Verdict**: WARN (informational, not a spec violation)
- **Code**: `base.py:303`: `fee_paid: int = 0` (default). `ledger.py:891-892` and `ledger.py:1262-1265` only overwrite `fee_paid` when `status.fee` / `payment.fee` is truthy. If a Lightning backend reports a SETTLED payment with `fee=None`, `fee_paid` remains 0.
- **Effect**: `overpaid_fee = fee_provided - 0 = fee_provided` → wallet receives the *entire* reserve back as change. This is a generous failure mode (favors the wallet, no funds lost), but it does mean the mint absorbs the Lightning fee silently when the backend fails to report it.
- **Spec alignment**: NUT-08 says "the actual fee was X" (L29), assuming the mint knows the true fee. The behavior when the mint *cannot* determine the fee is unspecified. Nutshell's choice (treat as 0) is a reasonable default but is worth flagging for operators using backends with weak fee reporting (e.g., some custodial LNDHUB implementations).
- **Recommendation**: Optionally log a warning when a SETTLED payment has `fee=None`, so operators can detect backends that under-report fees.

#### N08-R9 — Wallet provides fewer outputs than `ceil(log2(fee_reserve))`
- **Verdict**: PASS (graceful degradation, spec-permitted)
- **Spec** (L15): wallet *should* send `max(ceil(log2(fee_reserve)), 1)` blank outputs. This is a wallet-side recommendation.
- **Code**: `ledger.py:288`: `n_return_outputs = min(len(outputs), len(return_amounts))`. If the wallet sends fewer outputs than summands, only the largest `len(outputs)` summands are returned (because `return_amounts_sorted` is descending and the loop assigns in order). The smaller summands are silently dropped — the wallet forfeits the remainder.
- **Docstring** (L247-250): explicitly documents this: "If the given number of `outputs` matches the equation defined in NUT-08, we can be sure to return the overpaid fee perfectly. Otherwise, a smaller amount will be returned."
- **Impact**: Minimal — wallets in the Nutshell/cashu-ts/cdk ecosystem correctly compute the output count. Graceful degradation is the right server-side behavior.

## Findings

### Finding 1: `change` serialized as `[]` instead of omitted when no change is due
- **Severity**: Informational (non-blocking)
- **Location**: `cashu/mint/ledger.py:1281-1291` (`_execute_melt_payment`); `cashu/core/models/melt_quote.py:56`
- **Description**: After a melt, `melt_quote.change` is always set to either `[]` or a list of signatures — never `None`. The Pydantic model's default of `None` is overwritten even when no outputs were provided (`return_promises` is initialized as `[]` and `melt_quote.change = return_promises` runs unconditionally). `response_model_exclude_none=True` does not strip empty lists, so the JSON response contains `"change": []` in no-change cases. The spec's "ONLY IF" wording (L37) implies the field should be absent in those cases.
- **Impact**: None functionally. All surveyed wallets (cashu-ts, cdk, Nutshell's own wallet) treat `change: []`, `change: null`, and a missing `change` field as semantically identical ("nothing to claim").
- **Recommendation**: Either (a) initialize `return_promises = None` and only assign when `outputs` is truthy and `overpaid_fee > 0`, or (b) leave as-is and accept the divergence as cosmetic. Low priority.

### Finding 2: Silent full-refund when backend omits `fee` on SETTLED
- **Severity**: Low (operational, non-blocking)
- **Location**: `cashu/core/base.py:303` (`fee_paid: int = 0`); `cashu/mint/ledger.py:891-892, 1262-1265`
- **Description**: `fee_paid` defaults to 0. It is overwritten only when the Lightning backend returns a truthy `fee` value on a SETTLED payment. If a backend reports SETTLED with `fee=None` (or omits the field), `_generate_change_promises` computes `overpaid_fee = fee_provided - 0`, returning the entire fee reserve to the wallet. The mint silently absorbs the actual Lightning fee.
- **Impact**: The mint loses money on every settle-without-fee for backends that under-report. No client-side impact. The spec assumes the mint can determine the actual fee (L29); the failure mode is unspecified.
- **Recommendation**: Distinguish "fee unknown" from "fee is zero". Either (a) log a warning when SETTLED arrives with `fee=None`, or (b) treat `fee=None` as an unknown-fee state and skip change generation (wallet gets nothing back, mint holds the reserve — conservative). Option (a) is the lower-friction fix.

## Additional Observations (non-spec)

### Two code paths produce change, both consistent
`_generate_change_promises` is called from two sites:
1. `_execute_melt_payment` (L1283) — the synchronous / async-background melt path, immediately after `pay_invoice` returns SETTLED.
2. `get_melt_quote` (L910) — the late-settlement detection path, when a PENDING quote is later discovered SETTLED via `get_payment_status`.

Both paths compute `fee_reserve_provided = total_provided - melt_quote.amount - input_fees` (L907-909 and L1170), pass it as `fee_provided`, and assign `melt_quote.change = return_promises`. The computation is identical, so wallets receive the same change regardless of whether the melt settled inline or via polling. ✓

### DLEQ on change signatures
`get_melt_quote` (L858-865) regenerates DLEQ proofs for change signatures on every read:
```python
if melt_quote.change:
    change_outputs = await self.crud.get_blinded_messages_melt_id(...)
    for output, promise in zip(change_outputs, melt_quote.change):
        promise.dleq = self._generate_dleq(output, promise)
```
This is a NUT-12 concern (not NUT-08), but it confirms that change signatures are full first-class `BlindSignature`s eligible for DLEQ verification — the mint does not produce a degenerate signature for change.

### Unsigned blank outputs are scrubbed
When change is generated, any leftover unsigned blank outputs are deleted from the DB (`_generate_change_promises`, L302-304; also L273-276 in the no-change branch). This prevents blank-output reuse across melt attempts and keeps the pending-outputs table clean. Good hygiene, not strictly required by NUT-08.

### Wallet-side output count not validated by mint
The spec's recommended output count (`max(ceil(log2(fee_reserve)), 1)`, L15) is a wallet responsibility. The mint does not reject requests with a different count — it gracefully degrades (N08-R9). This is the correct server-side posture.
