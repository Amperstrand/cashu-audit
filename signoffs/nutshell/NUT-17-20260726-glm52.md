**Overall verdict: PASS** — The single explicit MUST in NUT-17 (L94: mint MUST first respond with the current state of the subscribed object, then continue sending updates) is satisfied for all three implemented subscription kinds. All message formats (WsRequest, WsResponse, WsNotification, WsError) conform to the JSON-RPC 2.0 structures defined in the spec. The `/v1/ws` endpoint, subscribe/unsubscribe commands, error codes, and NUT-06 advertisement are all correctly implemented. 2 non-blocking warnings: (1) a theoretical initial-state-vs-update ordering race in `_init_subscriptions`, and (2) BOLT12 subscription kinds are not implemented (acceptable — optional, not advertised).

## Deviations & Findings

### WARN-1: Initial-state vs. concurrent-update ordering race (non-blocking)
**Location**: `client.py:194` (`asyncio.create_task(self._init_subscriptions(...))`)
**Spec ref**: L94 ("MUST first respond with the _current_ state")

`_init_subscriptions` is dispatched as a fire-and-forget `asyncio.create_task` and reads the DB asynchronously. If a state change fires between the DB read and the notification send, a client could theoretically receive: update(new state) → initial-state(stale). This is a narrow time-of-check-to-time-of-use window. In practice the OK response is guaranteed to precede the initial notification (the init task cannot run until `_send_msg` for the OK response yields), and the race requires a state change within the sub-millisecond init window. The spec does not mandate atomicity of the init-vs-update ordering. **Verdict: acceptable, but a `asyncio.Lock` per-subId or pre-registration snapshot would eliminate it.**

### WARN-2: BOLT12 subscription kinds not implemented (informational)
**Location**: `json_rpc/base.py:60-63`
**Spec ref**: L77-78 (`bolt12_melt_quote`, `bolt12_mint_quote`)

Nutshell's `JSONRPCSubscriptionKinds` enum omits the two BOLT12 kinds. This is **spec-compliant**: NUT-17 is `optional`, BOLT12 support is itself optional, and Nutshell does not advertise BOLT12 commands in `nuts[17]` (features.py only iterates `Method["bolt11"]` backends). A wallet subscribing to a `bolt12_*` kind receives `-32600 INVALID_REQUEST` from Pydantic validation, which is the correct rejection behavior for an unsupported kind. **No action required.**

### INFO-1: `subId` format not validated as UUID v7
**Spec ref**: L68 ("subId is a unique UUID v7 generated by the wallet")

Nutshell accepts `subId: str` without format validation. The spec describes subId as wallet-generated UUID v7 but places no validation obligation on the mint. Lenient acceptance is the interoperable choice. **No action required.**

### INFO-2: Error response `id` type is `int`, spec error example shows string
**Spec ref**: L153 (`"id": "1"`)

The spec's WsRequest type declaration (L42) specifies `id: <int>`, but the WsError example (L153) shows `"id": "1"` as a string. This is an internal inconsistency in the spec itself. Nutshell uses `id: int` consistently (json_rpc/base.py:12,20,49), matching the type declaration. The JSON-RPC 2.0 standard also uses null when the id cannot be determined (Nutshell uses `0` as a fallback for pre-parse errors at client.py:88,101,68). **Nutshell follows the normative type declaration; the example is non-normative.**

### INFO-3: Multi-subId per filter supported
**Location**: `client.py:189-191`

The subscription store allows multiple `subId` values per filter (`self.subscriptions[kind].setdefault(f, []).append(subId)`), enabling multiple subscriptions to the same object from the same or different connections. The broadcast in `events.submit()` iterates all matching subs (events.py:55), so each subId gets its own notification. This correctly handles the spec's per-subId notification routing (L140).

### INFO-4: Rate limiting on WebSocket
**Location**: `limit.py:112-125`; `client.py:59-71`

`limit_websocket()` is called per received message (client.py:60), applying IP-based rate limiting via `assert_limit()`. Rate-limit violations return `-32000 SERVER_ERROR`. The endpoint also calls `limit_websocket` at connection time (router.py:471). Local connections (`127.0.0.1`) are exempt (limit.py:123-124). This is a robustness addition beyond the spec.

## Verdict

**PASS** — Nutshell's NUT-17 implementation is spec-compliant. The single explicit MUST (initial-state-then-updates) is satisfied. All four message types conform to their JSON-RPC 2.0 structures. The `/v1/ws` endpoint, subscribe/unsubscribe commands, error handling (with the full JSON-RPC error code set), and NUT-06 capability advertisement are all correctly implemented. The two warnings (init-race ordering, BOLT12 omission) are non-blocking and within the optional-nature of the spec. The implementation includes thoughtful hardening beyond the spec: per-message rate limiting, max-client (1000) and max-subscription (1000) caps, and lenient error recovery (malformed messages return errors without dropping the connection).
