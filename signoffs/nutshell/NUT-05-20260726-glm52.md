## Findings

### Finding 1: Melt quote expiry not checked at execution time
- **Severity**: Low (non-blocking)
- **Location**: `cashu/mint/ledger.py:1085-1157` (`_prepare_melt`)
- **Description**: The spec defines `expiry` as "the Unix timestamp until which the melt quote is valid" (L80). The `mint()` method enforces this invariant explicitly (ledger.py:526-527), but `_prepare_melt` does not. A wallet could theoretically execute a melt after the quote's stated expiry. In practice, for external Lightning payments, the backend rejects expired invoices, providing indirect enforcement. For internal settlements (`melt_mint_settle_internally`), there is no external time constraint, so an expired internal melt quote could still be settled.
- **Impact**: Low. The `melt_quote_ttl` setting, when shorter than the BOLT11 invoice expiry, would not be enforced for internal payments. External payments are protected by the backend. No funds-at-risk scenario identified since proofs are still consumed and invalidated.
- **Recommendation**: Add `if melt_quote.expiry and melt_quote.expiry < int(time.time()): raise TransactionError("quote expired")` in `_prepare_melt`, mirroring the `mint()` check.

### Finding 2: `MeltMethodSetting` missing `options` field
- **Severity**: Informational (non-blocking)
- **Location**: `cashu/core/models/info.py:19-24`
- **Description**: The spec defines `MeltMethodSetting` (L259-268) with an `options: <Object|null>` field. Nutshell's model omits it. No NUT defines method-specific melt options for bolt11, so the field would always be `null` and stripped by `response_model_exclude_none=True`.
- **Impact**: None functionally. The field is absent from the JSON response rather than present as `null`. Wallets that expect the field may need a null-coalescing access pattern, but no known wallet requires it.
- **Recommendation**: Add `options: Optional[Dict] = None` to `MeltMethodSetting` for spec completeness. Low priority.

## Additional Observations (non-spec findings)

### Internal Melt Optimization (not in NUT-05 spec)
Nutshell implements an internal payment optimization (`create_internal_melt_quote`, `melt_mint_settle_internally`) where a melt quote matching an existing mint quote is settled internally without hitting the Lightning backend. This is an implementation-specific optimization not described in NUT-05. It correctly:
- Sets internal fees to 0 (ledger.py:699)
- Validates amount, unit, method, and request matching (ledger.py:984-995)
- Updates both mint and melt quote states atomically (ledger.py:1018-1020)
- Emits events for both quotes (ledger.py:1022-1023)

### Async Error Handling
The background melt task (`melt_task`, ledger.py:1051-1056) catches all exceptions and logs them without propagating. If the background payment fails silently (e.g., process crash), the quote remains PENDING. The `_check_pending_proofs_and_melt_quotes` regular task (L218-231, runs on startup and periodically via `_run_regular_tasks`) provides recovery by re-checking pending melt quote states with the backend. This is a sound resilience pattern.

### Payment State Discrepancy Handling
When `pay_invoice` returns FAILED/UNKNOWN but the subsequent status check returns a different result, Nutshell keeps the transaction PENDING and disables melt globally (`self.disable_melt = True`, ledger.py:1233,1257). This conservative approach prevents double-spending at the cost of locking proofs until manual intervention. This is correct behavior for an unknown payment state — better to be safe than to roll back a potentially-successful payment.
