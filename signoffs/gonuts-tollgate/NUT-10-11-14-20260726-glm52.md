### Findings

#### F-1: Duplicate Tag Keys Not Detected (FAIL)
- **Location**: `nut11/nut11.go:100-168` `ParseP2PKTags`
- **Issue**: The function iterates tags and uses a switch to assign values. If the same tag key appears twice (e.g., two `["pubkeys", ...]` tags), the second overwrites the first. The spec says: "If a tag appears more than once, the P2PK secret is malformed and the Proof **MUST** be rejected as unspendable." (11.md L85)
- **Impact**: An attacker could craft a proof with two `pubkeys` tags — the first with the real recipient's key, the second with the attacker's key. Only the attacker's key would be used for verification.
- **Fix**: Track seen tag keys in a `map[string]bool`; if a key is already present, return error.

#### F-2: Duplicate Keys Per Pathway Not Checked (FAIL)
- **Location**: `nut11/nut11.go:100-168` `ParseP2PKTags`, `nut11/nut11.go:354-408` `VerifyP2PKLockedProof`
- **Issue**: The spec requires each key to appear at most once per multisig pathway (11.md L266, L295). Code does not check for duplicate keys within `pubkeys` tag values or between `data` field and `pubkeys` tag.
- **Impact**: Medium — duplicate keys could allow n_sigs threshold to be met with fewer unique signers than intended.
- **Fix**: After parsing all pubkeys for a pathway, check for duplicates by comparing x-coordinates (lowercased).

#### F-3: n_sigs_refund Not Supported (WARN)
- **Location**: `nut11/nut11.go:19-25` — no `NSIGS_REFUND` constant; `ParseP2PKTags` L112-164 — no case for `"n_sigs_refund"`
- **Issue**: The `n_sigs_refund` tag is silently ignored. Refund pathway always requires exactly 1 signature.
- **Impact**: Low — feature is rarely used, but proofs specifying `n_sigs_refund > 1` would be spendable with just 1 refund signature.

**NUT-11 Verdict: WARN** — Core P2PK (basic case, SIG_INPUTS, SIG_ALL, multisig, locktime) works correctly. Two MUST violations (duplicate tags, duplicate keys) are exploitable but require crafted proofs. The `n_sigs_refund` gap is a feature omission.

### Verification

| # | Requirement | Status | Evidence |
|---|------------|--------|----------|
| M14-1 | HTLC kind, hash in data | **PASS** | `nut14/nut14.go:29-32` — HTLCWitness struct; `nut10/nut10.go:17` — `HTLC` kind; hash lock verified at `nut14.go:156-163` |
| M14-2 | Preimage in witness | **PASS** | `nut14/nut14.go:30` — `Preimage string json:"preimage"` in HTLCWitness |
| M14-3 | HTLCWitness format | **PASS** | `nut14/nut14.go:29-32` — `{Preimage string, Signatures []string}` matching `{preimage, signatures}` |
| M14-4 | Receiver pathway: preimage + sigs | **FAIL** | `nut14/nut14.go:166-181` — signature verification gated on `if p2pkTags.NSigs > 0`. When `pubkeys` is present but `n_sigs` is absent, NSigs defaults to 0, and signatures are NOT verified. Spec says pubkeys present requires at least 1 valid sig (per NUT-11 Locktime Multisig default). |
| M14-5 | Preimage alone when no pubkeys | **PASS** | `nut14/nut14.go:166-181` — if NSigs is 0 (no n_sigs tag), the entire signature block is skipped, so preimage alone suffices. When pubkeys is also absent, this is correct behavior. |
| M14-6 | Sender pathway (refund) | **PASS** | `nut14/nut14.go:136-148` — after locktime expiry with refund keys, verifies refund signatures; if no refund keys, treats as anyone-can-spend (spec-compliant per 14.md L71) |
| M14-7 | SHA256 hash verification | **PASS** | `nut14/nut14.go:152-163` — `hashBytes := sha256.Sum256(preimageBytes); hash := hex.EncodeToString(hashBytes[:]); if hash != proofSecret.Data.Data` |
| M14-8 | 32-byte / 64-char hex | **PASS** | `nut14/nut14.go:159` — `if len(proofSecret.Data.Data) != 64` returns `InvalidHashErr` |
| M14-9 | Must verify hash equality | **PASS** | `nut14/nut14.go:152-163` — always verified before accepting spend |
| M14-10 | Mint info setting | **PASS** | `mint/mint.go:1524` — `Nut14: nut06.Supported{Supported: true}` |

### Findings

#### F-4: HTLC Receiver Pathway Skips Signatures When n_sigs Absent (FAIL)
- **Location**: `nut14/nut14.go:166-181`
- **Issue**: The code gates signature verification on `if p2pkTags.NSigs > 0`. When a proof has `pubkeys` tag but no `n_sigs` tag, `NSigs` defaults to 0, and the entire signature verification is skipped. The spec says when `pubkeys` is present, the receiver must provide BOTH preimage AND signatures per NUT-11 Locktime Multisig rules (which default to requiring 1 signature).
- **Contrast**: The P2PK code (`nut11.go:363,387`) correctly defaults `signaturesRequired := 1` and only overrides if `NSigs > 0`. The HTLC code should follow the same pattern.
- **Impact**: An HTLC proof locked with `pubkeys` can be spent by anyone who knows the preimage, without providing a signature from the listed public key. This defeats the purpose of the `pubkeys` lock.
- **Fix**: Change the condition to check for pubkeys presence:
  ```go
  if len(p2pkTags.Pubkeys) > 0 || p2pkTags.NSigs > 0 {
      signaturesRequired := 1
      if p2pkTags.NSigs > 0 { signaturesRequired = p2pkTags.NSigs }
      // verify signatures...
  }
  ```

#### F-5: HTLC AddWitnessHTLC n_sigs > 1 Rejection (Minor)
- **Location**: `nut14/nut14.go:52-53`
- **Issue**: `AddWitnessHTLC` returns error if `tags.NSigs > 1` ("unable to provide enough signatures"). This is a wallet-side limitation, not a spec violation — the wallet only supports single-signature HTLC witnessing.
- **Impact**: Low — wallet cannot construct witnesses for HTLC proofs requiring multiple signatures.

**NUT-14 Verdict: WARN** — Hash lock, preimage verification, sender/refund pathway, and 32-byte constraints are all correct. The receiver pathway signature gap (F-4) is a real spec violation exploitable when `pubkeys` is present without `n_sigs`.
