### The FAILs

#### FAIL-1: NUT-04 accounting fields completely absent (Critical)

**Quotes**: Q04-2 (`nut04.go:58`) + Q04-4 (`mint.go:255`)
> `// NUT #04: Mints **MUST** include amount_paid, amount_issued, and updated_at in all mint quote responses.`

**Code**:
- `nut04.PostMintQuoteBolt11Response` (nut04.go:59-67): Fields are `Quote, Request, Amount, Unit, State, Expiry, Pubkey` — **none of the three required fields**.
- `storage.MintQuote` (storage.go:67-75): Fields are `Id, Amount, PaymentRequest, PaymentHash, State, Expiry, Pubkey` — **none of the three required fields**.
- `server.go:366-373` (`mintRequest` handler): Builds response without accounting fields.
- `server.go:413-420` (`mintQuoteState` handler): Same omission.

**Confirmed via grep**: `amount_paid`, `amount_issued`, `updated_at` appear **nowhere** in the codebase except inside the two quote comments themselves.

**Verdict**: **FAIL** — The spec-quote correctly documents the MUST, but the implementation completely lacks these fields in every layer (storage model, API response model, handler). This is the most severe finding in this audit. The juxtaposition of the correct quote with the non-compliant code is the single most valuable finding enabled by the greatspectations approach for this implementation.

#### FAIL-2: NUT-05 quote ID not UUID v7

**Quote**: Q05-2 (`nut05.go:57`)
> `// NUT #05: quote is the quote ID string in UUID v7 format with all 74 variable bits generated by a CSPRNG`

**Code** (`cashu.go:606-614`):
```go
func GenerateRandomQuoteId() (string, error) {
    randomBytes := make([]byte, 32)
    _, err := rand.Read(randomBytes)
    if err != nil { return "", err }
    hash := sha256.Sum256(randomBytes)
    return hex.EncodeToString(hash[:]), nil
}
```

**Verdict**: **FAIL** — The function generates a 64-character hex string (SHA256 of 32 random bytes), not a UUID v7. While the entropy source is a CSPRNG (`crypto/rand`), UUID v7 requires a specific format with embedded timestamp (for sortability) and the standard `xxxxxxxx-xxxx-7xxx-yxxx-xxxxxxxxxxxx` structure. The practical security property (unpredictability) is satisfied, but the format is non-compliant.

### The WARNs

#### WARN-1: NUT-04 partial minting not supported

**Quotes**: Q04-3 (`nut04.go:75`) + Q04-5 (`mint.go:367`)
> `// NUT #04: Mints **MUST NOT** issue ecash whose total output amount exceeds amount_paid - amount_issued.`

**Code** (`mint.go:403`):
```go
if blindedMessagesAmount > mintQuote.Amount {
    return cashu.OutputsOverQuoteAmountErr
}
```

The code checks against `mintQuote.Amount` (the full quote amount), not `amount_paid - amount_issued`. Since the `Issued` state (L378-379) returns `MintQuoteAlreadyIssued`, the model is all-or-nothing: a quote can only be minted once in full. The spec supports partial minting where `amount_issued` increments by the minted amount. This is a functional deviation from the spec's accounting model.

#### WARN-2: NUT-04/05 method regex not explicitly validated

**Quotes**: Q04-1 (`nut04.go:51`), Q04-4 (duplicate), Q05-1 (`nut05.go:46`), Q05-4 (duplicate)
> `method MUST match [a-z0-9_-]+`

**Code**: No regex validation. Method is validated via hardcoded comparison in server handlers:
```go
if method != cashu.BOLT11_METHOD {
    ms.writeErr(rw, req, cashu.PaymentMethodNotSupportedErr)
    return
}
```

The implicit validation is **stricter** than the spec regex (only `bolt11` is accepted vs. any `[a-z0-9_-]+` string). This is safe but not spec-compliant for custom payment methods. The spec explicitly supports custom methods like `paypal`, `stripe`, etc.

## 5. Findings (Consolidated)

### Finding F-1: NUT-04 accounting fields completely absent (Critical)
- **Severity**: Critical
- **Location**: `nut04.go:58` (quote), `nut04.go:59-67` (response struct), `storage.go:67-75` (storage model), `server.go:366-373` (handler)
- **Quote**: "Mints **MUST** include `amount_paid`, `amount_issued`, and `updated_at` in all mint quote responses."
- **Code**: Neither `PostMintQuoteBolt11Response` nor `storage.MintQuote` has any of these three fields. The API response omits them entirely.
- **Impact**: Wallets consuming this mint's API cannot track partial minting, verify accounting invariants, or detect stale responses. The spec's anti-front-running guidance (monotonic `updated_at`) is unenforceable. This is a spec-level MUST violation.
- **Recommendation**: Add `AmountPaid`, `AmountIssued` (uint64), and `UpdatedAt` (int64) fields to both `storage.MintQuote` and `nut04.PostMintQuoteBolt11Response`. Track `amount_issued` incrementally in `MintTokens()`. Update `updated_at` on every state change.

### Finding F-2: NUT-05 quote ID not UUID v7
- **Severity**: Medium
- **Location**: `nut05.go:57` (quote), `cashu.go:606-614` (`GenerateRandomQuoteId`)
- **Quote**: "`quote` is the quote ID string in UUID v7 format with all 74 variable bits generated by a CSPRNG"
- **Code**: `GenerateRandomQuoteId()` produces `hex(sha256(rand_bytes(32)))` — a 64-character hex string, not UUID v7.
- **Impact**: Quote IDs lack timestamp embed (no natural sortability). Format mismatch may cause wallet compatibility issues if wallets validate UUID v7 structure. The CSPRNG security property is met.
- **Recommendation**: Replace with a UUID v7 implementation (e.g., `github.com/google/uuid` v7 support or manual construction with timestamp + random).

### Finding F-3: NUT-02 `final_expiry` absent from data model and V2 preimage
- **Severity**: Medium
- **Location**: `keyset.go:196-228` (`DeriveKeysetIdV2`), `nut02.go:10-17` (`Keyset` struct)
- **Spec**: NUT-02 step 5 (02.md:70): "If a final expiration is specified, add `|final_expiry:` to the preimage." Also 02.md:116-122 defines `final_expiry` as a keyset property.
- **Code**: `DeriveKeysetIdV2` has no `final_expiry` parameter. The `Keyset` struct has no `final_expiry` field. The V2 preimage omits this component entirely.
- **Impact**: Keyset IDs computed by this mint will differ from other implementations if `final_expiry` is ever needed. Keyset expiry functionality is unavailable.
- **Recommendation**: Add `FinalExpiry` field to the keyset model and include it in the V2 preimage when non-zero.

### Finding F-4: NUT-04 partial minting not supported
- **Severity**: Medium
- **Location**: `mint.go:403`, `mint.go:378-379`
- **Spec**: NUT-04 (04.md:83): "If a wallet mints less than the currently mintable amount, `amount_issued` only increases by the amount that was issued."
- **Code**: `MintTokens` checks `blindedMessagesAmount > mintQuote.Amount` (must match full amount). The `Issued` state returns `MintQuoteAlreadyIssued` — a quote can only be minted once in full.
- **Impact**: Wallets cannot mint partial amounts from a single quote. Tied to F-1 (no `amount_issued` tracking).
- **Recommendation**: Depends on F-1 fix. Once accounting fields exist, change the check to `blindedMessagesAmount > (amount_paid - amount_issued)`.

### Finding F-5: NUT-05 `method` field missing from melt quote response
- **Severity**: Low
- **Location**: `nut05.go:58-68` (`PostMeltQuoteBolt11Response`), `server.go:578-586`
- **Spec**: NUT-05 (05.md:66): response includes `"method": <str>`.
- **Code**: Response struct has no `Method` field. Since only `bolt11` is supported, the method is implicit, but the field is absent from the JSON response.
- **Impact**: Minor — wallets know the method from the request URL. But spec compliance requires the field.
- **Recommendation**: Add `Method string json:"method"` to the response struct and set it in handlers.

### Finding F-6: NUT-05 `prefer_async` and async melt processing absent
- **Severity**: Low (optional feature)
- **Location**: `nut05.go:72-76` (`PostMeltBolt11Request`)
- **Spec**: NUT-05 (05.md:112): request includes optional `prefer_async: <bool>`. Async flow described at 05.md:124-137.
- **Code**: Request struct has no `PreferAsync` field. All melts are synchronous.
- **Impact**: No async melt support. Acceptable for a mint that only supports `bolt11` with short timeouts, but limits wallet compatibility.
- **Recommendation**: Add `PreferAsync bool` to request struct if async support is desired.

### Finding F-7: NUT-06 `tos_url` field missing
- **Severity**: Low
- **Location**: `nut06.go:12-29` (`MintInfo` struct)
- **Spec**: NUT-06 (06.md:100): `(optional) tos_url is the URL pointing to the Terms of Service of the mint.`
- **Code**: `MintInfo` struct has no `TosURL` field. All other spec fields are present.
- **Impact**: Minor — field is optional. Wallets won't see a ToS link.
- **Recommendation**: Add `TosURL string json:"tos_url,omitempty"`.

### Finding F-8: NUT-00 mint URL trailing slash not stripped
- **Severity**: Low
- **Location**: `cashu.go:210` (`NewTokenV3`), `cashu.go:398` (`NewTokenV4`)
- **Spec**: NUT-00 (00.md:195, 281): "The mint URL **MUST** be normalized by stripping any trailing slashes (`/`)."
- **Code**: Both `NewTokenV3` and `NewTokenV4` store the `mint` parameter verbatim without `strings.TrimRight(mint, "/")`.
- **Impact**: Tokens generated with a trailing-slash mint URL will be non-compliant. Same finding as nutshell and cashu-cf audits.
- **Note**: No greatspectations quote exists for this requirement in gonuts-tollgate, so it's a coverage gap, not a quote-accuracy issue.

## 8. Methodology Notes

### Audit approach
1. Enumerated all 38 `// NUT #0[0-6]:` spec-quote comments via grep across the codebase.
2. Read all source files containing quotes: `crypto/bdhke.go`, `crypto/keyset.go`, `cashu/nuts/nut0{1-6}/nut0{1-6}.go`, `mint/mint.go`, `mint/server.go`, `mint/storage/storage.go`, `wallet/wallet.go`, `cashu/cashu.go`.
3. Read all 7 NUT specs (00.md through 06.md).
4. For each quote: verified quote text against spec (verbatim check), then verified code behavior against the quoted claim.
5. Identified spec requirements NOT covered by any quote (coverage gaps).
6. Cross-referenced findings against existing signoffs for nutshell, cdk, and cashu-cf.

### Scope
- **Mint-side focus**: Per task instructions, audit focused on mint-side implementation (`mint/`, `crypto/`, `cashu/nuts/`). Wallet-side quotes (`wallet/wallet.go`) were verified for text accuracy and basic code behavior but not deeply audited for wallet-spec compliance.
- **Files read in full**: `crypto/bdhke.go` (229 lines), `crypto/keyset.go` (398 lines), all `cashu/nuts/nut0{1-6}/*.go`, `mint/storage/storage.go` (89 lines), `cashu/cashu.go` (631 lines, relevant sections).
- **Files read partially**: `mint/mint.go` (1618 lines — read quote-adjacent sections: L230-430, 460-540, 540-660, 750-870), `mint/server.go` (828 lines — read all handlers: L335-495, 550-646, 774-828), `wallet/wallet.go` (2297 lines — read quote-adjacent sections only).

### Limitations
- SQLite storage layer (`mint/storage/sqlite/`) was not audited for field-level compliance — only the `storage.MintQuote`/`MeltQuote` structs in the interface file were examined.
- Integration tests (`mint_integration_test.go`, `wallet_integration_test.go`) were not run — findings are based on static code analysis.
- The `mint/lightning/` backend was not examined for NUT-23 (BOLT11) compliance.
