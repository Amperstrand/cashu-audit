## 2. NUT-12: DLEQ Proof of Blind Signature Equality

### Spec MUSTs Extracted

| # | MUST Requirement | Source |
|---|-----------------|--------|
| M12-1 | Mint **SHOULD** include DLEQ proof `{e, s}` in each `BlindedSignature` | 12.md L44-47 |
| M12-2 | If DLEQ proof included, wallets **MUST** verify it | 12.md L49-50 |
| M12-3 | Verification: reconstruct `B'` and `C'` using `r`, verify `e = Hash(R1, R2, A, C')` | 12.md L80-106 |
| M12-4 | `e = Hash(R1, R2, A, C')` where `R1 = s*G - e*A`, `R2 = s*B' - e*C'` | 12.md L90-96 |
| M12-5 | Mint **SHOULD** use deterministic nonce via `HMAC-SHA256(keyset_id, "dleq")` | 12.md L51-56 |
| M12-6 | DLEQ proof in `Proof` for P2PK transfer includes `r` blinding factor | 12.md L116-124 |
| M12-7 | Wallets **MUST** verify DLEQ proofs in received tokens if present | 12.md L116 |

### Verification

| # | Requirement | Status | Evidence |
|---|------------|--------|----------|
| M12-1 | DLEQ in BlindedSignature | **PASS** | `mint/mint.go:1333-1343` — `e, s := crypto.GenerateDLEQ(k, B_, C_)`; attached at L1340-1343: `DLEQ: &cashu.DLEQProof{E: hex..., S: hex...}` |
| M12-2 | Wallet verifies DLEQ | **PASS** | `nut12/nut12.go:16-32` — `VerifyProofsDLEQ` iterates proofs, skips if `proof.DLEQ == nil` (L18), verifies via `VerifyProofDLEQ` (L26); also `VerifyBlindSignatureDLEQ` at L159-189 |
| M12-3 | Reconstruct B', C' using r | **PASS** | `nut12/nut12.go:128` — `B_, _, err := crypto.BlindMessage(proof.Secret, r)` reconstructs B_; L148-153 — `C' = C + r*A` reconstructs C_; then `crypto.VerifyDLEQ(e, s, A, B_, C_)` at L155 |
| M12-4 | Verification math correct | **PASS** | `crypto/bdhke.go:181-229` — `VerifyDLEQ`: computes `R1 = s*G - e*A` (L191-204), `R2 = s*B' - e*C'` (L207-220), then `HashE([R1, R2, A, C_])` compared to `e.Serialize()` (L225-228) |
| M12-5 | Deterministic nonce | **WARN** | `crypto/bdhke.go:149-154` — uses `secp256k1.GeneratePrivateKey()` (random). Spec says **SHOULD** use `HMAC-SHA256(keyset_id_hex, "dleq")` for deterministic nonce. Not a MUST, but means DLEQ proofs are non-reproducible. |
| M12-6 | DLEQ with r in Proof transfer | **PASS** | `nut12/nut12.go:192-221` — `ParseDLEQ` handles optional `R` field (L210-218); `VerifyProofDLEQ` uses r to reconstruct B_ and C_ at L128, L148-153 |
| M12-7 | Wallet verifies in received tokens | **PASS** | `nut12/nut12.go:16` — comment: "If a DLEQ proof is included in a received token, wallets **MUST** verify the proof"; `VerifyProofsDLEQ` called in wallet receive path |

### Code Notes

`GenerateDLEQ` (`bdhke.go:144-179`) implements the Chaum-Pedersen protocol:
- Random nonce `r` → `R1 = r*G`, `R2 = r*B'`
- Challenge `e = HashE([R1, R2, A, C'])` where `HashE` SHA256s concatenated uncompressed pubkeys (L136-142)
- Response `s = r + e*a`

`HashE` (`bdhke.go:136-142`) concatenates `hex.SerializeUncompressed()` of each point, then SHA256. This matches the spec's hash construction.

`VerifyProofsDLEQWithKeysets` (`nut12.go:43-116`) adds production-grade keyset rotation handling — fetches historical keysets concurrently for proofs from rotated keysets. Well-engineered.

### Findings

#### F-1: Random Nonce Instead of Deterministic (WARN)
- **Location**: `crypto/bdhke.go:149-154`
- **Issue**: Spec says mint **SHOULD** use `HMAC-SHA256(keyset_id, "dleq")` for deterministic nonce generation. Code uses random nonce.
- **Impact**: Low — DLEQ proofs are still cryptographically valid. Deterministic nonce would enable auditability and reproducibility but is not a MUST.
- **Note**: This is a SHOULD, not MUST. No spec violation.

**NUT-12 Verdict: PASS**

## 3. NUT-13: Wallet Deterministic State

### Spec MUSTs Extracted

| # | MUST Requirement | Source |
|---|-----------------|--------|
| M13-1 | BIP32 derivation path: `m/129372'/0'/keyset_id_int'/counter'/{0|1}` | 13.md L45, L74-76 |
| M13-2 | `keyset_id_int` = `int(keyset_id) mod (2^31 - 1)` | 13.md L35-41 |
| M13-3 | Counter `0` → secret, Counter `1` → blinding factor `r` | 13.md L76-81 |
| M13-4 | Coin type always `0'` regardless of unit | 13.md L43 |
| M13-5 | Wallet **MUST** track separate counter per keyset | 13.md L16 |
| M13-6 | V2 keysets: derive `seed` via `HMAC-SHA256(keyset_id_hex, "keyset_id derivation")`, use first 8 bytes of keyset ID for path | 13.md L104-116 |

### Verification

| # | Requirement | Status | Evidence |
|---|------------|--------|----------|
| M13-1 | BIP32 path structure | **PASS** | `nut13/nut13.go:44-69` — `DeriveKeysetPath`: purpose `m/129372'` (L51), coin type `m/129372'/0'` (L57), keyset `m/129372'/0'/keyset_k_int'` (L63); `DeriveBlindingFactor` L72-91: counter `/0` and `/1`; `DeriveSecret` L94-116: counter `/0` |
| M13-2 | keyset_id_int modulo | **PASS** | `nut13/nut13.go:20-41` — `keysetIdToBigInt`: handles hex and base64 input, `result.Mod(result, modulus)` where `modulus = 2^31 - 1 = 2147483647` (L24) |
| M13-3 | Counter 0 = secret, 1 = r | **PASS** | `nut13/nut13.go:102` — `secretDerivationPath, _ := counterPath.Derive(0)` for secret; `nut13/nut13.go:80` — `rDerivationPath, _ := counterPath.Derive(1)` for blinding factor |
| M13-4 | Coin type always 0' | **PASS** | `nut13/nut13.go:43` — comment: "Note that the coin type is always `0'`, independent of the unit of the ecash"; L57-59: `purpose.Derive(hdkeychain.HardenedKeyStart + 0)` |
| M13-5 | Separate counter per keyset | **PASS** | `nut13/nut13.go:118` — comment: "The wallet **MUST** keep track of a separate counter for each keyset"; `CheckCollidingKeysets` L119-143 detects keyset ID collisions after modulo; wallet tracks per-keyset counters |
| M13-6 | V2 HMAC-SHA256 derivation | **WARN** | Not implemented. Code only supports legacy BIP32 derivation from seed. No V2 keyset path derivation code exists. V2 keyset IDs are not generated by this mint (uses V1 keyset IDs throughout). |

### Code Notes

`CheckCollidingKeysets` (`nut13.go:119-143`) is a thoughtful addition — it detects when two different keyset IDs collide after the modulo reduction, preventing ambiguous derivation paths.

The wallet correctly uses `DeriveSecret` and `DeriveBlindingFactor` in `wallet/wallet.go` for deterministic ecash generation, and `wallet/restore.go` uses the same derivation paths for wallet restore from seed.

### Findings

#### F-2: V2 Keyset Derivation Not Implemented (WARN)
- **Location**: Absent from `nut13/nut13.go`
- **Issue**: Spec describes V2 keyset derivation using `HMAC-SHA256` and truncated 8-byte keyset IDs (13.md L104-116). Code only implements legacy BIP32 derivation from master seed.
- **Impact**: Low — V2 keyset IDs are not generated by this mint (ISSUE-016 tracks V2 migration). When V2 keyset IDs are introduced, the derivation code will need updating.
- **Note**: This is forward-looking, not a current bug. The legacy path is correctly implemented per spec.

**NUT-13 Verdict: WARN** — Legacy BIP32 derivation is spec-perfect. V2 derivation absent but not needed until V2 keyset IDs are generated.

### Code Notes

The WebSocket implementation is production-quality:
- **Connection limits**: 100 subscriptions per connection (`websocket.go:199`), 50 quote filters per subscription (L234)

- **State diffing**: `MintQuotesSubClient.Read()` only sends notifications when quote state actually changes (`websocket.go:467` — `if previousState != mintQuote.State`)
- **Clean shutdown**: `WebsocketManager.Shutdown()` removes all clients (L78-85); `Client.close()` cancels all subscriptions (L378-385)
- **ProofStatesSubClient** is fully implemented (L512-607) but not wired up pending spec clarification on proof state subscriptions

The `ProofState` comment at L282 references `https://github.com/cashubtc/nuts/pull/213` — a legitimate spec ambiguity that was unresolved at implementation time.

### Findings

#### F-3: ProofState and Bolt11MeltQuote Commented Out (INFO)
- **Location**: `websocket.go:281-325`
- **Issue**: Two of three subscription kinds are commented out. `ProofState` pending spec clarification (PR #213). `Bolt11MeltQuote` not yet implemented.
- **Impact**: None — neither is advertised in mint info. Clients requesting these kinds get error code 1000 "invalid request method" (L327). This is correct behavior for unsupported features.
- **Note**: This is not a spec violation. The spec says mints MAY support a subset of kinds. The implementation honestly advertises only what it supports.

**NUT-17 Verdict: PASS** — Only `bolt11_mint_quote` is implemented, but it is fully correct and honestly advertised. The other two kinds are not advertised, which is spec-compliant.
