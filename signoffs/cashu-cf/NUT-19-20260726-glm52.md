## Implementation Quality Observations (non-spec)

| Observation | Detail |
|---|---|
| **Thundering-herd protection** | `nut19InFlight` Map (`mint-do.ts:142,578-603`) deduplicates concurrent identical requests — the second caller awaits the first's in-flight promise and receives the same response without re-executing the handler. Beyond spec requirements, prevents double-spend race conditions. |
| **Canonical JSON keying** | `canonicalJson()` (`mint-do.ts:354-365`) recursively sorts object keys before hashing. Ensures `{"b":1,"a":2}` and `{"a":2,"b":1}` produce the same cache key. Tested explicitly in `nut19-cache.test.ts:98-103` and `nut19-extended-cache.unit.test.ts:801-858`. |
| **Body cloning** | `nut19CacheKey` clones the request (`req.clone()`) before reading the body (`mint-do.ts:405`), ensuring the handler still receives the original stream. |
| **Error resilience** | Cache store failures are caught and logged, not propagated to the client (`mint-do.ts:590-594`). A failed `nut19Store` does not corrupt the response. |
| **Test coverage** | Integration test (`nut19-cache.test.ts`) validates end-to-end mint/swap replay with canonical JSON. Extended unit test suite covers concurrency, performance, chaos, and edge cases. |

## Findings

### Finding 1: SQL table `nut19_cache` exists but runtime uses KV storage (WARN)
- **Severity**: Low (architectural inconsistency, not a spec violation)
- **Location**: `src/database/schema.ts:121-130` (SQL DDL), `src/do/mint-do.ts:472-487` (runtime uses `state.storage.get/put`), `src/repositories/` (no NUT-19 SQL repository)
- **Description**: The `nut19_cache` SQL table is defined in both SCHEMA_V1 and SCHEMA_V2 with a proper index on `expires_at`. Migration code (`migrate-kv-to-sql.ts:378-398`) and verification code (`verify-migration.ts:561-593`) exist to move KV entries into SQL. However, the runtime cache operations (`nut19ServeCached`, `nut19Store`, `nut19CleanupExpired`) all use the DO KV API (`state.storage.get/put/list/delete`) exclusively — there is no SQL repository for NUT-19 in `src/repositories/sqlite/`. This means the SQL table receives entries only via the one-time migration script, not during normal operation.
- **Impact**: None for correctness — the DO KV API is persistent, transactional, and meets all spec requirements for fast insertion/lookup/deletion. The SQL table is unused overhead in the schema. If the M2 migration goal is to move all storage to SQL, NUT-19 cache is a remaining gap (consistent with the "ongoing" status noted in README).
- **Recommendation**: Either create a SQL repository for NUT-19 cache and route runtime operations through it (completing M2 migration for this table), or remove the SQL DDL if KV storage is the permanent choice for the response cache.
