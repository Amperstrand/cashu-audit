## Detailed Findings

### F1 — CRITICAL: Default keyset ID version is V1 (deprecated)

**Severity**: Critical (interoperability)

**Spec** (L61): "Keyset IDs are 33 byte hex strings with a version byte (two hexadecimal characters). The currently used version byte is `01`."

**Spec** (L91): "V1 keysets are 8 bytes long, including a version byte prefix `00`." — labeled deprecated.

**Code**:
- `src/env.ts:496`: `getKeysetIdVersion()` defaults to `'1'` when `KEYSET_ID_VERSION` env is unset.
- `src/core/keyset.ts:140`: `generateKeyset()` defaults `keysetIdVersion` to `'1'`.
- `src/mint/keysets.ts:295`: reads env via `getEnvKeysetIdVersion()` → defaults to `'1'`.

**Impact**: All deployed environments (testnut, rugs, signut, etc.) produce V1 keyset IDs (16 hex chars: `00` + 14 chars). Wallets that compute V2 IDs (66 hex chars: `01` + 64 chars) per the current spec will see ID mismatches. CDK and Nutshell both emit V2 IDs.

**Mitigating factors**: V2 derivation code exists and is correct (`keyset.ts:396-415`). A feature flag (`KEYSET_ID_VERSION=dual` or `KEYSET_ID_VERSION=2`) enables V2. The migration is tracked as ISSUE-016 (`docs/issues/ISSUE-016-nut02-keyset-id-v2-migration.md`) with status `todo`.

**Recommendation**: Deploy with `KEYSET_ID_VERSION=dual` on test environments, verify wallet compatibility, then roll out V2 to production.

### F2 — MINOR: `/v1/keys/{keyset_id}` hardcodes `active: true`

**Severity**: Low (cosmetic / metadata accuracy)

**Spec** (L23): The `active` property determines whether new ecash can be generated from this keyset.

**Code**: `src/mint/router.ts:417`:
```typescript
const response: KeysResponse = {
  keysets: [{
    id: keyset.keysetId,
    unit,
    keys: keyset.pubKeys,
    active: true,          // ← hardcoded regardless of actual status
    input_fee_ppk: meta?.input_fee_ppk ?? null,
    final_expiry: meta?.final_expiry ?? null
  }]
};
```

**Impact**: When a wallet requests keys for an inactive keyset (to verify old proofs), the response incorrectly reports `active: true`. This could mislead wallets into thinking they can mint new ecash from an inactive keyset.

**Recommendation**: Use `meta?.active ?? false` instead of hardcoded `true`.

### F3 — INFO: `final_expiry` not stored in keyset metadata

**Severity**: Informational

**Spec** (L116-122): "A unix epoch number for a future point in time... The final expiry is optional and **MAY** be omitted or `null`."

**Code**: The `KeysetMeta` type (`keysets.ts:17-30`) does not include a `final_expiry` field. The `KeysetPair` type (`keyset.ts:81-101`) also lacks it. The V2 derivation function (`keyset.ts:396-415`) accepts `finalExpiry` as a parameter, but `deriveKeysetFromParams` (`keysets.ts:297-304`) never passes it:

```typescript
const full = await generateKeyset({
  masterPrivateKey: master,
  version, unit, amounts,
  keysetIdVersion: idVersion,
  inputFeePpk,
  // finalExpiry not passed
});
```

**Impact**: `final_expiry` is always `null` in API responses (`router.ts:350,419`). This is spec-compliant (MAY be omitted) but prevents operators from setting keyset expiries.

**Recommendation**: Add `final_expiry` to `KeysetMeta` and `KeysetConfig` if keyset expiry support is desired. Low priority since it's optional per spec.

### F4 — INFO: Fee equation allows overpayment (spec deviation, intentional)

**Severity**: Informational

**Spec** (L40): `sum(inputs) - fees == sum(outputs)` (strict equality)

**Code**: `src/mint/features.ts:668-670`:
```typescript
const availableForFees = inputAmount - outputAmount;
if (availableForFees < requiredFee) { /* reject */ }
```

This enforces `inputAmount - outputAmount >= requiredFee`, i.e. `sum(inputs) - fees >= sum(outputs)`, which permits overpayment (wallet supplies more inputs than strictly necessary).

**Rationale**: Code comment at `features.ts:652` states "Nutshell semantics: inputs - fees must be >= outputs (allow overpayment for compatibility)." This matches the Nutshell reference implementation's behavior.

**Impact**: Spec-compliant wallets that compute exact fees will always pass. Wallets that overpay (e.g. rounding up) are also accepted. No security risk — the mint never loses funds.

### F5 — INFO: Legacy `src/api/keys.ts` handlers diverge from production router

**Severity**: Informational (developer confusion)

**Code**: `src/api/keys.ts` contains `handleGetKeys`, `handleGetKeyset`, `handleGetKeysets` that are NOT used in production routing. The Durable Object (`src/do/mint-do.ts:732-751`) delegates all key/keyset routes to `src/mint/router.ts` instead.

Differences:
- `keys.ts:80-86` (`handleGetKeys`): returns only the single `keysetPair` (misses multi-unit active keysets). Production `router.ts:323-366` returns ALL active keysets correctly.
- `keys.ts:119-121` (`handleGetKeyset`): returns 404 for any keyset ID not matching current `keysetPair`. Production `router.ts:396-445` resolves any keyset.
- `keys.ts:158-174` (`handleGetKeysets`): omits `final_expiry` from response. Production `router.ts:377` returns the full index object.

**Impact**: No production impact (dead code). Risk of developer confusion if reading `keys.ts` instead of `router.ts`.

**Recommendation**: Remove or clearly mark `keys.ts` as deprecated/unused.

## Fee Calculation Verification

`src/core/nut02.ts:10-25` against spec L46-51:

```
Spec:   fees = (sum_fees + 999) // 1000
Code:   Math.floor((sumPpk + 999) / 1000)
```

For non-negative integers, `Math.floor((n + 999) / 1000)` is identical to `(n + 999) // 1000` (Python floor division). **Correct.**

Test case from spec (L33): 3 inputs, `input_fee_ppk=100`:
- `sumPpk = 300`
- `Math.floor((300 + 999) / 1000) = Math.floor(1.299) = 1` ✓ (matches spec: `ceil(0.3) == 1`)

Multi-keyset fee handling (spec L55): "transactions can spend inputs from different keysets" — the code iterates per-input calling `getInputFeePpk(keysetId)` (nut02.ts:17), correctly summing fees across different keyset IDs. **Correct.**
