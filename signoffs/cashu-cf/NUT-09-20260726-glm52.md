## Per-MUST Verdicts

### NUT09-M1 — Store BlindedMessage + BlindSignature on every issuance
**Verdict: PASS**

`BlindedMessageTracker` provides two storage entry points, both writing to DO storage under `blindedMessage:{B_}` and a stable secondary key `nut09:{sha256(id\namount\nB_)}`:

- `storeSignedOutputs(outputs, signatures)` — direct batch store (`blinded-message-tracker.ts:267`)
- `signWithTracking(outputs, signFn)` — wraps check → sign → store; internally calls `storeSignedOutputs` at L437

Call-site survey (every blind-signature issuance path):

| Path | File:Line | Mechanism |
|---|---|---|
| Swap (NUT-03) | `src/mint/features.ts:816` | `storeSignedOutputs(sortedOutputs, signatures)` |
| Mint (NUT-04) | `src/api/mint.ts:1289` | `tracker.storeSignedOutputs(outputs, signatures)` |
| Mint (DO router) | `src/mint/router.ts:176` | `tracker.signWithTracking(messages, signFn)` |
| Mint (mint-do) | `src/do/mint-do.ts:1142` | `blindedMessageTracker.signWithTracking(messages, signFn)` |
| Melt change (DO) | `src/do/melt-quote-do.ts:215, 458` | `tracker.signWithTracking(outputsToSign, mockSignFn)` |

All paths terminate in `storeSignedOutputs`. The store is atomic-batch (`storagePutBatch`, L140) and write-through to the in-memory cache. Count-mismatch throws before any write (L271-273).

Storage keys written per output (L282-292):
1. `blindedMessage:{B_}` — primary dedup + legacy restore lookup
2. `nut09:{sha256(id|amount|B_)}` — stable restore index, decoupled from raw B_

Both store the full `SignedOutput { signature: SerializedBlindSignature, signedAt }`. See WARN-2 regarding the melt change path.

### NUT09-M2 — Only respond if previously signed
**Verdict: PASS**

Both handler implementations gate on a storage lookup that returns `null` when no prior signature exists:

- Live path (`router.ts:1590`): `await this.context.ledger.getStoredSignature(output)` → `ledger.ts:463` → `BlindedMessageTracker.getStoredSignature`
- `getStoredSignature` (`blinded-message-tracker.ts:326-364`): tries stable `nut09:` key first (L332-343), falls back to legacy `blindedMessage:{B_}` key (L346-356), returns `null` if neither matches.
- Handlers only `push` to result arrays inside the `if (storedSignature)` / `if (storedSignature)` branch (`router.ts:1592-1594`, `api/restore.ts:87-89`). Unknown outputs are silently skipped — no partial signature fabricated.

No signature is ever returned for a BlindedMessage the mint did not sign.

### NUT09-M3 — Returned BlindSignature contains `amount` and `id`
**Verdict: PASS**

Stored and returned objects are `SerializedBlindSignature` (from `@cashu/cashu-ts`), whose shape is `{ amount, id, C_, [dleq]?, [dleq_valid?]?, [witness?]? }`. The store path (`storeSignedOutputs`) persists the full signature object verbatim (`signature: signatures[i]`, L285), and the restore path returns it verbatim. `amount` and `id` are therefore always present in any restored signature.

Input validation in the handler also asserts `output.amount` and `output.id` are truthy before lookup (`router.ts:1585`, `api/restore.ts:79`), ensuring the request-side tuple is well-formed.

### NUT09-M4 — Request format `POST /v1/restore` with `{ outputs: [...] }`
**Verdict: PASS**

- Route registered: `src/do/mint-do.ts:776` → `router.post('/v1/restore', ...)` → `this.mintRouter.handleRestore(ctx.req)`.
- Handler parses JSON body and validates `outputs` is a non-empty array (`router.ts:1564-1572`), enforces `getMaxRestoreOutputs` upper bound (L1574-1577), returns 400 on violation. Lower bound (≥1) and upper bound both enforced. Alternate `validateArray` path in `api/restore.ts:63` applies identical bounds.
- Method is POST (route registration uses `router.post`).

### NUT09-M5 — Response format `{ outputs, signatures }`
**Verdict: PASS**

Live handler (`router.ts:1606-1609`) returns exactly `{ outputs: restoredOutputs, signatures: restoredSignatures }` via `createResponse`. Matches spec body (L31-36) field-for-field. See WARN-4 for the non-live alternate handler's extra `promises` field.

### NUT09-M6 — Same-length, index-correlated arrays
**Verdict: PASS**

Both handlers construct the two arrays in lockstep — a single `push(output)` and `push(signature)` pair executes atomically inside the found-signature branch:

```ts
// router.ts:1592-1594 (identical pattern in api/restore.ts:88-89)
if (storedSignature) {
  restoredOutputs.push(output);
  restoredSignatures.push(storedSignature);
}
```

No path pushes one without the other. Length equality and `outputs[i] ↔ signatures[i]` correspondence are structurally guaranteed. The invariant cannot be violated without editing this block.

### NUT09-M7 — NUT-06 advertises `"9": { "supported": true }`
**Verdict: PASS**

`src/mint/info.ts:146`:
```ts
'9': { supported: envFlagDefaultTrue(env.NUT9_SUPPORTED ?? true) },
```
- Shape matches spec example (09.md L46-49) exactly: `{ "9": { "supported": true } }`.
- Defaults to `true` (advertised) unless `NUT9_SUPPORTED=false`. Correct for an implemented optional NUT.
- Nested under the top-level `nuts` map returned by `GET /v1/info` (verified in NUT-06 audit, `info.ts:141-158`).

## Warnings (non-blocking)

### WARN-1 — Duplicate `handleRestore` implementation (dead code)
Two implementations exist:
- **Live**: `src/mint/router.ts:1558` (`MintRouter.handleRestore`) — wired via `mint-do.ts:776`.
- **Dead**: `src/api/restore.ts:54` (`handleRestore`) — not referenced by any route registration; references `ctx.observability` (L90,94,100,114) which is absent from its declared `RestoreContext` interface (L33-39), confirming it cannot compile as-typed against any live caller. The `RestoreAPI` export (L127) has no importer.

**Risk**: Low. Dead code cannot affect runtime behavior. But it is a maintenance hazard — a future edit to the wrong file would silently no-op. **Recommendation**: delete `src/api/restore.ts` or consolidate to a single shared handler imported by the router.

### WARN-2 — Melt change outputs store fake signatures (`mockSignFn`)
`src/do/melt-quote-do.ts:214` and `:457`:
```ts
const mockSignFn = async (msgs: any[]) =>
  msgs.map(m => ({ amount: m.amount, id: m.id, C_: `sig_${m.B_}` }));
changeSignatures = await tracker.signWithTracking(outputsToSign, mockSignFn);
```
The comment at L456 ("in production this will use real private keys") confirms this is a placeholder. These fake `C_` values are persisted into the NUT-09 restore index by `storeSignedOutputs`. A wallet that later restores one of these outputs via `POST /v1/restore` would receive a structurally-valid-but-cryptographically-invalid signature (`C_: "sig_…"`).

**Scope check**: This is the melt-quote DO's 2PC commit path. The primary melt flow goes through `src/api/melt.ts` / `src/mint/router.ts`, which use real signing. If the DO path is active in any deployed environment, restored change signatures from melts would be worthless to the wallet — defeating the NUT-09 recovery guarantee for that subset of outputs.

**Impact on NUT-09 MUSTs**: M1 (store) is satisfied structurally; M2/M3 are satisfied (signature exists, has amount+id). But the *purpose* of NUT-09 (recover a usable `Proof`) is violated for melt change outputs on this path. This is a functional bug, not a spec-shape bug.

**Recommendation**: Replace `mockSignFn` with real blind-signing using the mint's derived private keys (same `signFn` used by `router.ts:176`). File as a separate issue if confirmed live.

### WARN-3 — No dedicated NUT-09 spec tests
Search of `*.spec.ts` for `restore`, `NUT.?09`, `getStoredSignature`, `storeSignedOutputs`, `signWithTracking`, `blindedMessageTracker` returned **zero matches**. The restore endpoint, the store-on-issuance invariant, and the same-length response contract have no regression-protecting tests.

**Risk**: Medium — the index-correlation invariant (M6) and the "only-if-previously-signed" gate (M2) are subtle and could regress silently during refactors of the loop body. **Recommendation**: add a spec test that (a) mints a token, (b) calls `/v1/restore` with the original outputs and asserts signatures match, (c) calls `/v1/restore` with never-signed outputs and asserts empty arrays, (d) asserts `outputs.length === signatures.length`.

### WARN-4 — Non-standard `promises` field in dead handler
`src/api/restore.ts:105-109` returns `{ outputs, signatures, promises: restoredSignatures }`. The `promises` field is not in the NUT-09 spec. Because this handler is dead code (WARN-1), no client ever sees this field. No runtime impact. Noted for completeness; resolves automatically when WARN-1 is addressed.

## Design Notes (positive observations, no action required)

1. **Stable restore key** (`nut09:{sha256(id|amount|B_)}`, L37-42): Sound design. Decouples the restore lookup from the dedup key (`blindedMessage:{B_}`), so future changes to dedup strategy cannot break restore. SHA-256 over canonical `id\namount\nB_` payload avoids delimiter ambiguity.
2. **Legacy fallback** in `getStoredSignature` (L345-356): Gracefully handles entries stored before the stable-key migration — backward compatible with pre-existing DO state.
3. **Dual-write to SQL** (`storagePutBatch` → `dualWriteToSql`, L159-172; `nut09_index` table, `schema.ts:274`): Best-effort migration path with KV remaining source of truth; SQL failures are logged, never propagated. Migration verification tooling exists (`verify-migration.ts:374-412`). Correctly conservative.
4. **Write-through cache** (`signedOutputs` Map): Populated on both store and get, so repeated restores within a DO invocation avoid storage round-trips. Cache is never authoritative (storage is), so a cold DO restart loses only the cache, not data.
5. **Defensive count check** in `storeSignedOutputs` (L271-273): Throws before any write on `outputs.length !== signatures.length`, preventing a partial/corrupt batch from reaching storage.
