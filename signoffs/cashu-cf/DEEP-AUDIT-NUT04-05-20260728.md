## HIGH Severity Findings

### H1. Error Response Format Diverges from NUT-00 Spec

**Spec (NUT-00)**: Error responses use `{"detail": "message", "code": 10001}`  
**Nutshell**: `{"detail": "message", "code": 10001}` — matches spec  
**cashu-cf**: `{"error": "error_string", "detail": "message", "code": 10001}` — **extra `error` field**

**Location**: `src/utils/error-handling.ts:116-142` (`createStandardErrorResponse`)  
**Impact**: Wallets that strictly parse NUT-00 error format may fail to extract the error detail. The `error` field is non-standard. Most handlers use `createStandardErrorResponse`, but core errors via `createErrorResponse` (`src/core/errors.ts:197`) produce the correct format.

**Evidence**:
```typescript
// createStandardErrorResponse (non-standard — adds "error" field)
interface CashuErrorResponse {
  error: string;      // <-- NON-STANDARD
  detail?: string;
  code?: number;
}
// Body: {"error":"quote_not_paid","detail":"Quote request is not paid","code":20001}

// createErrorResponse (standard — Nutshell-compatible)
// Body: {"detail":"Quote request is not paid","code":20001}
```

**Note**: The `createErrorResponse` path (used for `QuoteNotPaidError`, `QuoteExpiredError`, etc.) produces the correct format. The divergence only affects errors via `createStandardErrorResponse` and `CommonErrors.*`.

---

### H2. EXPIRED State Persisted to Database — Not a Valid NUT-04/05 State

**Spec (NUT-04)**: Valid states are `UNPAID`, `PAID`, `ISSUED`  
**Spec (NUT-05)**: Valid states are `UNPAID`, `PENDING`, `PAID`  
**Nutshell**: Does not persist EXPIRED — checks expiry timestamp, raises exception  
**CDK**: `QuoteState` has `Unpaid, Paid, Pending, Unknown, Failed` — no EXPIRED  
**cashu-cf**: Persists `quote.state = 'EXPIRED'` to storage in multiple places

**Locations**:
- `src/api/mint.ts:564` — `quote.state = 'EXPIRED' as any; await context.updateMintQuote(quote);`
- `src/api/mint.ts:597-599` — Same pattern for grace window expiry
- `src/api/mint.ts:643-644` — Backend-confirmed expiry
- `src/api/mint.ts:680-681` — Time-based fallback expiry

**Impact**: If a wallet polls `GET /v1/mint/quote/bolt11/:id` and receives `state: "EXPIRED"`, it will receive a state not defined in the NUT-04 spec. The code comments acknowledge this ("EXPIRED is NOT a state per NUT-04"), but the code persists it anyway. The response at line 714-725 returns whatever `quote.state` is, meaning the non-standard `EXPIRED` state leaks to clients.

**Fix**: Either return `UNPAID` in the response while tracking expiry internally, or omit the state field and return an error response (which the code does in some paths but not all).

---

### H3. prefer_async Response Missing Required Fields

**Spec (NUT-05)**: Melt response format includes `payment_preimage`, `request`  
**Nutshell**: `PostMeltQuoteResponse.from_melt_quote()` includes all fields  
**cashu-cf**: `prefer_async` response path omits `payment_preimage` and `request`

**Location**: `src/api/melt.ts:2849-2857`

```javascript
// Missing payment_preimage and request fields
return attachMeltHeaders(new Response(JSON.stringify({
    quote: quote.quote,
    amount: quote.amount,
    unit: quote.unit,
    method: quote.method || 'bolt11',
    fee_reserve: quote.fee_reserve,
    state: 'PENDING',
    expiry: quote.expiry
    // MISSING: payment_preimage: null, request: quote.request
}), ...));
```

**Impact**: Wallets expecting the full response schema (per NUT-05) will encounter undefined fields. The `payment_preimage` should be `null` and `request` should contain the BOLT11 invoice string.

## MEDIUM Severity Findings

### M1. NUT-08 Change Calculation Subtracts Non-Standard Fees

**Nutshell** (`ledger.py:271`):
```python
overpaid_fee = fee_provided - fee_paid
# where fee_provided = total_provided - amount - input_fees
```

**cashu-cf** (`melt.ts:3090-3103`):
```typescript
const overpaid = totalInputAmount - mintFee - (quote.amount + effectiveFeeSats)
    - virtualRoutingFee - additionalFee;
```

**Divergence**: cashu-cf subtracts `virtualRoutingFee` (percentage fee from `MELT_VIRTUAL_ROUTING_FEE_PPK`) and `additionalFee` (flat fee from `MELT_ADDITIONAL_FEE_SATS`) from the change returned to the user. Nutshell only subtracts the actual Lightning fee paid.

**Impact**: When these fees are configured (non-zero), users receive less change than they would with Nutshell. This is an intentional mint-side revenue mechanism but diverges from the reference behavior.

**Mitigation**: Default values are 0 (`getMeltVirtualRoutingFeePpk` and `getMeltAdditionalFeeSats` both default to 0), so in default configuration there is no divergence. Only activated in custom deployments.

---

### M2. Fee Reserve Includes Non-Backend Components

**Nutshell** (`ledger.py:836`): `fee_reserve = payment_quote.fee.to(unit).amount` — backend fee only  
**cashu-cf** (`melt.ts:893-934`): `totalFeeReserve = backendFee + virtualRoutingFee + additionalFee + feeReserveBuffer`

**Divergence**: cashu-cf's `fee_reserve` includes additional components beyond what the Lightning backend quoted. Wallets that calculate exact proof amounts based on `fee_reserve` will provide more proofs than strictly necessary, and the excess becomes mint revenue.

**Impact**: Same as M1 — only when non-default fees are configured. Default configuration matches Nutshell (backend fee only, plus optional buffer).

---

### M3. Melt Payment Failure Does Not Double-Check Status

**Nutshell** (`ledger.py:1237-1278`): On payment FAILED/UNKNOWN, explicitly calls `get_payment_status()` again to verify. If both agree on failure, rolls back. If they disagree, keeps PENDING and disables melt.

**cashu-cf** (`melt.ts:2749-2759`): On payment FAILED, immediately throws `LightningPaymentFailedError` without double-checking. Rollback happens in catch block.

**Impact**: If the Lightning backend returns a spurious FAILED (e.g., timeout), cashu-cf rolls back immediately without verification. Nutshell's double-check pattern is more conservative and prevents false negatives. However, cashu-cf does have its own polling loop (lines 2862-2885) that attempts to detect settlement within a timeout, and a final-status check before rollback (lines 2888-2998), which partially mitigates this.

---

### M4. Nutshell Amount Validation Uses Strict Equality; cashu-cf Allows Partial Mint

**Nutshell** (`ledger.py:536`):
```python
if not quote.amount == sum_amount_outputs:
    raise TransactionError("amount to mint does not match quote amount")
```

**cashu-cf** (`mint.ts:1107-1112`):
```typescript
const currentlyMintable = (q.amount_paid ?? q.amount) - (q.amount_issued ?? 0);
const amountTotalValidation = validateAmountTotal(totalOutputAmount, currentlyMintable, '<=');
```

**Divergence**: cashu-cf allows partial mints (`output_amount <= amount_paid - amount_issued`), Nutshell requires exact match (`output_amount == quote.amount`). 

**Spec compliance**: NUT-04 says "Mints MUST NOT issue ecash whose total output amount exceeds `amount_paid - amount_issued`" — this is a `<=` constraint. cashu-cf is **more spec-compliant** than Nutshell here. This was fixed in ISSUE-023.

**Impact**: Wallets designed for Nutshell may not expect partial mint behavior. This is a forward-compatible improvement but could confuse wallets that assume exact-match enforcement.

---

### M5. HTTP Status Code for LightningPaymentFailedError

**Nutshell**: Returns HTTP 402 (Payment Required) or 502 for Lightning errors, depending on error subclass  
**cashu-cf**: `createErrorResponse` returns HTTP 400 for ALL `CashuError` subclasses including `LightningPaymentFailedError`

**Location**: `src/core/errors.ts:197-203`:
```typescript
export function createErrorResponse(error: unknown, headers: HeadersInit = {}): Response {
  const body = formatErrorResponse(error);
  const status = error instanceof CashuError ? 400 : 500;
  // ^--- ALL CashuErrors get 400, including LightningPaymentFailedError (code 20004)
```

**Impact**: Wallets that key on HTTP status to distinguish payment failures from validation errors will not be able to differentiate. NUT-05 implies Lightning failures should be distinguishable. CDK returns different status codes for different error types.

## LOW Severity Findings

### L1. Quote ID Format — Short Hex Instead of UUID v7

**Spec (NUT-04)**: Quote IDs "SHOULD be UUID v7"  
**Nutshell**: `generate_uuid_v7()` — proper UUID v7  
**CDK**: `QuoteId` type — UUID v7  
**cashu-cf**: `generateQuoteId()` — 16-character hex string (8 bytes from CSPRNG)

**Location**: `src/api/mint.ts:294`, `src/api/melt.ts:837`

**Impact**: This is a SHOULD, not a MUST. The short IDs are cryptographically random and collision-resistant. Wallets should not depend on UUID format. Low interop risk.

---

### L2. CDK Has FAILED and UNKNOWN Quote States; Neither cashu-cf nor Nutshell Do

**CDK** (`nut05.rs:40-52`): `QuoteState::Failed`, `QuoteState::Unknown`  
**Nutshell**: Only `UNPAID`, `PENDING`, `PAID`  
**cashu-cf**: Only `UNPAID`, `PENDING`, `PAID` (plus non-standard `EXPIRED`)

**Impact**: None — CDK's extra states are not in the NUT-05 spec. cashu-cf matches the spec here.

---

### L3. Nutshell Has `mint_max_balance` Check; cashu-cf Does Not

**Nutshell** (`ledger.py:353-356`): Checks `balance + quote_request.amount > settings.mint_max_balance` before creating mint quote  
**cashu-cf**: No equivalent check

**Impact**: Operational safety feature, not a spec requirement. cashu-cf relies on `MAX_OPERATION_AMOUNT` for per-transaction limits instead of aggregate balance limits.

---

### L4. Nutshell Rate-Limits Backend Invoice Status Checks

**Nutshell** (`ledger.py:430-440`): `try_update_mint_quote_last_checked()` with `settings.mint_quote_backend_check_rate_limit` — prevents excessive backend polling  
**cashu-cf**: No rate limiting on invoice status checks in `handleMintQuoteStatus`

**Location**: `src/api/mint.ts:630-711` — every status poll triggers a backend check if UNPAID

**Impact**: A wallet polling aggressively could cause excessive Lightning backend API calls. Nutshell protects against this with a rate limit per quote.

## INFO — Intentional Design Choices

### I1. Reservation-Based Mint Flow (cashu-cf Extension)

**cashu-cf** uses a two-phase reservation system for mint operations:
1. `setMintQuoteIssuing()` — atomically reserves the quote with an issuance token
2. `signBlindedMessages()` — performs the actual signing
3. `finalizeMintQuoteIssued()` — commits the final state

**Nutshell** uses a simpler `_set_mint_quote_pending` / `_unset_mint_quote_pending` pattern.

This is an intentional cashu-cf design for Cloudflare Workers' concurrent execution model. Not a divergence per se, but a different concurrency strategy.

---

### I2. Idempotency Journal

**cashu-cf** implements an `IdempotencyJournal` (`src/idempotency_journal.ts`) for replay-safe mint/melt operations. Neither Nutshell nor CDK have this. This is a robustness improvement, not a divergence.

---

### I3. Sibling Mint Detection

**cashu-cf** has extensive sibling mint swap detection (`src/utils/sibling-mint-query.ts`). This is a multi-mint deployment feature unique to cashu-cf. Not present in Nutshell or CDK.

## Recommendations (Priority Order)

1. **H1**: Unify error response format — make `createStandardErrorResponse` produce `{"detail", "code"}` only, without the `error` field. Or at minimum, ensure the spec-required fields are always present.

2. **H2**: Stop persisting `EXPIRED` as a quote state. Return `UNPAID` in responses for expired quotes, or return an error response (the code already does this in some paths). The persisted state should remain `UNPAID`; expiry is derived from the `expiry` timestamp.

3. **H3**: Add `payment_preimage: null` and `request: quote.request` to the prefer_async response at `melt.ts:2849-2857`.

4. **M5**: Map `LightningPaymentFailedError` to HTTP 402 (Payment Required) instead of 400. This aligns with wallet expectations for payment failures.

5. **M3**: Add Nutshell's double-check pattern for Lightning payment failures — before rolling back, query the backend once more to confirm failure.

6. **L4**: Add rate limiting for mint quote status checks to prevent excessive backend API calls from aggressive wallet polling.

---

## Conclusion

cashu-cf's NUT-04/NUT-05 implementation is broadly compatible with the Cashu ecosystem. The core state machines match the spec. The most significant interop risks are:

1. The non-standard `EXPIRED` state leaking into API responses (H2)
2. The extra `error` field in error responses (H1)  
3. Missing fields in the prefer_async response (H3)

The fee calculation extensions (M1, M2) are intentional design choices with safe defaults. The partial mint support (M4) is actually more spec-compliant than Nutshell.

The codebase demonstrates sophisticated handling of Cloudflare Workers' concurrency model with reservation-based minting, idempotency journals, and extensive crash recovery — features absent from both reference implementations.
