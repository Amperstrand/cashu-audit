## Findings

### Finding 1: prefer_async response missing `amount` and `unit` fields (FAIL)
- **Severity**: Medium
- **Location**: melt.ts:2833-2837
- **Spec reference**: NUT-05 L152-161 — Async response MUST include `quote`, `amount`, `unit`, `state`, `expiry`
- **Description**: When `prefer_async: true` and payment doesn't settle immediately, the response is:
  ```json
  {"quote": "...", "state": "PENDING", "expiry": 1234567890}
  ```
  The spec requires `amount` and `unit` to be present. Wallets relying on these fields from the async response will encounter `undefined` values.
- **Impact**: Medium — wallets that don't cache the original quote amount/unit will need a follow-up `GET` to retrieve them. Not a security issue but a protocol compliance gap.
- **Fix**: Change lines 2833-2837 to:
  ```typescript
  return attachMeltHeaders(new Response(JSON.stringify({
    quote: quote.quote,
    amount: quote.amount,
    unit: quote.unit,
    fee_reserve: quote.fee_reserve,
    state: 'PENDING',
    expiry: quote.expiry
  }), { status: 200, headers: { 'content-type': 'application/json' } }));
  ```
  Also consider using `createStandardJsonResponse()` for consistent CORS headers.
- **Related**: ISSUE-017 (`prefer_async` field implementation) was marked "done" but the response shape was not validated against the spec.

### Finding 2: Quote ID uses 128-bit random hex instead of UUID v7 (WARN)
- **Severity**: Low
- **Location**: `src/core/utils.ts:24-30`
- **Spec reference**: NUT-05 L75 — "quote is the quote ID string in UUID v7 format with all 74 variable bits generated by a CSPRNG"
- **Description**: `generateQuoteId()` returns `bytesToHex(crypto.getRandomValues(16))` — a 32-character hex string of 128 random bits. This is NOT UUID v7 format (which requires a 48-bit timestamp, version nibble `0111`, and variant bits). The implementation provides more entropy (128 bits vs 74 variable bits) but sacrifices time-ordering and format compliance.
- **Impact**: Low — quote IDs are opaque strings to wallets. Collision resistance is actually higher than UUID v7. The main loss is time-based sorting of quotes in storage. No interoperability issue observed.
- **Note**: Code comment at melt.ts:833 acknowledges the spec requirement ("NUT #05: quote is the quote ID string in UUID v7 format") but the implementation doesn't match.

### Finding 3: `method` field omitted from quote responses (WARN)
- **Severity**: Low
- **Location**: melt.ts:1014-1023 (quote creation), melt.ts:1225-1235 (status check), melt.ts:3212-3223 (melt response)
- **Spec reference**: NUT-05 L67 — common response fields include `"method": <str>`
- **Description**: The `method` field is stored on the `ExtendedMeltQuote` object (melt.ts:982: `method: isUpi ? 'upi' : ... : 'bolt11'`) but never included in any API response. The `MeltQuoteBolt11Response` type from `@cashu/cashu-ts` may not include this field.
- **Impact**: Low — all endpoints are under `/bolt11/` paths, so clients can infer the method. No wallet interoperability issue observed. Spec compliance gap only.

### Finding 4: No dynamic `{method}` path routing (WARN)
- **Severity**: Info
- **Location**: melt-routes.ts:10-27
- **Spec reference**: NUT-05 L38, L41 — `POST /v1/melt/quote/{method}` and `POST /v1/melt/{method}`
- **Description**: Routes are hardcoded to `bolt11`. Fiat-rail methods (`upi`, `payto`, `spayd`, `custom`) are detected from BOLT11 invoice descriptions (melt.ts:208-239) rather than routed as separate method paths. This is an intentional architectural choice — all fiat-rail quotes are created and melted via the `bolt11` endpoints.
- **Impact**: Info — the regex constraint `[a-z0-9_-]+` is trivially satisfied since only `bolt11` is routable. No security issue.

### Finding 5: ISSUE-023-style output validation bug NOT present (INFO — positive finding)
- **Severity**: N/A
- **Location**: melt.ts:2014-2018
- **Description**: ISSUE-023 found that NUT-04 mint output validation used `===` (strict equality) instead of `<=`. The melt flow correctly uses `>=` for input amount validation:
  ```typescript
  const requiredAmount = quote.amount + quote.fee_reserve + mintFee;
  const amountTotalValidation = validateAmountTotal(totalInputAmount, requiredAmount, '>=');
  ```
  This correctly allows wallets to overpay (with excess returned as NUT-08 change). No similar bug exists in the melt path.
