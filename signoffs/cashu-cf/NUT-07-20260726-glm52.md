## Findings

### Finding 1: `witness` field always null — NUT-10/11/14 witness data not persisted (WARN)
- **Severity**: Low (feature gap, not a spec violation)
- **Location**: `src/api/checkstate.ts:148,154,177,210,232,275,317` (all response construction sites); `src/proof-state-manager.ts:16-21` (`ProofState` interface lacks `witness` field)
- **Spec reference**: 07.md:72 — "`witness` is the serialized witness data that was used to spend the `Proof` if the token has a NUT-10 spending condition that requires a witness such as in the case of P2PK (NUT-11) or HTLCs (NUT-14)."
- **Description**: The `witness` field is structurally present in every response object (correct shape), but is hardcoded to `null` at all 7 response construction sites. The `ProofState` interface in `proof-state-manager.ts` has no `witness` field — witness data from P2PK/HTLC spend operations (`src/api/melt.ts:2116-2120`, `src/mint/spending-conditions.ts`) is used for verification during the spend but never persisted to storage for later retrieval.
- **Impact**: Wallets querying checkstate for P2PK or HTLC proofs will always see `witness: null` even after the proof is spent with a witness. This limits post-hoc auditability of spending conditions. NUT-11 (P2PK) is advertised as supported by default (`info.ts:148`), so this gap is user-facing. NUT-14 (HTLC) is disabled by default, softening impact.
- **Mitigating factors**: (1) The field IS present in the response — no shape violation. (2) For non-NUT-10 proofs (the vast majority), `null` is the correct value. (3) The spec uses declarative ("is the serialized witness data") rather than mandatory ("MUST return") language. (4) Witness verification at spend time IS correctly implemented — this is purely a storage/retrieval gap.
- **Recommendation**: Add a `witness` column to the proof state storage and populate it during `setSpent`/`setSpentBatch` when the spend operation includes witness data. Thread the witness through from melt/swap handlers to `ProofStateManager`.

### Finding 2 (informational): Legacy request format support extends beyond spec
- **Severity**: Informational (no action needed)
- **Location**: `src/api/checkstate.ts:126-243`
- **Description**: The handler supports two non-standard request formats beyond the spec's `Ys` array: `{ proofs: [{ secret, Y }] }` and `{ secrets: [...] }`. These legacy formats derive `Y` from secrets via `hashToCurve` and even handle hex-encoded secrets via a dual-derivation fallback (L157-175). The standard `Ys` format is the primary path (L122-327).
- **Impact**: None — backward compatibility extension. The standard format works correctly and is the first-matched branch.

### Finding 3 (informational): Duplicate Y rejection is stricter than spec
- **Severity**: Informational (no action needed)
- **Location**: `src/api/checkstate.ts:259-262`
- **Description**: The handler rejects requests with duplicate Y values with HTTP 400. The NUT-07 spec does not mention duplicate handling. This is a reasonable design choice but could theoretically break a wallet that sends duplicates expecting idempotent responses.

### Finding 4 (informational): Stale PENDING recovery mechanism
- **Severity**: Informational (positive finding)
- **Location**: `src/proof-state-manager.ts:834-968` (`recoverStalePendingProofs`)
- **Description**: The implementation includes a recovery mechanism for proofs stuck in PENDING state longer than a configurable threshold. This directly addresses the spec's note (07.md:21) about PENDING proofs needing to be tracked — if a rollback fails silently, proofs would be burned forever without this recovery. This is beyond spec requirements but strengthens the PENDING tracking guarantee.
