## Spec Requirement Extraction

NUT-03 (`03.md`) is marked `mandatory` (L3). The core normative statement (L7):

> "Mints **verify** and **invalidate** the inputs and **issue new promises (`BlindSignatures`)**."

Derived MUST requirements:
- **R1** — Accept `POST /v1/swap` endpoint (L28)
- **R2** — Request body is `PostSwapRequest { inputs: Array[Proof], outputs: Array[BlindedMessage] }` (L31–38)
- **R3** — **Verify** input proofs (cryptographic validity) (L7)
- **R4** — **Invalidate** input proofs (mark spent; cannot be reused) (L7, L15)
- **R5** — **Issue** new `BlindSignature`s for output `BlindedMessage`s (L7)
- **R6** — Response body is `PostSwapResponse { signatures: Array[BlindSignature] }` (L71–77)
- **R7** — Balance conservation: input total covers output total (examples L15, L21 show equal sums; NUT-02 fees apply)
- **R8** — Settlement guarantee: once new outputs are issued, old inputs cannot be double-spent (L21)

## Findings

### FINDING-1 — WARN: Probe-based pre-check redundancy (non-blocking)
**Location**: `router.ts:776-812`
**Description**: `handleSwap` performs a "probe" cycle — `setPendingBatch` then immediately `rollbackPending` — before delegating to `features.swapProofs`, which performs its own independent proof-state check + pending lock (`features.ts:504-527`). The probe adds two extra storage I/O round-trips per swap that are fully redundant with `swapProofs`'s built-in ACID handling.
**Correctness impact**: None. Cloudflare Durable Objects serialize handlers per-object, and `swapProofs` re-checks state authoritatively. A concurrent swap that completes between probe-rollback and `swapProofs` will be correctly rejected by `swapProofs`'s own SPENT check. The probe is purely an early-reject optimization that never weakens the invariant.
**Recommendation**: Consider removing the probe and relying solely on `swapProofs`'s proof-state management to reduce storage write amplification. Non-blocking for spec compliance.

### FINDING-2 — INFO: Overpayment policy (intentional, Nutshell-aligned)
**Location**: `features.ts:652, 663-692`
**Description**: The balance check enforces `inputAmount >= outputAmount + requiredFee` (≥, not ==). This permits a client to supply inputs exceeding the required output+fee total, with the excess effectively burned. The NUT-03 spec examples show exactly-balanced swaps but do not mandate rejection of overpayment.
**Assessment**: Matches Nutshell reference behavior (explicit comment `features.ts:652`: "Nutshell semantics: inputs - fees must be >= outputs (allow overpayment for compatibility)"). Intentional design choice. No spec violation.

### FINDING-3 — INFO: DLEQ proof attachment (NUT-12 surface)
**Location**: `features.ts:776-797`
**Description**: Each `BlindSignature` returned in the swap response carries an additive `dleq` field (NUT-12). If `createDLEQProof` throws, the code falls back to a SHA256-based pseudo-proof (`:788-792`), then to zero-valued placeholders (`:793-796`). The zero-placeholder fallback produces a cryptographically meaningless DLEQ proof.
**Assessment**: The core NUT-03 fields (`id`, `amount`, `C_`) are always correct regardless of DLEQ status. The `dleq` field is a NUT-12 extension; wallets ignoring it are unaffected. This is a NUT-12 quality concern, not a NUT-03 violation. The zero-fallback path is unreachable in practice (SHA256 over a valid point + 32-byte key never fails), so impact is theoretical.

## Privacy Enhancement (exceeds spec)

NUT-03 L17 recommends (SHOULD, client-side) that wallets order outputs by ascending amount. The mint goes further: `features.ts:715-720` sorts outputs server-side before signing, then reorders signatures to match the client's original request order (`features.ts:803-809`, `originalIndexMap` at `:725-737`). This defensive privacy measure defeats amount-inference attacks even when clients don't follow the SHOULD. Not required by spec — exceeds it.
