**Overall verdict: PASS** — All core cryptographic requirements are correctly implemented. The mint produces spec-compliant blind signatures (`C_ = kB_`), verifies proofs (`k*hash_to_curve(x) == C`), serializes curve points as SEC1 compressed, and uses the correct `hash_to_curve` domain separator via `@cashu/cashu-ts`. ## Findings

### Finding 1: Dual-encoding secret fallback in `cashu-crypto.ts` (WARN)
- **Severity**: Low (backwards-compatibility only; new signatures always UTF-8)
- **Location**: `src/crypto/cashu-crypto.ts:209-226`; `src/crypto/secret-encoding.ts:48-60`
- **Description**: `verifyProofSignatureWithPrivateKey()` (cashu-crypto.ts:177-241) first tries UTF-8 encoding of the secret (spec-compliant, L195-207), but if that fails, it falls back to hex-decoding 64-char hex secrets (L211-226). This dual-encoding support exists for backwards compatibility with legacy ecash that may have been signed with hex-decode encoding.
- **Spec position**: NUT-00 L27 states "`x` UTF-8-encoded random string". The spec defines exactly one encoding. The fallback technically accepts proofs that were NOT created per the current spec.
- **Impact**: New proofs are always created with UTF-8 encoding (`KeysetManager.ts:479` uses `TextEncoder().encode()` exclusively — no hex-decode path). The fallback only affects verification of old ecash from other mints that used hex-decode. Since verification is a mint-side concern (the mint verifies proofs it receives for melt/swap), this could theoretically accept a proof signed by a non-compliant mint as valid if the private key happens to match — but this is astronomically unlikely since key derivation is mint-specific.
- **Note**: The primary verification path in `KeysetManager.verifyProofWithKey()` (L474-500) uses **UTF-8 only** — no fallback. The dual-encoding path exists only in the standalone `cashu-crypto.ts` module. The `secretToBytes()` function in `secret-encoding.ts:48-60` also implements dual logic (hex-decode for 64-char hex, UTF-8 otherwise), which is used by `verifyProofSignature()` (cashu-crypto.ts:143).

### Finding 2: Dual error-response systems — legacy adds non-standard `error` field (WARN)
- **Severity**: Low (additive field; primary system is compliant)
- **Location**: `src/utils/error-handling.ts:93-97,116-142` vs `src/core/errors.ts:8-20,182-204`
- **Description**: The codebase has two error-response systems:
  1. **`core/errors.ts`** (primary, NUT-00 compliant): `CashuError.toJSON()` → `{detail, code}`. `createErrorResponse()` → HTTP 400. Used by `mint-do.ts`, `mint-routes.ts`, `melt-routes.ts`.
  2. **`utils/error-handling.ts`** (legacy, non-standard): `CashuErrorResponse` = `{error: string, detail?: string, code?: number}`. `createStandardErrorResponse()` produces responses with an extra `error` field and optionally omits `code`. Used by `src/mint/router.ts`.
- **Spec deviation**: NUT-00 L128-133 defines error body as exactly `{"detail": "...", "code": ...}`. The legacy system adds `error` (non-standard) and makes `code` optional (spec implies it's always present). The `code` field is conditionally spread: `...(code && { code })` at L126, meaning `code: 0` would be omitted (falsy).
- **Impact**: The primary system (`core/errors.ts`) is used by the NUT endpoint handlers in `mint-routes.ts` and `melt-routes.ts`. The legacy system (`router.ts`) handles `/v1/keys`, `/v1/keysets`, `/v1/info`, `/v1/swap`, `/v1/checkstate` — these return `{error, detail?, code?}` instead of `{detail, code}`. Compliant clients parse `detail` and `code`, so the extra `error` field is harmless. However, some responses from the legacy system omit `code` entirely when it's falsy.
- **Mitigation**: `router.ts:67` explicitly labels `createErrorResponse` as "DEPRECATED - use CommonErrors instead", indicating active migration toward the compliant system.

### Finding 3: V4 token encoder does not strip trailing slashes from mint URL (WARN)
- **Severity**: Very Low (tools-only path; not used in production API responses)
- **Location**: `src/tools/token-formats.ts:132,184`
- **Description**: `encodeTokenV4Cbor()` reads `token.mint` at L132 without stripping trailing `/` characters, violating the MUST at spec L281. The V3 encoder delegates to upstream `getEncodedTokenV3()` which handles this correctly.
- **Impact**: The `tools/` directory contains test/utility code. The mint's production API endpoints (`/v1/mint/bolt11`, `/v1/swap`) return `SerializedBlindedSignature[]` arrays, not serialized token strings. Token serialization is a wallet-side concern. This only affects tokens generated by the cashu-cf test/tools utilities.

**NUT-00 compliance: PASS**

All core cryptographic operations (BDHKE key exchange, blind signing, proof verification, hash_to_curve with correct domain separator, SEC1 compressed point serialization) are correctly implemented via `@cashu/cashu-ts` v3.3.0 and `@noble/curves`.
