## Critical Finding: Message Construction Deviation

### The spec format (NUT-20 L109-123)

```
msg_to_sign = b"Cashu_MintQuoteSig_v1"
              || len32(quote) || quote
              || for each output i:
                   len32(amount_i) || amount_i
                   || len32(B_i)   || B_i
```

Where `len32(x)` is 4-byte big-endian length; `amount_i` is canonical minimal big-endian; `B_i` is raw bytes decoded from hex.

### The implementation (nut20.ts:33-38)

```typescript
export function constructMessage(quoteId: string, outputs: SerializedBlindedMessage[]): Uint8Array {
  const serializedOutputs = outputs.map(o => o.B_).join('');
  const payload = encoder.encode(quoteId + serializedOutputs);
  return sha256(payload);
}
```

This computes `SHA256( UTF8(quoteId + B_1_hex + B_2_hex + ... + B_n_hex) )`.

### What's missing

| Component | Spec | Implementation |
|-----------|------|----------------|
| Domain separation tag `b"Cashu_MintQuoteSig_v1"` | 20 raw bytes, not length-prefixed | **Absent** |
| `len32(quote)` prefix | 4-byte BE length before quote bytes | **Absent** |
| `len32(amount_i) \|\| amount_i` per output | Amount committed in signature | **Absent** (amounts excluded entirely) |
| `len32(B_i)` prefix per output | 4-byte BE length before raw B_ bytes | **Absent** |
| `B_i` as raw bytes | hex-decoded 33/48-byte point | **UTF-8 hex string** (ASCII characters) |

### Runtime proof against official test vector

Official vector (nuts/tests/20-test.md): pubkey `0279be667e...` (sk=0x01), quote `0192d3c0-...`, 2 outputs à 1 sat.

```
cashu-cf hash:   8191ccee77269f05dfb42a2fd713b75a270f4c599e6952ce02b6f49062cf7874
                 → schnorr.verify = false  ❌

spec hash:       c164fd384879f74ab6ea2e7cf13d90ed42e6df9d5de607eeb5c9cc7d36fb1c21
                 (matches expected hash in test vector)
                 → schnorr.verify = true   ✅
```

**Any spec-compliant wallet's valid signature will be rejected by this mint.**

### Security impact

Amounts are excluded from the signed message. While the mint validates total output amount elsewhere (`mint.ts:948`), the signature no longer commits to individual output amounts. A signer who signed for outputs `[8, 2]` cannot prove they didn't sign for `[10, 0]` — the signature is identical for any amount combination with the same `B_` values. This weakens the non-repudiation guarantee that NUT-20 is designed to provide.

## Secondary Findings

### F1: Test file uses fabricated "official" test vectors

`test/unit/protocol/nut20-quote-signature.unit.test.ts:223` is titled **"NUT-20 official test vectors (nuts/tests/20-test.md)"** but uses self-generated vectors with the *old* message format, not the actual vectors from `nuts/tests/20-test.md`:

| Field | Test file (fake) | Actual nuts/tests/20-test.md |
|-------|-----------------|------------------------------|
| pubkey | `03d56ce4e446a85b...` | `0279be667ef9dcbb...` |
| signature | `d4b386f21f7aa717...` | `4881093a332ff7c7...` |
| quote | `9d745270-...` | `0192d3c0-...` |

The test at line 254 claims "expected bytes copied from nuts/tests/20-test.md" but the expected byte array is merely the UTF-8 encoding of `quoteId + B_hex_concat` — the wrong format. This masks the bug: tests pass but prove nothing about spec compliance.

### F2: Duplicate verification logic (dead code)

`verification.ts:107-119` (`_verifyQuoteWitness`) duplicates the same wrong message construction from `nut20.ts:constructMessage`. The production mint path (`mint.ts:1227`) calls `verifyMintQuote()` from `nut20.ts` directly — the `LedgerVerification.verifyQuote()` path is only exercised in unit tests. Both paths share the same bug.

### F3: `generateKeypair()` always produces 02-prefixed pubkeys

`nut20.ts:25` — `publicKey: \`02${bytesToHex(publicKey)}\`` unconditionally uses `02` (even-y). BIP340 x-only pubkeys implicitly assume even-y, so the compressed form should always be `02`-prefixed for keys generated this way. This is correct behavior for a key generation utility, though note this function is wallet-side and not used by the mint itself.

The NUT-20 implementation has correct API plumbing, error codes, settings advertisement, and pubkey validation. However, the **core cryptographic message format is wrong**, making it completely non-interoperable with spec-compliant wallets. The official test vector fails. The unit tests are self-referentially validating the wrong format while claiming to use official vectors.

**Recommendation:** Rewrite `constructMessage()` in `nut20.ts` to follow the spec's binary format with domain separation tag and length-prefixed fields. Replace the fabricated test vectors with the real ones from `nuts/tests/20-test.md`. Remove the duplicate logic in `verification.ts`.
