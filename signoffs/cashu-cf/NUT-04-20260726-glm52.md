## Findings

### Finding 1: Quote ID embedded in invoice description (WARN)
- **Severity**: Medium
- **Location**: mint.ts:341 (`const invoiceDescription = description ?? \`quote ${quoteId}\`;`)
- **Description**: When no user-supplied `description` is provided (the common case), the full 32-character quote ID is embedded in the BOLT11 invoice description as `"quote <quoteId>"`. The BOLT11 payment request is a self-contained string whose description field is readable by anyone who decodes it. NUT-04 L89 states: "`quote` MUST remain a secret between user and mint and MUST NOT be derivable from the payment request. A third party who knows the `quote` ID can front-run and steal the tokens."
- **Impact**: If the payment request is shared with a third party (e.g., Bob pays Alice's invoice), that party can decode the BOLT11, extract the quote ID, and call `POST /v1/mint/bolt11` with their own outputs to steal the minted tokens. This is the exact front-running attack the spec warns about.
- **Mitigations present**: (1) If the user supplies a custom `description`, the quote ID is not embedded. (2) NUT-20 pubkey locks (mint.ts:1223-1231) prevent unauthorized minting. (3) Lightning routing nodes do not see the description field — only the payment hash.
- **Stale comment**: mint.ts:339 says "Use short 16-character quote ID only (no full UUID in description)" but the code embeds the full 32-char ID. The comment does not match the implementation.
- **Recommendation**: Use an opaque lookup identifier (e.g., a separate `lookup_id` not used as the quote ID) for sibling mint detection, or hash the quote ID before embedding. Alternatively, document this as an accepted risk when NUT-20 is not used.

### Finding 2: `updated_at` not persisted or tied to accounting changes (WARN)
- **Severity**: Low
- **Location**: mint.ts:424, 722, 806 (all response builders use `nowSec()`)
- **Description**: `updated_at` is computed fresh as `Math.floor(Date.now() / 1000)` on every response. It is never stored on the quote record and does not reflect when `amount_paid` or `amount_issued` actually changed. The spec (L85) says: "Mints MUST update `updated_at` whenever `amount_paid` or `amount_issued` changes." A GET status check that returns a different `updated_at` than a previous check does not indicate any accounting change occurred — it just means time passed.
- **Impact**: Low — wallets use `updated_at` for staleness detection (spec L85: "Wallets MUST NOT replace locally stored quote data with a response whose `updated_at` is lower"). Since `updated_at` only ever increases (wall clock), this staleness check never triggers false positives. However, it also never meaningfully signals that accounting changed.
- **Recommendation**: Persist `updated_at` on the quote record. Set it to `nowSec()` when `amount_paid` or `amount_issued` changes (in `updateMintQuote`, `finalizeMintQuoteIssued`). Return the stored value in responses rather than recomputing.

### Finding 3: `updated_at` lacks sub-second monotonicity guarantee (WARN)
- **Severity**: Low
- **Location**: core/utils.ts:14-16 (`nowSec`)
- **Description**: `nowSec()` has 1-second resolution. Two concurrent requests within the same second produce identical `updated_at` values. The spec (L85) says: "Mints MUST ensure that `updated_at` monotonically increases for each quote, even if multiple updates occur within the same timestamp resolution."
- **Impact**: Low — the practical impact is that two rapid updates to the same quote within 1 second are indistinguishable by `updated_at`. Since `amount_issued` is always `0` and `amount_paid` only transitions once (UNPAID→PAID), the practical collision window is narrow.
- **Recommendation**: If strict monotonicity is required, use millisecond timestamps or a monotonic counter combined with the second-resolution timestamp.

### Finding 4: Partial-mint lifecycle incomplete (WARN)
- **Severity**: Low
- **Location**: mint.ts:1067-1076 (validation), crud.ts:440-444 (finalization)
- **Description**: ISSUE-023 correctly fixed the validation to allow partial mints (`output <= amount_paid - amount_issued`). However, the downstream lifecycle does not support the multi-pass partial-mint pattern implied by spec L83: "If a wallet mints less than the currently mintable amount, `amount_issued` only increases by the amount that was issued." After any successful mint, `finalizeMintQuoteIssued` (crud.ts:440-444) sets `state = ISSUED` and `consumed = true` without recording how much was issued. `amount_issued` remains `0` in storage and in all responses. A subsequent mint attempt returns `QuoteAlreadyIssuedError` (mint.ts:1101,1133).
- **Impact**: Low — wallets that mint the full amount in one pass (the dominant pattern) are unaffected. Only multi-pass partial mints (mint some now, mint the rest later) are impacted: the second pass fails. No known wallet uses multi-pass partial minting today.
- **Recommendation**: If multi-pass partial minting is desired, persist `amount_issued` on the quote record, increment it by the minted output total in `finalizeMintQuoteIssued`, and only set `ISSUED`/`consumed` when `amount_issued >= amount_paid`. This was noted as an open question in ISSUE-023.

### Finding 5: Quote ID is not UUIDv7 format (INFO)
- **Severity**: Info
- **Location**: core/utils.ts:24-30
- **Description**: Quote IDs are 32-character hex strings (16 random bytes from CSPRNG), not UUIDv7 format. NUT-04 L89 says: "`quote` SHOULD be UUID v7 with all 74 variable bits generated by a CSPRNG." This is a SHOULD, not a MUST.
- **Impact**: None functionally. The 128 bits of entropy (16 bytes) exceed UUIDv7's 74 variable bits. The format differs (raw hex vs `xxxxxxxx-xxxx-7xxx-...`), which may affect wallets that validate quote ID format, though no known wallet does.
- **Recommendation**: Consider migrating to UUIDv7 format for spec alignment. Low priority since the requirement is SHOULD.
