## Scenario Verification

### Scenario 1: Standard overpayment return (happy path)
- **Setup**: Invoice 1000 sat, fee_reserve 10 sat, wallet provides 1010 sat + 4 blank outputs. Actual LN fee = 2 sat.
- **Expected**: overpaid = 1010 − 0 (mintFee) − (1000 + 2) − 0 − 0 = 8 sat. Decomposed to [8] or [4,4] depending on keyset denominations. Signed and returned as `change`.
- **Code path**: melt.ts:3081 computes `overpaid = 8`. nut08.ts:52 `splitAmountToDenominations(8, [1,2,4,8,...])` → `[8]` (greedy). nut08.ts:65-68 imprints amount=8 on first blank output, 0 on rest. nut08.ts:72 filters to `[output_0_with_amount_8]`. melt.ts:3152 signs it. melt.ts:3222 includes `change: [{amount:8, C_:"...", id:"..."}]`.
- **Verdict**: ✅ Correct

### Scenario 2: No overpayment (exact fee)
- **Setup**: Invoice 1000 sat, fee_reserve 10 sat, wallet provides 1010 sat + 4 blank outputs. Actual LN fee = 10 sat.
- **Expected**: overpaid = 1010 − 0 − (1000 + 10) − 0 − 0 = 0. No change returned.
- **Code path**: melt.ts:3081 `overpaid = 0`. melt.ts:3123 `0 > 0` is false → skip change signing. `changeSignatures` stays `[]`. melt.ts:3222 `0 > 0` false → `change` omitted from response.
- **Verdict**: ✅ Correct

### Scenario 3: No blank outputs provided
- **Setup**: Invoice 1000 sat, fee_reserve 10 sat, wallet provides 1010 sat, NO outputs.
- **Expected**: No change returned even if overpaid > 0.
- **Code path**: melt.ts:3123 `changeOutputs.length > 0` is false → skip. Response omits `change`.
- **Verdict**: ✅ Correct

### Scenario 4: Overpaid amount requires more blank outputs than provided
- **Setup**: fee_reserve=1000 (requires ceil(log2(1000))=10 blank outputs), wallet provides only 3.
- **Expected**: Mint should handle gracefully.
- **Code path**: melt.ts:2103 `minBlank = requiredBlankOutputsForFeeReserve(1000) = 10`. `3 < 10` → 400 error "Not enough blank outputs for fee_reserve=1000 (need >= 10)".
- **Verdict**: ✅ Correct (fails safe with clear error)

### Scenario 5: Order preservation with mixed zero/non-zero amounts
- **Setup**: 5 blank outputs, overpaid decomposes to [0, 4, 0, 2, 0] (positions in original array).
- **Expected**: Returned signatures = [4-sig, 2-sig] in that order (positions 1 and 3).
- **Code path**: nut08.ts:65 maps over all 5: [0, 4, 0, 2, 0]. nut08.ts:72 filters amount > 0: [4-sig@pos1, 2-sig@pos3]. Order preserved. melt.ts:3152 signs in this order. Response `change` array is [4-sig, 2-sig].
- **Verdict**: ✅ Correct

## Findings Summary

### PASS Items (14)
All 7 MUST requirements (N08-M1 through N08-M7) are correctly implemented. Additional robustness in keyset validation (N08-V1), minimum output enforcement (N08-V2), quote persistence (N08-V3), safe failure on insufficient outputs (N08-C1), zero-overpaid handling (N08-C2), and both async settlement paths (N08-A1, N08-A2).

### WARN Items (3 — all non-blocking)

1. **N08-O1: Overpaid formula includes mint-kept fees** (melt.ts:3081)
   - Sync path subtracts `virtualRoutingFee` and `additionalFee` from overpaid, reducing user's change return. These are mint profit, not LN fees. Spec formula is `input_amount − fees − total_paid` where "fees" is ambiguous. In Blink passthrough mode, both are 0 (spec-compliant). For non-Blink backends, user gets less change than strict reading of spec suggests. **Impact**: User receives slightly less change; mint keeps more. Not a security issue. **Recommendation**: Document this as intentional fee policy, or align the formula across all backends.

2. **N08-O2: B_ reuse recovery not spec-defined** (melt.ts:3154-3183)
   - On retry with same B_ values, the mint replays stored signatures instead of erroring. This is a pragmatic idempotency measure but NUT-08 doesn't define retry semantics. **Impact**: Prevents user fund loss on retries. **Recommendation**: Acceptable as-is; behavior is user-friendly.

3. **N08-A3: Async overpaid formula drift** (melt-quote-do.ts:205, poll-melts.ts:202)
   - Async settlement paths (MeltQuoteDO, Blink poll) use simpler formula without `virtualRoutingFee`/`additionalFee`, while sync path includes them. Same inputs produce different change amounts depending on settlement path. **Impact**: Async-settled melts return more change. **Recommendation**: Align formulas across all code paths.

### FAIL Items (0)
None.

## Conclusion

**NUT-08 Status: ✅ COMPLIANT**

All MUST requirements are met. The implementation correctly:
1. Accepts blank outputs from wallets and ignores their `amount` field
2. Computes overpaid fees after Lightning settlement
3. Decomposes overpaid amounts into keyset denominations
4. Imprints amounts on blank outputs preserving original order
5. Returns only non-zero signatures in correct order
6. Conditionally includes `change` in the response (only when overpaid > 0 and outputs provided)
7. Advertises NUT-08 support in the NUT-06 info endpoint

The three WARN items are non-blocking policy/consistency observations, not spec violations. The overpaid formula deviation (N08-O1) is in the mint's favor and only affects non-Blink backends. The async formula drift (N08-A3) is in the user's favor. Neither represents a correctness or security issue.
