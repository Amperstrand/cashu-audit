## MUST Extraction

NUT-19 is a short spec (64 lines) that uses SHOULD/CAN normative keywords — no explicit MUST statements. The requirements below are SHOULD-level normative statements and structural definitions from the spec.

| # | Source | Requirement | Type |
|---|--------|-------------|------|
| S1 | Line 11 | Mint **should** elect a data structure `D` that maps requests to responses, fit for fast insertion, look-up, and deletion | Explicit SHOULD |
| S2 | Line 15 | Key `k` **should** depend on the method, path, and the payload of `request` | Explicit SHOULD |
| S3 | Lines 19-20 | If no cached response found: process request as usual | Behavioral |
| S4 | Line 20 | If cached response found: return cached response | Behavioral |
| S5 | Line 24 | Store response in `D[k]` for each successful response (`status_code == 200`) | Behavioral |
| S6 | Line 28 | Mint decides the `ttl`; entries **can** be evicted after ttl | Explicit CAN |
| S7 | Lines 32-53 | NUT-19 announced as extension to `nuts` field of `GetInfoResponse` (NUT-06) | Structural |
| S8 | Lines 39-53 | Settings structure: `"19": { "ttl": <int\|null>, "cached_endpoints": [{method, path}] }` | Structural |
| S9 | Line 58 | `ttl` is number of seconds; `null` means cached indefinitely | Structural |
| S10 | Lines 43-49, 59 | `cached_endpoints` is a list of `{method, path}`; `method` is uppercase HTTP method string (e.g. `"POST"`); `path` is route path string (e.g. `"/v1/mint/bolt11"`) | Structural |

## Check Results

### S1: Data structure D for request→response mapping — PASS

**Evidence**:
- `HttpCache` struct (`cache/mod.rs:39-46`) wraps a pluggable `HttpCacheStorage` trait with `get`/`set` operations.
- Two backends provided:
  - `InMemoryHttpCache` (`backend/memory.rs`) using `moka::future::Cache` — concurrent, O(1) lookups, supports TTL + TTI eviction natively, max 10,000 entries.
  - `HttpCacheRedis` (`backend/redis.rs`) using Redis `SET_EX` / `GET` — supports single-node and cluster modes.
- Both satisfy "fast insertion, look-up, and deletion (eviction)".

### S2: Key k should depend on method, path, and payload — PASS (with note)

**Evidence**:
- `calculate_key<K: Serialize>` (`cache/mod.rs:222-242`) serializes the key material to JSON, enforces a 10 MB max, then double-SHA-256 hashes to a fixed-size `HttpCacheKey([u8; 32])`.
- Custom handlers (mint/melt/batch) encode all three components explicitly:
  - Mint: `("mint", method.as_str(), &payload)` (`custom_handlers.rs:573`)
  - Melt: `("melt", method.as_str(), &parsed_payload)` (`custom_handlers.rs:624`)
  - Batch mint: `("mint_batch", method.as_str(), &payload)` (`custom_handlers.rs:703`)
- Swap handler key is payload-only: `calculate_key(&payload)` (`router_handlers.rs:35`). Method (POST) and path (/v1/swap) are implicit in the route-specific handler. This is safe: the SwapRequest serializes as a JSON object while custom handlers serialize as JSON arrays, making cross-endpoint hash collisions impossible. See **Note N1** below.

### S3: No cached response → process as usual — PASS

**Evidence**:
- All cache handlers follow the same pattern: compute key → `cache.get()` → on `None`, fall through to processing.
- `cache_post_swap` (`router_handlers.rs:42-44`): `if let Some(cached_response) = ... { return }` — fall-through reaches handler.
- `cache_post_mint_custom` (`custom_handlers.rs:585-593`): `if let Some(cached_response) ... { return }` else processes and caches.
- Key calculation failure (`None` from `calculate_key`) also falls through to direct processing without caching.

### S4: Cached response found → return cached — PASS

**Evidence**:
- `cache_post_swap`: `return Ok(Json(cached_response))` on hit (`router_handlers.rs:43`).
- `cache_post_mint_custom`: `return Ok(Json(cached_response))` on hit (`custom_handlers.rs:586`).
- `cache_post_melt_custom`: `return Ok(melt_quote_response_to_json(cached_response))` on hit (`custom_handlers.rs:641`).
- `cache_post_batch_mint`: `return Ok(Json(cached_response))` on hit (`custom_handlers.rs:716`).

### S5: Store only successful (status_code == 200) responses — PASS

**Evidence**:
- `cache_post_swap` macro (`router_handlers.rs:45-47`): `let response = $handler(...).await?;` — the `?` operator returns early on `Err`, so `cache.set` (line 46) is only reached on success. Success returns `Ok(Json(...))` which axum serializes as HTTP 200.
- `cache_post_mint_custom` (`custom_handlers.rs:589-596`): `process_mint_input(...).await.map_err(into_response)?` — `?` returns the error response early; `cache.set` only reached on success.
- `cache_post_melt_custom` (`custom_handlers.rs:644-648`): same pattern — `process_melt_request(...).map_err(into_response)?` before `cache.set`.
- `cache_post_batch_mint` (`custom_handlers.rs:719-725`): same pattern.
- Error responses (4xx/5xx) never reach `cache.set`.

### S6: TTL-based eviction — PASS

**Evidence**:
- In-memory: moka `Cache::builder().time_to_live(ttl).time_to_idle(tti)` (`backend/memory.rs:20-24`). Entries auto-evict after TTL.
- Redis: `SET_EX key value ttl_secs` (`backend/redis.rs:128,138`). Redis handles expiry.
- TTL is configurable via `HttpCache::from_config()` → `config.ttl.unwrap_or(60)` (`cache/mod.rs:101`).
- cdk-mintd propagates the actual cache TTL into the NUT-19 Settings announcement: `with_cache(Some(cache.ttl.as_secs()), ...)` (`cdk-mintd/src/lib.rs:1360`). The announced TTL reflects the real eviction time. See **Note N2**.

### S7: Announced as extension to NUT-06 nuts field — PASS

**Evidence**:

- Mint builder: `MintBuilder::with_cache(ttl, cached_endpoints)` (`builder.rs:289-298`).

### S9: ttl semantics (int = seconds, null = indefinite) — PASS (with note)

**Evidence**:
- `ttl: Option<u64>` (`nut19.rs:11`). `Some(n)` → integer seconds. `None` → JSON `null`.
- The type system supports indefinite caching (`None`). However, cdk-mintd always passes `Some(cache.ttl.as_secs())` (`lib.rs:1360`), so the mint never announces `null` in practice. See **Note N3**.

### S10: cached_endpoints format — PASS

**Evidence**:
- `Method` enum (`nut19.rs:60-67`) with `#[serde(rename_all = "UPPERCASE")]`:
  - `Get` → `"GET"`, `Post` → `"POST"` — matches spec examples.
- `Path` enum (`nut19.rs:70-101`):
  - `Swap` → `"/v1/swap"` (custom Serialize impl, line 84).
  - `Custom(String)` → arbitrary path string (e.g., `"/v1/mint/bolt11"`).
- cdk-mintd `configure_cache` (`lib.rs:1341-1357`) registers all cached endpoints:
  - `CachedEndpoint::new(Post, Swap)` → `{"method": "POST", "path": "/v1/swap"}`
  - `CachedEndpoint::new(Post, custom_mint(method))` → `{"method": "POST", "path": "/v1/mint/bolt11"}`

## Wallet-Side Replay (Derive & Repeat)

The wallet side correctly implements the replay mechanism described in the spec's "Derive & Repeat" section:

- `HttpClient` stores `cache_support: (u64, HashSet<(Method, Path)>)` — the announced TTL and set of cached endpoints (`http_client.rs:34`).
- Populated from `get_mint_info()` (`http_client.rs:887-898`): reads `info.nuts.nut19` and builds the lookup set.
- `retriable_http_request()` (`http_client.rs:240-313`):
  - Computes `retriable_window` = TTL duration if the (method, path) is in the cached set, else zero.
  - On non-4xx HTTP error, retries the request if within the retriable window.
  - On 4xx, returns immediately (client errors won't resolve on retry — correct).
  - On success, returns immediately.
- All mutating wallet operations (`post_swap`, `post_mint`, `post_melt`, `post_mint_batch`) route through `retriable_http_request`.

This correctly implements the spec's intent: on network error after the mint has processed the request, the wallet replays the identical request, and the mint returns the cached response.

## Additional Findings

### Security Hardening (beyond spec, all positive)

- **Path traversal protection**: `encode_path_segment()` (`nut19.rs:44-57`) percent-encodes all non-alphanumeric characters in custom payment method names. Tested against `../../v1/swap`, `..`, `.` injection attempts (`nut19.rs:109-160`).
- **Payload size guard**: `MAX_PAYLOAD_SIZE = 10 MB` (`cache/mod.rs:71`). Oversized payloads skip caching entirely, preventing CPU exhaustion via hash computation on large inputs.
- **Double-hash key**: SHA-256(SHA-256(payload)) produces a fixed 32-byte key regardless of input size, preventing storage blowup in the key index.

### Note N1: Swap key omits explicit method/path (informational)

The swap cache handler derives its key from the payload alone (`router_handlers.rs:35`), while custom handlers include operation type and method name in the key tuple. The spec says the key "should depend on the method, path, and the payload." The swap handler satisfies this implicitly: it is registered to a single route (`POST /v1/swap`), so method and path are fixed constants. Cross-endpoint key collision is impossible because SwapRequest serializes as a JSON object while the custom handler keys serialize as JSON arrays. **Not a deviation** — just a different implementation strategy for single-route vs. multi-route handlers.

### Note N2: TTI (Time-To-Idle) in addition to TTL (informational)

The in-memory cache backend uses both `time_to_live` and `time_to_idle` eviction (moka, `memory.rs:22-23`). The spec only mentions TTL. TTI may evict entries before their TTL expires if they haven't been accessed. This is stricter than the spec requires (faster eviction, lower memory pressure) but does not violate it — the spec says the mint "decides" the TTL and "can" evict. A response cached with TTL=60s might be evicted at 30s if idle, meaning a replay after 30s of silence could miss the cache. This is acceptable: the wallet retries, gets a fresh response, and the mint re-caches it.

### Note N3: cdk-mintd never announces ttl: null (informational)

The `Settings` type supports `ttl: None` (→ JSON `null`, indefinite caching per spec line 62). However, `configure_cache()` always passes `Some(cache.ttl.as_secs())` where the cache TTL defaults to 60 seconds. This means cdk-mintd in practice always announces a concrete integer TTL. This is a deliberate safety choice — indefinite caching risks unbounded memory growth. The library type correctly represents the full spec range; the mintd configuration simply chooses not to use the indefinite option. Wallets handle both via `ttl.unwrap_or(300)` (`http_client.rs:889`).

### Note N4: `"19"` key always present in JSON (informational)

Unlike `nut15` and `nut29` which use `#[serde(skip_serializing_if = "...::is_empty")]`, the `nut19` field has no skip directive (`nut06.rs:319-322`). A mint with no cached endpoints still emits `"19": {"ttl": null, "cached_endpoints": []}`. This is slightly noisy but not a spec violation — the spec doesn't mandate omission when empty. Wallets handle empty `cached_endpoints` gracefully (no retry window).

### Note N5: `post_cache_wrapper_with_prefer!` macro unused (informational)

The macro `post_cache_wrapper_with_prefer!` (`router_handlers.rs:54-86`) is defined to add caching to handlers with `PreferHeader` support but is never invoked. The melt endpoint handles caching manually in `cache_post_melt_custom` instead, because it needs custom payload parsing per payment method (`parse_melt_payload`). This is dead code but harmless.
