## Spec Context

NUT-09 ("Restore signatures") is an **optional** nut used by NUT-13 (Deterministic secrets / wallet backup). It lets a wallet recover `BlindSignature`s (and hence `Proof`s) by re-presenting the original `BlindedMessage`s; the mint replies only for messages it has previously signed. The spec is short (58 lines): it defines a `POST /v1/restore` request/response pair, two behavioral "must" clauses, a length invariant, and a NUT-06 capability flag. Notably the spec uses lowercase "must" rather than RFC-2119 "MUST"; this audit treats those clauses as binding normative requirements regardless.

## Warnings (WARN)

### WARN-1: Restore silently skips expired keysets (condition not in spec)
- **Location**: `crates/cdk/src/mint/mod.rs:1301-1309`
- **Detail**: NUT-09 states a single condition for returning a signature: the mint must have previously signed the `BlindedMessage` (L11). CDK adds a second gate — if the signature's keyset `is_expired()`, the entry is dropped with `continue` (L1302-1308) and a `debug!` log. From the wallet's perspective this is **silent**: the output disappears from the response with no error and no signal that an expiration policy (rather than "never signed") caused the omission.
- **Risk**: Medium (recovery correctness) — For NUT-13 wallet-backup recovery, a keyset that expires between backup and restore means those tokens become unrestorable even though the mint holds the signature. The spec's recovery guarantee ("recover … by requesting from the mint to reissue the blind signatures") no longer holds for expired keysets. Whether this is acceptable depends on mint policy (expired keysets may have unloaded keys), but it is a strict-text deviation: the spec does not list keyset expiry as a reason to withhold a previously-signed signature.
- **Recommendation**: Either (a) document this as an explicit, deliberate CDK policy in user-facing docs so wallet authors know restore is best-effort for expired keysets, or (b) restore expired-keyset signatures anyway if the keys are still loaded (NUT-01 keysets remain queryable for expired keysets in CDK, so the data to unblind exists). At minimum, consider whether silent dropping vs. an explicit signal is the right UX for the NUT-13 recovery path.

## Cross-Cutting Observations

### DoS guard: max-outputs limit (non-spec, defensive)
`restore()` enforces `request.outputs.len() <= self.max_outputs` (mint/mod.rs:1262-1272), returning `Error::MaxOutputsExceeded`. NUT-09 places no limit on request size. This is a sane abuse-mitigation (a restore request is an unauthenticated DB-lookup amplification vector otherwise) and does not affect conformance for well-formed wallets.

### NUT-21 authentication gate (non-spec, conditional)
The cdk-axum `post_restore` handler calls `state.mint.verify_auth(...)` against `ProtectedEndpoint::new(Method::Post, RoutePath::Restore)` (router_handlers.rs:228-235) before processing. NUT-09 says nothing about authentication. This is CDK's NUT-21 (Clear Auth) integration: the endpoint is auth-gated **only when** the mint has auth configured. For mints with auth disabled, restore is open as the spec assumes. No NUT-09 violation — informational.

### DB-result-length assertion (defensive invariant)
`restore()` asserts `blinded_signatures.len() == output_len` after the DB lookup (mint/mod.rs:1293-1295), erroring `Error::Internal` on mismatch. This pins the contract that `get_blind_signatures` returns exactly one slot (possibly `None`) per queried `B_`, in request order. Correct defensive coding; never user-visible unless a backend violates its own contract.

### Order-preservation verification (stronger than spec)
The post-loop check (mint/mod.rs:1315-1336) verifies response `outputs` appear in the same relative order as the original request (via the `position_map` built at L1278-1283). NUT-09 only requires `outputs[i]↔signatures[i]` correspondence, not request-order preservation. CDK's stricter guarantee helps wallets that match by position rather than by `B_` value, and turns any ordering bug into a hard `Error::Internal` rather than silent mis-pairing.

### `BlindedMessage` lookup key is `blinded_secret` (the `B_`)
Storage and lookup key by `output.blinded_secret` (the `B_` point, mint/mod.rs:1282,1286). This is the natural identifier: `B_` is the wallet-chosen blinding and is what the mint signs, so it is the correct join key for "have I signed this before?" No collision risk beyond the inherent discrete-log hardness of ecash.

## Conclusion

CDK's NUT-09 implementation is **spec-compliant**. The `nut09.rs` types (`RestoreRequest`/`RestoreResponse`) are exact, minimal wire representations matching the spec's JSON shapes and field names, and the mint handler in `crates/cdk/src/mint/mod.rs` honors every normative requirement:

- **Storage at issuance** (NUT09-M1): all three signature-producing flows — NUT-04 mint, NUT-03 swap, NUT-05 melt change — call `add_blind_signatures`, so no blind signature is issued without being persisted.
- **Conditional response** (NUT09-M2): only `Some` DB lookups are returned; never-signed messages yield no signature, ever.
- **`amount` + `id` present** (NUT09-M3): the NUT-00 `BlindSignature` type carries both fields as required, non-optional.
- **Length & correspondence invariant** (NUT09-F3): equal length is structural (paired push); `outputs[i]↔signatures[i]` holds by construction, with request-order preservation as a stricter guarantee.
- **Capability flag** (NUT09-C1): `"9": {"supported": bool}` serializes byte-for-byte to the spec example.

The single WARN (expired-keyset silent skip) is a defensible mint policy that adds a condition the spec does not state; it warrants documentation but does not break protocol interoperability. No FAILs.
