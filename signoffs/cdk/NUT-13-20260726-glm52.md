## Spec Context

NUT-13 ("Deterministic Secrets") is an **optional** nut that enables ecash wallet recovery from a BIP39 mnemonic seed phrase. The wallet deterministically derives `secret` values and blinding factors `r` for each proof, allowing it to regenerate the same `BlindedMessage`s during recovery and request re-issuance of `BlindSignature`s via NUT-09. The spec defines two derivation methods selected by keyset ID version: **BIP32 legacy** (V00 keysets, deprecated) and **HMAC-SHA256** (V01 keysets, current). The spec contains 5 explicit MUST clauses (3 behavioral, 2 about version dispatch), a deprecated keyset-ID-to-integer mapping, and recommends batch-of-100 restore with 3-empty-batch termination.

## Informational Deviations

### INFO-1: Blinding factor uses range-check instead of `% N`

- **Location**: `SecretKey::derive()` nut13.rs:114-116
- **Spec text** (L40): `blinding_factor = hmac_digest % N`
- **CDK code**: `SecretKey::from(secp256k1::SecretKey::from_slice(&result_bytes[..32])?)`
- **Behavior**: `secp256k1::SecretKey::from_slice` accepts the value if `0 < val < N` (the secp256k1 group order) and returns `Error` otherwise. It does **not** perform modular reduction.
- **Difference**: If the raw HMAC-SHA256 digest happens to be ≥ N, the spec says reduce mod N; CDK returns an error.
- **Probability of divergence**: N ≈ 2^256 − 2^128. The probability of a uniform 256-bit value landing ≥ N is ≈ 2^128 / 2^256 = 2^-128 ≈ 2.9 × 10^-39. This will never occur in practice.
- **Assessment**: Equivalent for all practical inputs. All official test vectors pass without error. Listed as informational, not a defect.

### INFO-2: Counter typed as `u32` rather than `u64`

- **Location**: All `from_seed` signatures use `counter: u32`
- **Spec text** (L35): "counter_k_bytes is the counter encoded as an unsigned 64-bit integer in big-endian format"
- **CDK code**: Correctly casts to u64 for message encoding: `(counter as u64).to_be_bytes()` — the wire encoding is correct u64 big-endian.
- **Difference**: The input type limits the counter to u32::MAX (4,294,967,295). The spec's counter encoding supports u64::MAX.
- **Impact**: Negligible. With the spec's recommended batch size of 100 and 3-empty-batch termination, a wallet would need to generate ~4 billion proofs in a single keyset to hit this limit. No realistic scenario approaches it.
- **Assessment**: Not a correctness issue. Listed as informational for completeness.

## Additional Observations

### OBS-1: CDK V2 tests use non-official keyset IDs
CDK's `test_secret_derivation_keyset_v2` and `test_secret_key_derivation_keyset_v2` (L341-404) use keyset ID `012e2347…` instead of the official `015ba18a…` from `tests/13-tests.md`. The hardcoded expected values are self-computed, not cross-validated against the spec. However, a temporary integration test using the official V2 keyset ID and expected vectors confirmed that CDK's derivation logic produces the correct outputs — the implementation is correct even though the test coverage doesn't directly assert against the spec's vectors. **Recommendation**: Replace the self-computed V2 test vectors with the official ones from `tests/13-tests.md` to provide ongoing regression protection against spec drift.

### OBS-2: Stale test comment references SHA-512
`test_v2_hmac_message_construction` (L477-505) contains the comment `// Message should be: b"Cashu_KDF_HMAC_SHA512" + …` and variable `let _expected_prefix = b"Cashu_KDF_HMAC_SHA512"`. The actual implementation uses SHA-256 (correct). This is a copy-paste artifact in the test only — the production code is correct. Cosmetic issue.

### OBS-3: `restore_batch` end_count is exclusive
`restore_batch(start_count, end_count)` iterates `start_count..end_count` (exclusive end). This is consistent with `from_seed_blank`'s counter range and is tested at L328-338. The spec doesn't specify inclusivity semantics for batch boundaries, so this is a valid design choice.
