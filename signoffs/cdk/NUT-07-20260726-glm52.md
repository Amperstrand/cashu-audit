## Detailed Verification

### MUST-1: PENDING proof tracking (PASS — library level)

**Spec (L21):** "Mints **MUST** remember which proofs are currently `PENDING` to avoid reuse of the same token in multiple concurrent transactions."

The `cashu` crate provides the `State::Pending` variant (nut07.rs:32–33) with correct serialization as `"PENDING"` via `#[serde(rename_all = "UPPERCASE")]` (nut07.rs:24). This matches the spec's `str_enum[STATE]` value exactly (spec L71).

The actual PENDING tracking (mutex locks, database state) is a **mint runtime concern** (cdk-mintd), not the type library. The library provides all necessary type infrastructure. **PASS.**

### MUST-2: Response order preservation (PASS — library level)

**Spec (L68):** "The elements of the `states` array **MUST** be returned in the same order as the corresponding `Ys` checked in the request."

CDK types:

`Vec` preserves insertion order by contract. The type system imposes no barrier to order preservation. The actual ordering enforcement is in the mint's HTTP handler implementation. **PASS** (library types support ordered returns).

#### Witness serialization deep-dive (PASS)

The spec example (L94) shows witness as a **JSON string value** containing stringified JSON:
```json
"witness": "{\"signatures\": [\"b2cf120a...\"]}"
```

CDK's `Witness` enum (nut00/mod.rs:302–311) uses `#[serde(untagged)]` with per-variant custom serde modules:
```rust

pub enum Witness {
    #[serde(with = "serde_htlc_witness")]
    HTLCWitness(HTLCWitness),
    #[serde(with = "serde_p2pk_witness")]
    P2PKWitness(P2PKWitness),
}
```

The `serde_p2pk_witness` module (`serde_p2pk_witness.rs:7–13`) serializes as **stringified JSON**:
```rust
pub fn serialize<S>(x: &P2PKWitness, s: S) -> Result<S::Ok, S::Error> {
    s.serialize_str(&serde_json::to_string(&x).map_err(ser::Error::custom)?)
}
```

This produces the exact wire format the spec requires: a JSON string value containing the serialized witness object. `None` serializes as `null`. **Exact match with spec.**

## Observations (non-blocking)

### Observation-1: Extension states `RESERVED` and `PENDING_SPENT` not in spec (LOW)

`State::Reserved` ("RESERVED") and `State::PendingSpent` ("PENDING_SPENT") are CDK extensions beyond the spec's three-value enum (`UNSPENT`, `PENDING`, `SPENT`).

**Risk:** A strict wallet that rejects unknown enum values would fail when a CDK mint returns these states. However, the Cashu spec says `state` has "possible values" (L71) without a strict MUST enumerating only those values, so sending additional states is not a MUST violation. In practice, these states arise during swap/melt internal flows and would typically not be returned in a checkstate response from a well-behaved mint.

**Recommendation:** If strict interop is desired, CDK mints should map `RESERVED` → `PENDING` and `PENDING_SPENT` → `SPENT` at the HTTP handler boundary. This is a mint-layer concern, not a library defect.

### Observation-2: Module docstring title mismatch (COSMETIC)

Module doc comment (nut07.rs:1) says `NUT-07: Spendable Check` while the spec title is `NUT-07: Token state check`. No functional impact.
