## Spec Context

NUT-21 ("Clear Authentication") is an **optional** NUT that defines an OAuth 2.0 / OpenID Connect-based authentication scheme allowing mint operators to restrict endpoint access to registered users. The wallet obtains a Clear Authentication Token (CAT) — an OIDC `access_token` JWT — and includes it in the `Clear-auth:` HTTP header for protected endpoints. The mint signals protected endpoints via `MintClearAuthSetting` in its NUT-06 info response (key `"21"`), specifying the OIDC discovery URL, client ID, and a list of protected endpoint paths using exact or prefix (`*` wildcard) matching. The mint verifies the JWT signature and expiry on each request to a protected endpoint.

The spec contains: 5 OIDC **deployment** MUSTs (operator identity-provider config), 4 **library-enforceable** route-matching MUSTs, 1 JWT verification requirement, 2 error codes, and 1 header convention.

## Informational Deviations

### INFO-1: Payment method matching is case-insensitive (strict spec says "equal")

- **Location**: `nut21.rs:300-306` — `normalize_payment_method` lowercases; `payment_methods_match` lowercases both sides
- **Spec text** (L51): "request path **MUST** equal `path`"
- **CDK behavior**: A configured path `/v1/mint/quote/BOLT11` normalizes to `/v1/mint/quote/bolt11` at deserialization (L178). A request for `/v1/mint/quote/bolt11` matches. Case-insensitive matching via `payment_methods_match` (L304-306).
- **Difference**: Strict spec reading implies byte-for-byte string equality. CDK treats the payment-method segment case-insensitively.
- **Impact**: Negligible. Payment methods in the Cashu ecosystem are conventionally lowercase (`bolt11`, `bolt12`). No spec example uses uppercase. A wallet requesting `/v1/mint/quote/BOLT11` would be matched by CDK but not by a strict-spec implementation — however, no real wallet sends uppercase payment methods.
- **Assessment**: Defensible design choice (HTTP path segments are conventionally case-insensitive for well-known tokens). Tested explicitly at L618-681. Listed as informational.

### INFO-2: `Method` enum limited to GET and POST

- **Location**: `nut21.rs:117-124` — `enum Method { Get, Post }`
- **Spec text**: Spec example shows only `"POST"` (L38); no other HTTP methods referenced.
- **CDK behavior**: Only GET and POST are representable. A `PUT`, `DELETE`, or `PATCH` method in config would fail deserialization.
- **Impact**: None for current spec. The Cashu HTTP API exclusively uses GET (read endpoints) and POST (write endpoints). No NUT defines PUT/DELETE/PATCH endpoints.
- **Assessment**: Adequate for current and foreseeable spec. Would need extension if future NUTs add other methods. Not a defect.

### INFO-3: `RoutePath` only recognizes `/v1/`-prefixed paths

- **Location**: `nut21.rs:169-191` — `from_str` match arms for known `/v1/` routes; unknown paths → `Error::UnknownRoute`
- **Spec text**: Spec examples all use `/v1/` prefix but does not mandate it normatively.
- **CDK behavior**: Exact-match paths not matching any known `/v1/` route variant are rejected at deserialization with `UnknownRoute`. This is MORE restrictive than the spec.
- **Impact**: None for current Cashu version (all endpoints are under `/v1/`). A future `/v2/` API would require extending `RoutePath`. Correct for current spec.
- **Assessment**: Defensive restriction. The typed `RoutePath` enum prevents arbitrary path injection. Wildcard patterns (`/v2/*`) still work via the `Wildcard` variant, so a `/v2/` prefix could be configured if needed.

### INFO-4: Wildcard expansion produces verbose NUT-06 info responses

- **Location**: `nut21.rs:69-88` — custom `Deserialize` for `Settings` expands wildcard patterns into concrete `RoutePath` variants PLUS the `Wildcard` variant
- **Behavior**: A config entry `{"path": "/v1/*"}` deserializes into all 13 known paths + 1 `Wildcard("/v1/")`. When the mint serializes its NUT-06 info response, ALL expanded endpoints are listed individually.
- **Spec intent** (L30): "The mint lists each protected endpoint that requires a clear authentication token (CAT)" — the operator configures patterns, the mint advertises endpoints.
- **Impact**: Functionally correct — every listed endpoint genuinely requires auth, and the wildcard entry IS included so prefix-matching wallets work. However, the response is unnecessarily verbose: a single `/v1/*` config becomes 14+ entries in the info response.
- **Assessment**: Not a spec violation (each listed endpoint does require a CAT). Cosmetic verbosity. A wallet processing the info response handles both exact and prefix entries correctly regardless.
