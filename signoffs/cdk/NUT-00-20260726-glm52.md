## Detailed Verification

### MUST-1: V4 mint URL trailing-slash normalization (PASS)

Spec (L281): "The mint URL **MUST** be normalized by stripping any trailing slashes (`/`)."

`MintUrl::format_url` (mint_url.rs:52–83) calls `url.trim_end_matches('/')` at line 55, stripping all trailing slashes. The `MintUrl` type is used uniformly across `TokenV4.mint_url` (token.rs:438), `TokenV3Token.mint` (token.rs:269), and all API types — so normalization is enforced at the type boundary.

Tests confirm multi-slash stripping (mint_url.rs:136–148):
```rust
let very_unformatted_url = "http://url-to-check.com////";
// ...
assert_eq!(formatted_url, very_trimmed_url.to_string());
```

Also confirmed for V4 token round-trip (mint_url.rs:219–229): two tokens with and without trailing slash in the mint URL deserialize to equal `MintUrl` values.

### MUST-2: Same-keyset grouping in V4 `p` arrays (PASS)

Spec (L283): "All proofs in the corresponding `p` array **MUST** belong to the same keyset ID."

`Token::new` (token.rs:44–68) groups proofs by `keyset_id` using a `HashMap<Id, Vec<Proof>>` fold before constructing `TokenV4Token` entries:

```rust
let proofs = proofs.into_iter().fold(HashMap::new(), |mut acc, val| {
    acc.entry(val.keyset_id)
        .and_modify(|p: &mut Vec<Proof>| p.push(val.clone()))
        .or_insert(vec![val.clone()]);
    acc
}).into_iter().map(|(id, proofs)| TokenV4Token::new(id, proofs)).collect();
```

`TokenV4Token::new` (token.rs:611–621) accepts a single `keyset_id: Id` and assigns it to all proofs in the group. Since the `keyset_id` field on `TokenV4Token` is a single `ShortKeysetId` (not per-proof), the grouping is structurally enforced.

The V4 `Proof` objects (`ProofV4`, mod.rs:436–458) intentionally omit the `id` field — it is carried at the group level, matching the spec (L283): "original keyset ID field `id` omitted."

### MUST-3: Hex↔bytes conversion for CBOR (PASS)

Spec (L285): "Implementations **MUST** convert between hex strings and raw byte arrays when translating between JSON and CBOR representations."

CDK handles this through a dual-path serde strategy:

**PublicKey** (public_key.rs:117–134): Custom `Serialize`/`Deserialize` that always uses hex string encoding. In V4 CBOR, the `c` field of `ProofV4` overrides this with `serialize_v4_pubkey`/`deserialize_v4_pubkey` (mod.rs:580–593) which use `serializer.serialize_bytes(&key.to_bytes())` and `Vec::<u8>::deserialize`.

**SecretKey** (secret_key.rs:116–158): Smart serde that checks `is_human_readable()`:
```rust
match serializer.is_human_readable() {
    true => serializer.serialize_str(&self.to_secret_hex()),  // JSON
    false => serializer.serialize_bytes(self.as_secret_bytes()), // CBOR
}
```

This ensures DLEQ fields (`e`, `s`, `r` of type `SecretKey` in `ProofDleq`) serialize as hex in V3 JSON and as bytes in V4 CBOR — exactly matching the spec's V4 format (L266–269: `"e": bytes, "s": bytes, "r": bytes`).

**Keyset ID** in V4 (`TokenV4Token.keyset_id`): Custom `serialize_v4_keyset_id`/`deserialize_v4_keyset_id` (token.rs:596–609) serialize as CBOR bytes.

### MUST-5: Support both short and full keyset ID representations (PASS)

Spec (L298): "Wallets receiving a Token **MUST** support both short and full keyset ID representations."

`ShortKeysetId::from_bytes` (nut02.rs:399–407) accepts any prefix length:
```rust
let version = KeySetVersion::from_byte(&bytes[0])?;
let prefix = bytes[1..].to_vec();
Ok(Self { version, prefix })
```

`Id::from_short_keyset_id` (nut02.rs:263–293) validates prefix length is within `[BYTELEN_V1, BYTELEN_V2]` = `[7, 32]`, meaning:
- V1 short/full: 8 bytes total (version + 7 bytes) — accepted
- V2 short: 8 bytes total (version + 7 bytes) — accepted
- V2 full: 33 bytes total (version + 32 bytes) — accepted

Test `test_from_short_keyset_id_accepts_exact_32_byte_v2_prefix` (nut02.rs:1213–1235) confirms the full 33-byte V2 ID is accepted:
```rust

assert_eq!(short_id.prefix.len(), 32);
let res = Id::from_short_keyset_id(&short_id, &keysets).unwrap();
assert_eq!(res, v2_id);
```

### MUST-6: Resolve short keyset ID before processing proofs (PASS)

Spec (L298): "When a short keyset ID is encountered, the wallet **MUST** resolve it to the corresponding full keyset ID before processing the contained `Proof` objects."

`TokenV4::proofs` (token.rs:452–459) calls `Id::from_short_keyset_id` for every token group, then passes the resolved `long_id` to `ProofV4::into_proof`:

```rust
for t in self.token.iter() {
    let long_id = Id::from_short_keyset_id(&t.keyset_id, mint_keysets)?;
    proofs.extend(t.proofs.iter().map(|p| p.into_proof(&long_id)));
}
```

`ProofV4::into_proof` (mod.rs:460–472) sets the resolved full keyset ID on each `Proof`. The resolution happens before any downstream processing. Unknown short IDs return `Err(Error::UnknownShortKeysetId)`, preventing processing with unresolved IDs.

Test `test_token_proofs_with_unknown_short_keyset_id` (token.rs:978–1025) confirms that an unresolvable short keyset ID causes `proofs()` to return `Err`.

### MUST-7: Ambiguous short keyset ID must fail — DEVIATION (F-1)

Spec (L300): "If a short keyset ID resolves to more than one known full keyset ID, the identifier is considered ambiguous. In this case, the wallet **MUST** fail token parsing and return an error."

`Id::from_short_keyset_id` (nut02.rs:281–292) returns the **first** matching keyset instead of checking for ambiguity:

```rust
KeySetVersion::Version01 => {
    for keyset_info in keysets_info.iter() {
        if keyset_info.id.version == KeySetVersion::Version01
            && keyset_info.id.id.to_vec().starts_with(&short_id.prefix)
        {
            return Ok(keyset_info.id);  // ← returns FIRST match, no ambiguity check
        }
    }
    Err(Error::UnknownShortKeysetId)
}
```

**Impact:** If two V2 keysets share the same 7-byte prefix (probability ≈ 2^(-56) ≈ 1.4×10^(-17)), CDK will silently use the first one rather than failing. The spec requires failure.

**Severity:** Low. The collision probability is negligible under normal operation. An adversary cannot practically exploit this since keyset IDs are derived from SHA-256 hashes of public keys.

**Recommendation:** Add a match-count check and return `Err` if >1 match is found.

### MUST-8: hash_to_curve procedure (PASS)

Spec (L36–41):
> `Y = PublicKey('02' || SHA256(msg_hash || counter))` where `msg_hash` is `SHA256(DOMAIN_SEPARATOR || x)`
> - `DOMAIN_SEPARATOR` = `b"Secp256k1_HashToCurve_Cashu_"`
> - `counter` uint32 little endian, incremented from 0 until a point lies on the curve

CDK implementation (dhke.rs:19, 43–67):

```rust
const DOMAIN_SEPARATOR: &[u8; 28] = b"Secp256k1_HashToCurve_Cashu_";

pub fn hash_to_curve(message: &[u8]) -> Result<PublicKey, Error> {
    let msg_to_hash: Vec<u8> = [DOMAIN_SEPARATOR, message].concat();
    let msg_hash: [u8; 32] = Sha256Hash::hash(&msg_to_hash).to_byte_array();
    let mut counter: u32 = 0;
    while counter < 2_u32.pow(16) {
        let mut bytes_to_hash: Vec<u8> = Vec::with_capacity(36);
        bytes_to_hash.extend_from_slice(&msg_hash);
        bytes_to_hash.extend_from_slice(&counter.to_le_bytes());  // ← little endian ✓
        let hash: [u8; 32] = Sha256Hash::hash(&bytes_to_hash).to_byte_array();
        match XOnlyPublicKey::from_slice(&hash) {
            Ok(pk) => return Ok(NormalizedPublicKey::from_x_only_public_key(pk, Parity::Even).into())
            //                                                            ^^^^^^^^^^^^ = '02' prefix ✓
            Err(_) => counter += 1;  // ← incremented from 0 ✓
        }
    }
    Err(Error::NoValidPoint)
}
```

Step-by-step verification:
1. `msg_hash = SHA256(DOMAIN_SEPARATOR || x)` ✓
2. `counter` starts at 0, incremented by 1 ✓
3. Counter encoded as `u32::to_le_bytes()` (little endian) ✓
4. `SHA256(msg_hash || counter_le)` used as x-coordinate ✓
5. `Parity::Even` produces `02` prefix ✓

Domain separator byte count: `"Secp256k1_HashToCurve_Cashu_"` = 28 bytes ✓.

The iteration cap of 2^16 is a practical safety bound; the spec says "until a point is found" without specifying a limit. The probability of needing >65536 iterations is vanishingly small (each attempt has ~50% success, so expected iterations ≈ 2).

Test vectors (dhke.rs:201–230) verify three known test vectors including one requiring multiple iterations.

## Findings

### F-1: Ambiguous short keyset ID returns first match instead of failing (LOW)

**Location:** `nut02.rs:281–292` (`Id::from_short_keyset_id`)
**Spec:** L300 — ambiguous short keyset IDs MUST fail.
**Reality:** Returns first match without checking for multiple matches.
**Probability:** 2^(-56) for natural collision between two V2 keysets.
**Risk:** An attacker cannot force this since keyset IDs are SHA-256 derived. The only scenario is a mint with an astronomically large number of keysets.
**Recommendation:** Collect all matches; if count > 1, return a new `Error::AmbiguousShortKeysetId`.

## Summary

CDK's NUT-00 implementation is **compliant** with the specification. All 12 MUST requirements pass except MUST-7 (ambiguous short keyset ID), which has a low-severity deviation (F-1) that is practically unexploitable. The BDHKE cryptographic protocol is implemented exactly as specified. Model types match the JSON schemas with correct field names, types, and optional/required semantics. V3 and V4 token serialization (including binary format) is correct with proper base64_urlsafe padding flexibility and hex↔bytes conversion for CBOR.
