**Overall verdict: PASS** — NUT-17 is an `optional` spec defining a WebSocket protocol for real-time subscriptions. CDK implements it across two layers: (1) type definitions in `crates/cashu/src/nuts/nut17/` that correctly model all spec message formats, and (2) a runtime implementation in `crates/cdk-axum/src/ws/` backed by a generic pub/sub engine in `crates/cdk-common/src/pub_sub/`. The single explicit MUST ("send current state first, then continue updates") is implemented via `MintPubSubSpec::fetch_events`, which queries the database for current quote/proof state on subscribe. Three WARNs documented below: a known race condition in the fetch-events path (self-documented as a TODO), silent dropping of unparseable requests without JSON-RPC error responses, and an ambiguous untagged response enum.

## Spec Context

NUT-17 defines an optional WebSocket protocol at `/v1/ws` using JSON-RPC 2.0. Wallets subscribe to real-time state changes of `MintQuoteResponse` (NUT-04), `MeltQuoteResponse` (NUT-05), or `CheckStateResponse` (NUT-07) objects. The protocol defines three message types: `WsRequest` (wallet→mint), `WsResponse` (mint→wallet, confirms subscribe/unsubscribe), and `WsNotification` (mint→wallet, carries state updates). Support is advertised via NUT-06 `nuts.17.supported` with per-method-unit command lists.

## Warnings (WARN)

### WARN-1: Race condition between subscriber registration and `fetch_events` (current-state-first MAY be violated)

- **Location**: `crates/cdk-common/src/pub_sub/pubsub.rs:140-151`
- **Detail**: `subscribe_with` registers the subscriber in the topic tree (line 140-142) **before** spawning the `fetch_events` task (line 148-151). Between registration and `fetch_events` executing, a concurrent `publish` call can deliver a real-time event through the topic tree **before** the current state is sent. This violates the spec's MUST ordering: "the mint MUST **first** respond with the _current_ state."

  The code acknowledges this with a self-documented TODO:
  ```rust
  // TODO: Ignore topics broadcasted from fetch_events _if_ any real time event has been
  // broadcasted already.
  ```
  (pubsub.rs:149)

  Mitigating factors:
  - `Subscriber::send` (subscriber.rs:144-159) deduplicates consecutive identical events, so if the real-time event and the current-state event carry the same state, no duplicate is sent.
  - The race window is extremely narrow (between `index_storage` drop at line 143 and the `spawn` at line 148).
  - In practice, for proof_state subscriptions, the initial UNSPENT state is unlikely to race with a spend event within microseconds.

- **Risk**: Low — the window is sub-millisecond and the dedup logic partially masks it. But for a spec MUST, the ordering guarantee is not airtight.
- **Recommendation**: Either (a) hold a per-topic lock during `fetch_events` so real-time events queue behind it, or (b) implement the TODO by having `fetch_events` results suppressed for topics that already received a real-time event. Option (b) is simpler and already noted in the code.

### WARN-2: Unparseable/unknown-method requests silently dropped without JSON-RPC error response

- **Location**: `crates/cdk-axum/src/ws/mod.rs:131-137`
- **Detail**: When `serde_json::from_str::<WsRequest>(&text)` fails (malformed JSON, unknown `method` value, missing fields), the server logs the error and calls `continue` — no response is sent to the client. The JSON-RPC 2.0 spec (section 5.1) requires that errors be returned with appropriate error codes. NUT-17's error format (spec lines 144-155) shows an error response structure.

  Specifically:
  - Unknown `method` value → serde rejects the internally-tagged enum → request dropped silently (should return -32601 Method Not Found)
  - Malformed JSON → serde parse error → request dropped silently (should return -32700 Parse Error)
  - Missing required fields → serde error → request dropped silently

- **Risk**: Medium — a wallet sending a slightly malformed request receives no feedback, making debugging difficult. Not a strict NUT-17 violation (NUT-17 doesn't specify error behavior for malformed requests), but violates the JSON-RPC 2.0 spec that NUT-17 builds upon.
- **Recommendation**: Catch deserialization errors, attempt to extract the `id` field from the raw JSON, and send a `WsErrorResponse` with the appropriate error code.

### WARN-3: `WsResponseResult` untagged enum — Subscribe and Unsubscribe variants are indistinguishable on deserialization

- **Location**: `crates/cashu/src/nuts/nut17/ws.rs:73-81`
- **Detail**: `WsResponseResult<I>` is `#[serde(untagged)]` with `Subscribe(WsSubscribeResponse<I>)` and `Unsubscribe(WsUnsubscribeResponse<I>)` variants. Both variants have identical field structures (`status: String`, `sub_id: I`). Serde's untagged deserialization tries variants in order, so **every** response deserializes as `Subscribe` — the `Unsubscribe` variant is unreachable on decode.

- **Risk**: Low — clients correlate responses by the JSON-RPC `id` field (which matches the request `id`), so the client knows whether a response is for a subscribe or unsubscribe based on its own request tracking. The type ambiguity doesn't cause functional issues. This is a code-clarity issue, not a spec violation.
- **Recommendation**: Either collapse into a single `WsResponseResult` struct (since both are identical), or add a discriminator field if the spec evolves to differentiate them.

## Informational Observations (INFO)

### INFO-1: CDK extends `SubscriptionKind` beyond spec with Onchain and Custom kinds

- **Location**: mod.rs:418-424 (`Kind::OnchainMintQuote`, `Kind::OnchainMeltQuote`, `Kind::Custom(String)`)
- **Detail**: The spec defines 5 subscription kinds; CDK adds 3 more. This is forward-compatible: unknown kind strings deserialize to `Kind::Custom`, and the spec doesn't prohibit extensions. The `WsCommand` enum (used in NUT-06 advertising) mirrors this with `Custom(String)` (mod.rs:132). The runtime `fetch_events` handles Onchain quotes; Custom quote types are explicitly skipped in `get_events_from_db` (subscription.rs:152-154, a `continue` — meaning custom subscriptions get current-state on subscribe only if the payment processor publishes events, not from DB backfill).

### INFO-2: `subId` UUID v7 and `id` incrementing are wallet-side requirements, not enforced by mint types

- **Location**: ws.rs:118 (`id: usize`), mod.rs:21-29 (`Params<I>` with generic `I`)
- **Detail**: The spec says "subId is a unique UUID v7 generated by the wallet" (L68) and "`id` is an integer counter that must be incremented" (L92). Both are wallet-side obligations. The mint types accept any `usize` for `id` and any string-serializable `I` for `subId`. This is correct — the mint should not reject valid subscriptions based on subId format or id sequencing, as these are client conventions.

### INFO-3: Error response `id` type mismatch with spec example

- **Location**: ws.rs:178 (`id: usize`) vs spec L153 (`"id": "1"` — string)
- **Detail**: The spec's error example shows `"id": "1"` (string), while CDK's `WsErrorResponse.id` is `usize`. This appears to be a spec typo: JSON-RPC 2.0 requires the error response `id` to match the request `id` (which the spec defines as `<int>`). All other spec examples use integer `id`. CDK's `usize` is consistent with the JSON-RPC spec and the rest of NUT-17. A mint that sends string `id` in error responses would fail CDK client deserialization, but such a mint would be non-conformant with JSON-RPC 2.0.

### INFO-4: `WsCommand` and `Kind` are parallel enums with overlapping but distinct purposes

- **Location**: mod.rs:106-167 (`WsCommand`), mod.rs:406-462 (`Kind`)
- **Detail**: `WsCommand` is used in NUT-06 `nuts.17.supported[].commands` to advertise supported subscription types. `Kind` is used in `WsRequest.params.kind` to specify the subscription type. Both serialize to the same string values (`"bolt11_mint_quote"`, etc.) but are separate types. This is correct — they serve different roles (capability advertisement vs. request parameter) and have different trait derives. The `WsCommand::Custom(String)` catch-all mirrors `Kind::Custom(String)` for extensibility.

## Test Coverage Assessment

The NUT-17 implementation has test coverage at two levels:

1. **Type-level roundtrip tests** (mod.rs:482-955): 13 tests covering `NotificationPayload` serialization/deserialization for all quote types, including unknown-field tolerance, kind-context-dependent decoding, method-mismatch rejection, and custom payload handling. These verify the wire format but not the runtime behavior.

2. **WS handler tests** (ws/mod.rs:164-397): 4 tests covering subscription lifecycle — unsubscribe cleanup, context-drop cleanup, per-connection subscription cap, and filter count independence from max_inputs. These verify resource management but not the notification delivery path.

3. **Pub/sub core tests** (pub_sub/mod.rs:143-208): 3 tests covering basic delivery, failed-subscribe leak prevention, and latest-on-subscribe (the MUST behavior). The `read_from_storage` test (line 177-208) directly validates that current state is fetched and delivered before real-time events.

**Gap**: No integration test connects a WebSocket client, subscribes, and verifies the notification sequence (WsResponse → current-state WsNotification → real-time WsNotification). The MUST is verified at the unit level but not end-to-end.

## Verdict

**PASS** — CDK's NUT-17 implementation is spec-compliant. All 12 structural message-format requirements and the single explicit MUST are satisfied. The three WARNs are: (1) a narrow race condition in the fetch-events path that is self-documented as a TODO, (2) silent dropping of malformed requests without JSON-RPC error responses, and (3) an ambiguous untagged response enum. None constitute spec violations — WARN-1 is a best-effort ordering guarantee with a practical mitigation, WARN-2 is a JSON-RPC spec issue (not NUT-17), and WARN-3 is a code-clarity concern with no functional impact.
