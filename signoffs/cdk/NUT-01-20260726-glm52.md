## Per-Requirement Verdicts

### M1: Compressed Secp256k1 Public Key Format — **PASS**

| Aspect | Evidence | Verdict |
|---|---|---|
| Serialization always produces compressed hex | `public_key.rs:90-92` — `to_hex()` delegates to `secp256k1::PublicKey::to_string()`, which emits 66-char compressed hex. `Serialize` impl (L117-123) calls `to_hex()`. | PASS |
| Deserialization rejects uncompressed keys | `public_key.rs:57-63` — `from_hex()` checks `hex.len() != 33 * 2` (i.e. 66 chars). Uncompressed keys are 130 hex chars → `InvalidPublicKeySize` error. | PASS |
| `to_bytes()` produces compressed format | `public_key.rs:72-74` — calls `self.inner.serialize()` → `[u8; 33]` (compressed per secp256k1 API). | PASS |

| Id derivation uses compressed bytes | `nut02.rs:241-244` — `v1_from_keys` maps `pubkey.to_bytes()` → `Vec<[u8; 33]>`, confirming compressed format in keyset-id computation. | PASS |

**Conclusion**: Compressed format is enforced bidirectionally. No code path can produce or accept an uncompressed key in the NUT-01 keys response.

## Additional Findings

### WARN-1: VecSkipError Silently Drops Malformed Keysets

**Location**: `mod.rs:147` — `#[serde_as(as = "VecSkipError<_>")]` on `KeysResponse.keysets`.

**Behavior**: If any individual `KeySet` in the `keysets` array fails deserialization (e.g., malformed public key, invalid amount), it is silently skipped rather than producing an error.

**Risk**: A wallet receiving a response with a corrupt keyset entry would silently miss that keyset, potentially leading to tokens that can't be decoded. This is a deliberate resilience/forward-compatibility choice (allows adding new fields without breaking older wallets), but it masks data corruption.

**Severity**: Low — only triggers on malformed data that shouldn't occur in normal operation.

**Recommendation**: Consider logging a warning when a keyset is skipped, to aid debugging.

### OBS-1: SecretKey Drop Erasure

**Location**: `secret_key.rs:160-165` — `Drop` impl calls `self.inner.non_secure_erase()` and logs via `tracing::trace!`.

**Assessment**: Good security hygiene. Secret key material is wiped from memory on drop, reducing exposure window. Note: `non_secure_erase()` is best-effort (compiler may optimize away writes), but this is a known Rust limitation and the intent is correct.

### OBS-2: SecretKey Dual-Format Serialization

**Location**: `secret_key.rs:116-158` — `Serialize`/`Deserialize` choose hex string (human-readable) or bytes (binary) based on `is_human_readable()`.

**Assessment**: Good design. NUT-01 uses JSON (human-readable), so secret keys serialize as hex. Binary formats like CBOR get raw bytes, avoiding hex overhead.

### OBS-3: PublicKey Size Validation Precedes secp256k1 Parse

**Location**: `public_key.rs:57-63` — `from_hex` checks `hex.len() != 33 * 2` before calling `secp256k1::PublicKey::from_str`.

**Assessment**: Correct. The explicit size check provides a clear `InvalidPublicKeySize` error variant with expected/found values, rather than a generic secp256k1 parse error. The secp256k1 library would also reject wrong-length keys, but the early check improves error messaging.
