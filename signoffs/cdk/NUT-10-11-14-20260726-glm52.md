## Findings

### Finding 1: Duplicate tags silently use first-occurrence-wins (FAIL — NUT-11 L85)
- **Severity**: Low (spec violation, low practical impact)
- **Location**: `crates/cashu/src/nuts/nut10/spending_conditions.rs:336-371`
- **Description**: When parsing `Conditions` from tags, CDK uses `if field.is_none() { field = Some(value) }` for all 6 tag types (locktime, pubkeys, refund, sigflag, n_sigs, n_sigs_refund). A second occurrence of any tag is silently ignored. NUT-11 L85 states: "Each of the above tags may appear exactly ONCE... If a tag appears more than once, the P2PK secret is malformed and the Proof MUST be rejected as unspendable."
- **Impact**: Low — first-match behavior is deterministic and an attacker cannot exploit it to bypass spending conditions. However, it violates the spec MUST and could mask wallet bugs (a wallet accidentally emitting duplicate tags would not get an error).
- **Evidence**: Test `test_duplicate_tags_first_match` (spending_conditions.rs:417-449) explicitly asserts first-match semantics as intended behavior.
- **Recommendation**: Add a `seen_tags: HashSet<TagKind>` check in the `TryFrom<Vec<Vec<String>>>` loop. If a tag kind is encountered twice, return an error.

### Finding 2: `n_sigs > pubkeys` not validated on verification path (FAIL — NUT-11 L87)
- **Severity**: Low (spec violation, no security hole)
- **Location**: `crates/cashu/src/nuts/nut10/spending_conditions.rs:326-408` (`TryFrom<Vec<Vec<String>>>`)
- **Description**: The tag-parsing path (used by the mint when verifying proofs) checks `n_sigs != 0` and `n_sigs_refund <= refund_keys.len()`, but does NOT check `n_sigs <= (1 + pubkeys.len())` for the primary pathway. The `validate()` method (L184-200) does check this, but is only called on the construction side (`Conditions::new`, `SpendingConditions::validate`), not when parsing from a proof secret. NUT-11 L87: "If `n_sigs`...exceeds the total number of keys in its pathway, the P2PK secret is malformed and the Proof MUST be rejected as unspendable."
- **Impact**: Low — the primary path simply becomes unspendable (verification fails with `SpendConditionsNotMet`), which is functionally equivalent to rejection. But the refund path remains usable, and the error is not the spec-mandated "rejected as unspendable." The proof is not bricked — it's just deferred.
- **Evidence**: The construction-side `validate(1)` (spending_conditions.rs:263) checks this. The verification-side `TryFrom<Vec<Vec<String>>>` does not call `validate()`.
- **Recommendation**: Call `validate()` at the end of `TryFrom<Vec<Vec<String>>> for Conditions`, passing `primary_key_count=1` for P2PK and `primary_key_count=0` for HTLC. Alternatively, add the `n_sigs > available_keys` check inline.

### Finding 3: HTLC hash/preimage lowercase hex not enforced (WARN — NUT-14 L86, L88)
- **Severity**: Info (spec deviation, no security impact)
- **Location**: `crates/cashu/src/nuts/nut14/mod.rs:277,94`
- **Description**: NUT-14 specifies hash and preimage as "64-character lowercase hexadecimal strings." CDK's `Sha256Hash::from_str` (bitcoin library) accepts upper/mixed-case hex. `hex::decode` for preimages also accepts any case. The byte-level comparison (`SHA256(preimage) == hash`) is correct regardless of input case, so security is not impacted.
- **Impact**: Info — lenient reading improves interoperability with wallets that emit upper-case hex, but technically violates the "lowercase" formatting requirement.
- **Recommendation**: Optionally add a `chars().all(|c| c.is_ascii_lowercase() || c.is_ascii_digit())` check if strict spec compliance is desired. Low priority.

### Finding 4: NUT-10 custom tag empty-string values not validated (WARN — NUT-10 L68)
- **Severity**: Info
- **Location**: `crates/cashu/src/nuts/nut10/tag.rs:165-173`
- **Description**: NUT-10 L68 states tags "must contain non-empty strings only." CDK rejects empty tag arrays (`[]` → `KindNotFound`), but `Tag::Custom` accepts empty string values without validation. Known tag types (pubkeys, locktime, etc.) implicitly reject empty strings via `PublicKey::from_str` / `parse::<u64>()` failures.
- **Impact**: Info — only affects custom (unknown) tag types, which are passively accepted and not used for verification.
- **Recommendation**: Add a non-empty check for all tag string values in `Tag::try_from`.
