## Spec Context

NUT-06 defines a single read-only endpoint (`GET /v1/info`) that returns mint metadata for wallet display and capability discovery. The response (`GetInfoResponse`) contains descriptive fields (all optional) and a `nuts` object enumerating supported NUT specifications with their settings. CDK models this as the `MintInfo` struct, which serves directly as the JSON response body — there is no separate `GetInfoResponse` wrapper type (the name from the spec is descriptive, not a type mandate).

## Warnings (WARN)

### WARN-1: MintVersion deserialization rejects version strings with multiple slashes
- **Location**: nut06.rs:57-60
- **Detail**: `MintVersion::deserialize` splits the input string on `/` and requires exactly 2 parts (`parts.len() != 2` → error). A version string like `"cdk-mintd/v1.2.3/rc1"` or `"My Mint/v2"` would fail to deserialize. The spec says the version is "the implementation name and the version of the software running on this mint separated with a slash `/`" (L92), which implies a single `/` separator. However, real-world version strings or mint names containing `/` would be rejected.
- **Risk**: Low — the spec implies exactly one separator, and all known Cashu mint implementations use the `"Name/X.Y.Z"` format. This only matters when parsing responses from hypothetical mints with `/` in their name or version.
- **Recommendation**: If robustness is desired, use `splitn(2, '/')` instead of `split('/')` so the version part can contain additional slashes. This is a minor improvement, not a spec violation.

## Informational Observations (INFO)

### INFO-1: `nuts` field is non-optional (always serialized)
- **Location**: nut06.rs:94 (`pub nuts: Nuts` — not `Option<Nuts>`)
- **Detail**: The spec marks `nuts` as `(optional)` (L101). In CDK, `nuts` is a required field (not wrapped in `Option`), so it always appears in the JSON output. When unconfigured, it serializes as `{"4": {"methods": [], "disabled": false}, "5": {"methods": [], "disabled": false}, "7": {"supported": false}, ...}` due to `#[serde(default)]` on all sub-fields.
- **Assessment**: Not a violation. "Optional" in the spec means the mint CAN include it — always including it is a valid choice. Wallets that receive a `nuts` object with all capabilities disabled/defaulted can correctly determine the mint supports nothing beyond the mandatory NUTs. This is more informative than omitting the field entirely.

### INFO-2: ContactInfo accepts legacy array-format deserialization
- **Location**: nut06.rs:497-502 (standard serde derive), test at L627-674
- **Detail**: The spec defines contact objects as `{"method": "...", "info": "..."}`. CDK's `ContactInfo` uses standard `#[derive(Deserialize)]`, which in serde accepts both map format (`{"method": "email", "info": "x"}`) and seq format (`["email", "x"]`) — assigning struct fields in declaration order. The test `test_ser_mint_info` explicitly round-trips both formats and asserts equality. The seq format was used by older Cashu implementations (e.g., early Nutshell).
- **Assessment**: Non-spec extension for backward compatibility. CDK **serializes** using map format (spec-compliant). The ability to also **parse** legacy array format is a beneficial interop feature that does not affect wire output.

### INFO-3: MintInfo provides helper accessors for auth-related NUT settings
- **Location**: nut06.rs:225-268
- **Detail**: `MintInfo` includes convenience methods beyond the spec: `protected_endpoints()` (returns NUT-21/22 protected endpoint map), `openid_discovery()` (NUT-21), `client_id()` (NUT-21), `bat_max_mint()` (NUT-22), `supported_units()` (union of NUT-04/05 units). These are internal API helpers, not serialized to the wire. They correctly derive their values from the nested `nuts` structure.
- **Assessment**: Clean separation between wire types and domain logic. No spec impact.

## Cross-Cutting Observations

### Dynamic Time Field
The HTTP handler (`router_handlers.rs:175-186`) clones the stored `MintInfo` and calls `.time(unix_time())` on each request, ensuring the `time` field always reflects the current server time. This is correct — a cached or stale timestamp would mislead wallets about server clock health.

### Configuration Sources
MintInfo fields are populated from multiple sources in the `cdk-mintd` crate:
- **Config file** (`cdk-mintd/src/config.rs`): `[mint_info]` TOML section with `name`, `description`, `icon_url`, `motd`, `contact_nostr_public_key`, `contact_email`, `tos_url`
- **Environment variables** (`cdk-mintd/src/env_vars/mint_info.rs`): `CDK_MINTD_MINT_*` overrides
- **Builder pattern** (`cdk/src/mint/builder.rs`): `with_name()`, `with_contact_info()`, `with_motd()`, etc. + automatic NUT-04/05 population from payment processors, NUT-17 from WebSocket config, NUT-21/22 from auth config
- **Database persistence**: Stored in KV store under `cdk_mint/config/mint_info`

### Nuts Object Completeness
The `Nuts` struct covers all NUTs that have info-response settings as of the current spec:
- NUT-04 (mint methods), NUT-05 (melt methods) — full `Settings` with methods arrays
- NUT-07/08/09/10/11/12/14/20 — `SupportedSettings { supported: bool }`
- NUT-15 (MPP) — `nut15::Settings` with method/unit pairs (conditionally serialized)
- NUT-17 (WebSocket) — `SupportedSettings` with supported method list
- NUT-19 (cache) — TTL + cached endpoints
- NUT-21 (clear auth) — OpenID discovery, client ID, protected endpoints (conditionally serialized)
- NUT-22 (blind auth) — BAT max mint, protected endpoints (conditionally serialized)
- NUT-29 (batched mint) — batch size + supported methods (conditionally serialized)

The spec's example only shows NUTs 4, 5, 7, 8, 9, 10, 12, but CDK correctly extends to all NUTs that define info-response settings. Additional NUTs are not a violation — the spec says `nuts` "indicates each NUT specification that the mint supports and its settings."

## Conclusion

CDK's NUT-06 implementation is **fully spec-compliant**. The single mandatory requirement (serve `GET /v1/info`) is correctly implemented at the correct path. All twelve response fields are modeled with correct types, correct JSON serialization, and correct conditional omission. The `MintVersion` custom serde produces the exact `"name/version"` format the spec requires. The `PublicKey` serializes as compressed hex matching the spec example. The `time` field is dynamically populated per-request.

The single WARN (MintVersion rejecting multi-slash strings) is a theoretical robustness gap with no practical impact — all known Cashu implementations use single-slash version strings. The three INFO observations document non-spec extensions (legacy array-format contact parsing, always-present `nuts` object, internal helper accessors) that do not affect wire-format compliance.

NUT-06 is the simplest mandatory spec, and CDK's implementation is clean, well-tested (7 unit tests covering serialization round-trips, builder completeness, conditional serialization, and auth helpers), and production-ready.
