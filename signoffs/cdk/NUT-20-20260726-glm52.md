## Spec Context

NUT-20 defines signature-based authentication for mint quote redemption. A wallet includes a compressed secp256k1 `pubkey` when requesting a mint quote; the mint then requires a valid BIP340 Schnorr `signature` over a domain-separated message (committing to the quote ID, output amounts, and blinded messages) before processing the mint operation. This prevents anyone who merely knows the quote ID from minting tokens. Support is advertised via NUT-06 `nuts.20.supported`.

## Informational Observations (INFO)

### INFO-1: Legacy message format fallback for backwards compatibility

- **Location**: nut20.rs:61-71,127-135
- **Detail**: CDK maintains a `legacy_mint_quote_msg_to_sign` function that constructs the message as `quote_id_bytes || B_1_hex_bytes || B_2_hex_bytes || ...` (no domain tag, no length prefixes, no amounts, hex ASCII instead of raw bytes). The `verify_signature` method tries the spec-compliant format first; if verification fails, it falls back to the legacy format and logs a warning: `"Accepted legacy mint quote signature format"`.

  This predates the spec's domain-separated format. The fallback exists for interoperability with wallets/mints that haven't upgraded. The spec-compliant format is always tried first, so this does not weaken security for new quotes — it only extends acceptance to older signature formats.

- **Risk**: None for spec compliance. Minor security note: the legacy format does not commit to output amounts or use domain separation, making it vulnerable to cross-protocol signature reuse if a wallet signs the same key for different protocols. CDK mitigates by treating legacy acceptance as exceptional (logged at WARN level).
- **Recommendation**: Eventually deprecate the legacy fallback once ecosystem migration is complete. Add an expiry or feature flag.

### INFO-2: Wallet generates random keys, not deterministic BIP32 derivation

- **Location**: cdk/src/wallet/issue/mod.rs:214
- **Detail**: The spec (L42-60) describes an optional BIP32 derivation path `m/129373'/20'/0'/0'/{counter}` for deterministic quote locking key generation from the wallet seed. CDK instead calls `SecretKey::generate()` (cryptographically random) for each mint quote. The spec uses "can" language ("Wallets **can** deterministically generate..."), making this optional.

  Consequence: CDK wallets cannot restore NUT-20 signing keys from seed alone during recovery — they depend on the local database having stored the `secret_key` field. The CDK wallet stores the key alongside the quote (wallet/issue/mod.rs:268: `Some(secret_key)`).

- **Risk**: None for spec compliance. Operational: wallet backup must include the local DB; seed-only recovery loses NUT-20 locked quotes.
- **Recommendation**: Consider implementing the BIP32 derivation path as a recovery fallback for seed-based restoration, matching the spec's intent.

### INFO-3: CDK rejects signatures on unlocked quotes (stricter than spec)

- **Location**: issue/mod.rs:827-830
- **Detail**: If a quote has no `pubkey` but the mint request includes a `signature`, CDK returns `Error::SignatureMissingOrInvalid`. The spec does not mandate this behavior — it only requires erroring when a pubkey IS set but no signature is provided. Rejecting unexpected signatures is a reasonable defensive posture (fail-closed on unexpected data), but it is stricter than the spec requires.

- **Risk**: None. This is a conservative security choice. A wallet that erroneously includes a signature on an unlocked quote will get a clear error.
- **Recommendation**: No change needed.

### INFO-4: Bolt12 quotes require a pubkey (NUT-25 interaction)

- **Location**: issue/mod.rs:802-808
- **Detail**: CDK requires `pubkey` on all Bolt12 (NUT-25) mint quotes, returning `Error::SignatureMissingOrInvalid` if absent. NUT-20 itself is bolt11-focused (the spec examples use bolt11), but NUT-25 (Bolt12) builds on NUT-20 for quote locking. This cross-NUT enforcement is correct for Bolt12 mints but goes beyond NUT-20's explicit requirements.

- **Risk**: None. This is correct behavior for NUT-25 compliance.
- **Recommendation**: No change needed.

## Verdict

**PASS** — CDK's NUT-20 implementation is fully spec-compliant with zero FAILs and zero WARNs. The binary message construction format (`mint_quote_msg_to_sign`) exactly implements the spec's domain-separated, length-prefixed layout: `b"Cashu_MintQuoteSig_v1"` (unprefixed) `|| len32(quote) || quote || [len32(amount_i) || amount_i || len32(B_i) || B_i]`. The canonical minimal big-endian amount encoding, 4-byte big-endian length prefixes, and raw-byte (not hex) blinded message representation all match precisely. The BIP340 Schnorr signature scheme operates on the SHA-256 hash of `msg_to_sign` as required. The official test vector (pubkey `0279be66...`, quote `0192d3c0-...`) produces the exact expected hex and hash, and the signature verifies. All type fields (`pubkey`, `signature`), error codes (`20008`, `20009`), and NUT-06 settings (`"20": {"supported": bool}`) are correctly implemented. Four INFO-level observations document non-normative design choices (legacy fallback, random vs deterministic keys, stricter-than-spec rejection of unexpected signatures, Bolt12 pubkey requirement) — none affect compliance.
