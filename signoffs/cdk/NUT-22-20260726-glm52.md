**Overall verdict: PASS** — All NUT-22 MUSTs are satisfied across the data model, wallet, and mint surfaces. The `BlindAuthToken` serialization format (`authA` + base64url JSON) is correct and accepts both padded and unpadded forms. ## Spec Context

NUT-22 ("Blind Authentication") is an **optional** NUT (depends on NUT-21, NUT-12) that defines a blind authentication scheme. Users first obtain a clear auth token (CAT) via OIDC (NUT-21), then exchange it for single-use blind auth tokens (BATs) — which are ecash over a special keyset with unit `auth` and amount `1`. BATs are attached to requests in the `Blind-auth:` header (serialized as `authA<base64url>`). The mint verifies the BAT signature like normal ecash (NUT-00), checks it isn't double-spent, and marks it spent. DLEQ proofs (NUT-12) are mandatory on minting (to prevent mint pinning) but MUST be stripped from the BAT before sending (to protect wallet privacy). Protected endpoints are signaled in the NUT-06 info response under key `"22"` via `MintBlindAuthSetting` (`bat_max_mint` + `protected_endpoints` with exact/prefix path matching).

The spec contains: 1 CAT-gating MUST, 2 DLEQ MUSTs (validate-on-receive, include-on-transfer), 1 base64 padding MUST, 1 CAUTION (strip DLEQ before send), 1 delete-after-use MUST + SHOULD, 1 mint-DLEQ-return MUST, 4 route-matching MUSTs (inherited/shared with NUT-21), and 4 error codes (31001–31004).

## Findings

### WARN-1: BAT `Display` does not auto-strip DLEQ (privacy footgun at the type boundary)
- **Severity**: Low (no live bug; defense-in-depth gap)
- **Spec**: NUT22-STRIP (L185, CAUTION): "the BAT MUST NOT contain the `dleq` proof when it is sent to the mint in the request header."
- **Code**: `BlindAuthToken::Display` (`nut22.rs:225-231`) serializes `self.auth_proof` verbatim via `serde_json::to_string`. If `auth_proof.dleq` is `Some`, the dleq is included in the base64url payload. The correct privacy behavior depends on every caller remembering to invoke `without_dleq()` first.
- **Current state**: The sole caller, `auth_wallet.rs:362`, does call `proof.without_dleq()` before display, so **no privacy leak exists today**. The `without_dleq` doc comment ("We do not send the DLEQ to the mint as it links redemption and creation") signals intent clearly.
- **Risk**: A future caller (e.g. a CLI tool, FFI binding, or a different wallet implementation using `cdk-common` types directly) that serializes a `BlindAuthToken` without `without_dleq()` would silently leak the DLEQ, linking BAT creation to redemption — the exact privacy break the spec's CAUTION warns against. The type system does not prevent this.
- **Recommendation**: Make the privacy invariant unforgeable at the type level. Either (a) have `Display`/`to_string` always strip `dleq` (the BAT wire format never carries dleq by spec), or (b) split into a `StoredBlindAuthToken` (with dleq) and a `BlindAuthToken` (without), where only the latter implements `Display`. Option (a) is the minimal change. There is no scenario where a BAT in the `Blind-auth:` header legitimately carries a dleq, so stripping in `Display` cannot break a valid use case.

### INFO-1: `bat_max_mint` exceeded emits generic code 11006, not the dedicated 31003
- **Severity**: Informational (interoperability nit)
- **Spec**: L249 defines `31003: "Maximum BAT mint amount exceeded"`.
- **Code**: The mint path (`mint/issue/auth.rs:31-37`) returns `Error::AmountOutofLimitRange`, which serializes to code **11006** (`error.rs:916-917, 1412`), not `BatMintMaxExceeded` (31003). The dedicated `BatMintMaxExceeded` variant exists and round-trips 31003, but is only referenced on the *wallet* side (`error.rs:1239`: `ErrorCode::BatMintMaxExceeded => Self::InsufficientBlindAuthTokens`) — i.e., it's used when the *wallet* interprets a 31003 from a mint, not when CDK's own mint emits the error.
- **Impact**: A wallet authored to NUT-22 that switches on code 31003 to present a "mint fewer BATs" UX would not match CDK-mintd's 11006. The error message is still descriptive (`AmountOutofLimitRange(min, max, requested)`), so programmatic recovery is possible, but the code divergence is a spec-conformance gap.
- **Recommendation**: In `mint/issue/auth.rs`, return `Error::BatMintMaxExceeded` (or a new `Error::BatMintAmountExceeded` mapping to 31003) when the BAT-mint count exceeds `bat_max_mint`, reserving `AmountOutofLimitRange` (11006) for ecash-amount limits.

### INFO-2: Conditional dleq-on-transfer MUST is model-supported but not type-enforced
- **Severity**: Informational (no reachable violation)
- **Spec**: NUT22-XFERDLEQ (L165): "Should `AuthProofs` be sent to another user of the mint, it MUST include the `dleq` proof so that the receiving user can validate it."
- **Code**: `AuthProof.dleq` is `Option<ProofDleq>` and is retained through `construct_proofs` and DB storage. The CDK wallet has no inter-user AuthProof transfer feature, so this conditional is not exercisable in current code paths.
- **Note**: This is a "transfer protocol" requirement. The library correctly preserves dleq on stored AuthProofs, which is all a library can do. Any future transfer feature must remember to serialize with dleq included. No action required for the current audit.

### INFO-3: `MintAuthRequest::amount()` counts outputs rather than summing amounts
- **Severity**: Informational (correct by invariant)
- **Code**: `nut22.rs:264-267` returns `outputs.len() as u64`. The spec (L138) phrases the limit as "The sum of all amounts of the outputs cannot exceed `bat_max_mint`." Because the auth keyset has a single denomination of `1` (enforced at `mint/issue/auth.rs:42-44`), `len() == sum`. The mint separately rejects any amount ≠ 1 *before* the count is consulted for the limit, so the invariant holds.
- **Note**: Worth a code comment documenting the equivalence; functionally correct.

Recommend adding a test that constructs an `AuthProof` with `dleq: Some(...)`, calls `without_dleq()`, serializes, and asserts the decoded JSON lacks the `dleq` key. ## Cross-Implementation Notes

CDK's NUT-22 shares the `ProtectedEndpoint` / `RoutePath` / `matching_route_paths` machinery with NUT-21 (a sensible DRY choice, since both NUTs define identical `protected_endpoints` matching semantics). This means the route-matching verdict is identical to the NUT-21 signoff — exact, prefix, wildcard-final-char, and no-regex are all correct. The `Settings` custom `Deserialize` for NUT-22 (`nut22.rs:63-110`) is a near-exact copy of NUT-21's (`nut21.rs:47-89`); the only difference is the fields (`bat_max_mint` vs `openid_discovery`/`client_id`).

## Verdict

**PASS** — CDK's NUT-22 implementation is spec-compliant across all 11 MUSTs and the CAUTION. All four error codes (31001–31004) are correctly defined. The data model matches the spec JSON schemas. The wallet validates DLEQs, strips DLEQ before send, and deletes BATs on use. The mint always returns DLEQs, enforces `bat_max_mint`, and gates on a verified CAT. The single WARN (DLEQ not auto-stripped in `Display`) is a defense-in-depth gap with no live privacy leak given the current sole caller; it should be fixed to make the privacy invariant unforgeable. The three INFO items are minor interoperability/documentation nits that do not affect correctness.

No blocking issues. Recommended follow-ups (non-blocking):
1. **(WARN-1)** Strip `dleq` in `BlindAuthToken::Display` so the wire format can never carry it.
2. **(INFO-1)** Emit code 31003 (not 11006) when `bat_max_mint` is exceeded on `/v1/auth/blind/mint`.
3. **(Test gap)** Add a `without_dleq` → serialize → parse → assert `dleq == None` test.
