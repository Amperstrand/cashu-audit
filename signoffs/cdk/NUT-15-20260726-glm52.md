## Check Results

### M1: Mint MUST indicate each method/unit that supports mpp — PASS

**Evidence**:

- `MppMethodSettings` struct (`nut15.rs:20-25`) holds `method: PaymentMethod` and `unit: CurrencyUnit`.
- `Settings { methods: Vec<MppMethodSettings> }` (`nut15.rs:29-32`) holds the array of supported pairs.
- Serialized under key `"15"` in NUT-06: `Nuts` struct has `#[serde(rename = "15")]` on `nut15` field (`nut06.rs:310-314`).
- Omitted when empty via `#[serde(skip_serializing_if = "nut15::Settings::is_empty")]`.
- Builder populates settings when backend reports MPP support: `bolt11_settings.mpp == true` triggers `MppMethodSettings` creation (`builder.rs:419-428`).
- Mint **enforces** at melt time: rejects MPP if method+unit not in settings (`melt/mod.rs:233-239`, returns `Error::MppUnitMethodNotSupported`).

Serialized output matches spec example exactly:
```json
"15": {
  "methods": [
    {"method": "bolt11", "unit": "sat"}
  ]
}
```

### M2: Melt quote request accepts `options.mpp.amount` — PASS

**Evidence**:

- `MeltQuoteBolt11Request` (`nut23.rs:164-172`) has `options: Option<MeltOptions>`.
- `MeltOptions` enum (`nut23.rs:175-188`) uses `#[serde(untagged)]` with variant `Mpp { mpp: Mpp }`.
- `Mpp` struct (`nut15.rs:11-16`) has single field `amount: Amount`.
- Serialization: `{"mpp": {"amount": <int>}}` — matches spec lines 31-35 exactly.
- Deserialization tested in `nut23.rs` tests (lines 340-401).

### M3: Amount is in millisats (msat) — PASS

**Evidence**:

- `Mpp.amount` is `Amount<()>` (unitless raw value).
- `MeltOptions::amount_msat()` (`nut23.rs:216-221`) returns `mpp.amount` directly — method name and downstream usage treat it as msat.
- `MeltQuoteBolt11Request::amount_msat()` (`nut23.rs:236-257`) returns `mpp.amount` for MPP case, consistent with BOLT11 invoice's `amount_milli_satoshis()` for the non-MPP case.
- Wallet side (`wallet/melt/bolt11.rs:39-41`): `options.map(|opt| opt.amount_msat().into())` — treats MPP amount as msat, wraps in `Amount::new(amount_msat, CurrencyUnit::Msat)`.
- Test `melt_options_report_configured_amounts` (`nut23.rs:364-367`): `MeltOptions::new_mpp(Amount::from(21)).amount_msat()` returns 21 msat.

The value flows consistently as msat from wire → struct → backend. No sat/msat confusion exists in the actual code paths.

**Note (INFO-1)**: `Amount<()>` is unitless — nothing in the type system prevents accidental sat interpretation. Type safety relies on convention (method named `amount_msat`), not enforcement. This is a design choice shared across CDK's Amount type, not a NUT-15-specific defect.

### M4: Info endpoint settings format under key "15" — PASS

**Evidence**:

- `Nuts` struct serializes `nut15` as `"15"` (`nut06.rs:312`).
- `Settings` serializes as `{"methods": [{"method": "...", "unit": "..."}]}` (`nut15.rs:29-32`).
- Custom deserializer (`nut15.rs:42-60`) accepts **both** formats:
  - Array: `[{"method": "bolt11", "unit": "sat"}]`
  - Object: `{"methods": [{"method": "bolt11", "unit": "sat"}]}`
- Tests confirm both formats (`nut15.rs:69-89`).
- Spec's pseudo-code for `MultipathPaymentSetting` is malformed JSON (bare array inside object). CDK's dual-format deserialization is more robust than required.

### M5: Response is normal NUT-05 melt quote response — PASS

**Evidence**:

- `MeltQuoteBolt11Response<Q>` (`nut23.rs:261-274`) is the standard NUT-05 response. No NUT-15-specific response fields exist, matching the spec's statement: "The mints then respond with a normal `PostMeltQuoteBolt11Response`."

## Additional Findings

### INFO-2: Dead serde attribute on `Mpp` struct

`#[serde(rename = "lowercase")]` on the `Mpp` struct (`nut15.rs:12`) is ineffective. The struct is consumed inside `MeltOptions` which uses `#[serde(untagged)]` — in untagged enums, the variant's type name is irrelevant to serialization. Only the field names within each variant matter. The attribute is harmless dead code but could mislead readers into thinking it controls the `"mpp"` key name (it doesn't — the key comes from the field name `mpp` in `Mpp { mpp: Mpp }`).

### INFO-3: Internal MPP prevention (spec-exceeding safety check)

The mint rejects MPP melt quotes when a mint quote exists for the same invoice request (`melt/mod.rs:229-230`, returns `Error::InternalMultiPartMeltQuote`). This prevents a wallet from attempting to split an internal (same-mint) payment into MPP parts, which would be impossible since internal transfers don't go through Lightning. This is a sensible guard not required by the spec.

### INFO-4: Backend delegation model

CDK's mint does not implement the MPP split itself. The partial amount flows through `Bolt11OutgoingPaymentOptions.melt_options` (`melt/mod.rs:337-343`) to the Lightning payment processor trait, which must support partial payments per the spec's requirement: "The Lightning backend of the mint must support paying a partial amount of an Invoice." This delegation is architecturally correct.
