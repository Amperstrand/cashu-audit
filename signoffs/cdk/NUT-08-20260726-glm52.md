## Spec Context

NUT-08 is `optional` and `depends on: NUT-05`. It defines how overpaid Lightning fees are returned to wallets via _blank outputs_ — blinded messages with undetermined value that the mint imprints with overpaid fee amounts after payment settlement. The spec specifies one explicit MUST (ordering of returned signatures), a Python reference for blank output count, an overpaid fee formula, and the NUT-06 setting for advertising support.

CDK implements NUT-08 across two layers: the **mint** (`process_melt_change` in `shared.rs`) decomposes overpaid fees into keyset denominations and signs them in order, and the **wallet** (`melt/saga/mod.rs` + `PreMintSecrets::from_seed_blank` in `nut13.rs`) calculates blank output count and generates the blank blinded messages.

## Warnings (WARN)

### WARN-1: Degraded change return when wallet provides fewer blank outputs than decomposition requires
- **Location**: shared.rs:323–337 (`process_melt_change`)
- **Detail**: When `change_outputs.len() < amounts.len()` (the wallet provided fewer blank outputs than the denomination split needs), the code sorts `amounts` in descending order (L329) and `zip` truncates to `change_outputs.len()` items (L334). This means the smallest denomination amounts are silently dropped. For example: change_target = 15 sats → `amounts = [8, 4, 2, 1]` (4 items), but wallet provided only 3 blank outputs → mint keeps `[8, 4, 2]` and drops `1`, returning 14 sats instead of 15.
- **Spec alignment**: The spec's MUST says "return all blank signatures with a value greater than 0" — but this scenario is not directly addressed by the spec because the spec assumes the wallet follows the `ceil(log2(fee_reserve))` recommendation, which always provides sufficient outputs. The dropped amounts have value > 0, so technically the mint is not returning "all" value > 0 signatures — but it physically cannot (insufficient blank outputs from wallet).
- **Risk**: Low — the wallet's `PreMintSecrets::from_seed_blank` always generates `ceil(log2(change_amount))` blank outputs (nut13.rs:167), which is sufficient to represent any amount up to `change_amount` in powers-of-two denominations. This edge case can only occur with a buggy or non-CDK wallet that under-provides blank outputs. CDK's degradation strategy (keep largest denominations, drop smallest) is the least-harm option.
- **Recommendation**: No code change needed. The behavior is already the most reasonable response to a wallet error. Could optionally log a warning when truncation occurs (currently only a `debug!` log at L324–328) to aid debugging for non-compliant wallets.

## Supporting Analysis

### Denomination Decomposition (Amount::split)

The spec (L29) describes the mint "splitting" overpaid fees into "summands of `2^n`". CDK's `Amount::split()` (amount.rs:205–225) uses a greedy algorithm iterating available keyset denominations from largest to smallest (`fee_and_amounts.amounts.iter().rev()`), producing the minimal number of outputs. For standard `2^n` keysets (the default fallback in `get_keyset_fee_and_amounts`, shared.rs:51: `(0..32).map(|x| 2u64.pow(x))`), this produces the canonical binary representation. The spec example (900 → `[4, 128, 256, 512]`) is handled correctly: `split` produces `[512, 256, 128, 4]` (same set, descending order).

### Change Signing Flow (finalize_melt_quote → process_melt_change)

The complete change flow in `finalize_melt_quote` (shared.rs:626–849):
1. Load melt request info (inputs_amount, inputs_fee, change_outputs) from DB (L652)
2. Core finalization: mark proofs spent, update quote to Paid (L735–746 via `finalize_melt_core`)
3. `process_melt_change` (L752–761): compute change_target, split into denominations, sign, store
4. Record completed operation with change amount (L784–821)
5. Commit TX2 (L831)
6. Publish quote status with change signatures via pubsub (L834–839)

The change signatures flow from `process_melt_change` → return value of `finalize_melt_quote` → HTTP response `change` field. No reordering or filtering occurs between signing and response serialization.

### Wallet-Side Blank Output Generation

The wallet melt saga (melt/saga/mod.rs:800–837):
1. Computes `change_amount = proofs_total - quote_info.amount - actual_input_fee` (L801)
2. If `change_amount <= 0`: no blank outputs (L803–804)
3. Otherwise: `num_secrets = max(ceil(log2(change_amount)), 1)` (L806–807) — matches spec
4. Generates blank outputs via `PreMintSecrets::from_seed_blank()` (L817–822)
5. Wraps in `Option::Some` only if `change_amount > 0` (L833–837)

This ensures the wallet always provides exactly the right number of blank outputs for the expected change, preventing the WARN-1 degradation case in normal operation.

### Test Coverage

- `nut08.rs:66–119` — Three unit tests verifying `change_amount()` correctly sums change `BlindSignature` amounts across BOLT11, BOLT12, and Custom response types.
- `test_blind_signature_order.rs:11–84` — Integration test verifying DB preserves blank output insertion order, which is the prerequisite for the MUST's ordering requirement.
- The ordering guarantee itself (zip preserves index alignment) is structurally enforced by Rust's `Iterator::zip` — no runtime test can fail this unless the types change.

## Verdict

**PASS** — CDK's NUT-08 implementation is spec-compliant. The single explicit MUST (ordered return of value > 0 signatures with omission of value-0 signatures) is correctly implemented via index-preserving `zip` and natural truncation. All four definitional requirements (overpaid fee formula, conditional change field, blank output count, amount-field-ignored) match the spec. The NUT-06 advertisement setting is correctly wired and enabled by default. The one WARN is a graceful-degradation edge case that cannot occur with spec-compliant wallets and represents the least-harm response to a misbehaving wallet.
