## Findings

### Finding 1: Legacy `state` field retained in BOLT11 response (WARN)
- **Severity**: Info
- **Location**: `crates/cashu/src/nuts/nut23.rs:112-114`
- **Description**: `MintQuoteBolt11Response` includes a `state: QuoteState` field (UNPAID/PAID/ISSUED) that was removed from the NUT-04 spec when `amount_paid`, `amount_issued`, and `updated_at` were added. The `state` field is redundant with the accounting fields: `amount_paid == 0` implies UNPAID; `amount_paid > amount_issued` implies PAID; `amount_paid == amount_issued` implies ISSUED (see `compute_quote_state()` at cdk-common/mint.rs:796-811). The `MintQuoteCustomResponse` type (nut04.rs:432-467) correctly omits `state`.
- **Impact**: None functionally. The extra field is ignored by spec-compliant wallets (L142: "MUST ignore unrecognized fields"). However, it encourages wallets to depend on `state` rather than migrating to the accounting model, slowing ecosystem convergence.
- **Recommendation**: Add `#[serde(skip_serializing_if = "...")]` or deprecate after confirming downstream wallet compatibility. Low priority.

### Finding 2: BOLT11 response `unit`/`amount` are `Option<>` (WARN)
- **Severity**: Info
- **Location**: `crates/cashu/src/nuts/nut23.rs:95-99`
- **Description**: The spec response format (L59) shows `unit` as a required field. CDK declares both `amount: Option<Amount>` and `unit: Option<CurrencyUnit>` with REVIEW comments acknowledging they should be non-optional. The response builders always set them to `Some(...)`, so the wire format is correct — the `Option<>` only affects deserialization tolerance (accepting responses that omit these fields from older mints).
- **Impact**: None on the wire — responses always include the fields. Minor type-safety gap: code consuming a deserialized response must handle `None` even though it never occurs in practice.
- **Recommendation**: Remove `Option<>` wrapper once all known mints are updated, as the REVIEW comments suggest.

### Finding 3: `updated_at` monotonicity depends on database backend (WARN)
- **Severity**: Low
- **Location**: `crates/cdk-common/src/mint.rs:666-689` (`add_issuance`), `763-792` (`add_payment`); `crates/cdk-sql-common/src/mint/quotes.rs:907-910` (SQL enforcement)
- **Description**: The `MintQuote` domain model does not update `updated_at` in `add_payment()` or `add_issuance()`. The monotonicity guarantee is implemented solely in the SQL database layer via a `CASE WHEN ... ELSE updated_at + 1 END` expression. This means: (1) the in-memory `MintQuote` object has a stale `updated_at` until `tx.update_mint_quote()` runs and reads it back via `set_updated_at()`; (2) non-SQL backends must replicate the same CASE logic independently. The generic database test suite (`database/mint/test/mint.rs:1190-1327`) does test this behavior across backends, so any compliant backend implementation would catch a regression.
- **Impact**: Low — all production database backends (SQLite, PostgreSQL) use the SQL layer with the CASE statement. The in-memory test database would need its own implementation. The stale `updated_at` window (between `add_payment` and `update_mint_quote`) is within a single transaction and never exposed to clients.
- **Recommendation**: Consider updating `updated_at` in `add_payment()`/`add_issuance()` at the domain-model level as a defense-in-depth measure, then letting the database layer refine it. Low priority.
