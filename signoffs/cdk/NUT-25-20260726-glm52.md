## Check Results

### M1: Mint MUST NOT issue a mint quote without a pubkey — PASS

**Evidence (defense in depth, two layers):**

1. **Protocol boundary (request type):** `MintQuoteBolt12Request.pubkey: PublicKey` (`nut25.rs:39`) is a **required, non-Option** field. Serde deserialization fails if the `pubkey` key is absent from the JSON body → 400 response → no mint quote created. This enforces MUST #1 at the API surface exactly as the spec demands ("the mint MUST NOT issue a mint quote if one is not included").

   This contrasts with NUT-04's `MintQuoteBolt11Request` where `pubkey` is `Option<PublicKey>` (`nut23.rs`) — correctly reflecting that NUT-20's pubkey is optional for BOLT11 but **required** for BOLT12 per line 24.

2. **Mint-time defensive guard:** Even if a bolt12 quote somehow exists internally without a pubkey, the mint blocks token issuance: `if mint_quote.payment_method.is_bolt12() && mint_quote.pubkey.is_none() { ... return Err(Error::SignatureMissingOrInvalid); }` (`issue/mod.rs:801-808`). The internal `MintQuote` type stores `pubkey: Option<PublicKey>` (shared across methods), so this guard closes the gap for bolt12.

3. **NUT-20 signature verification:** Beyond presence, the pubkey's signature is verified on the mint request (`issue/mod.rs:810-824`), satisfying the NUT-20 dependency for bolt12.

### M2: Mints MUST accept mint requests where total output ≤ (amount_paid − amount_issued) — PASS

**Evidence:**

- `MintQuote::amount_mintable()` (`cdk-common/src/mint.rs:724-728`) is defined as `amount_paid.checked_sub(&amount_issued)`, saturating at zero. This is exactly the spec's `amount_paid - amount_issued`.
- At mint time (`issue/mod.rs:764-794`), for bolt12 quotes the expected amount defaults to `mint_quote.amount_mintable()` (line 777) unless a batch `expected_amount` overrides it.
- The invariant is enforced: `if expected_amount > mintable { return Err(Error::TransactionUnbalanced(...)); }` (`issue/mod.rs:781-794`). Any output total exceeding `amount_paid - amount_issued` is rejected.
- Critically, the spec says mints **MUST accept** requests **up to and including** the full difference. CDK permits any `expected_amount <= mintable` (line 782 uses strict `>` for rejection), and the `Issued` state for bolt12 is treated as re-mintable when `amount_paid > amount_issued` (`issue/mod.rs:751-753`) rather than hard-rejecting — enabling the multiple-issuance model the spec describes in "Multiple Issuances" (lines 127-129).
- `add_issuance(amount_issued)` (`issue/mod.rs:966`) increments the tracked `amount_issued` after each mint, so subsequent mints correctly see a reduced `amount_mintable`.

### M3: amountless.amount_msat MUST equal offer amount if the offer has one — PASS

**Evidence:**

- The data model supports the field: `MeltOptions::Amountless { amountless: Amountless }` (`nut23.rs:184-187`) where `Amountless { amount_msat: Amount }` (`nut23.rs:226-229`). Serialized via `#[serde(untagged)]` as `{"amountless": {"amount_msat": <int>}}` — matches spec lines 157-161 exactly.
- In melt quote creation (`melt/mod.rs:421-475`), the `options` (including amountless) are passed straight through to the Lightning backend via `Bolt12OutgoingPaymentOptions.melt_options` (`melt/mod.rs:453-459`) → `ln.get_payment_quote(...)` (`melt/mod.rs:461-475`).
- Determining whether "the offer has an amount" requires parsing the BOLT12 offer (`Offer::from_str` at `melt/mod.rs:449`) — backend-specific logic. CDK delegates the equality validation to the payment processor, which is architecturally correct: the backend that understands the offer semantics is the right place to enforce `amount_msat == offer.amount`.

  This delegation pattern is consistent with how CDK handles all payment-method-specific validation (see NUT-15 INFO-4: "Backend delegation model"). The `MeltOptions` value reaches the backend unmodified.

### S8: Multiple issuance tracking — PASS

**Evidence:** See M2. The `amount_paid`/`amount_issued` pair on `MintQuoteBolt12Response` (`nut25.rs:62-64`) and the underlying `MintQuote` (`cdk-common/src/mint.rs`) provide the ledger for partial minting. `amount_mintable()` computes the available difference, and the mint endpoint accepts any output total up to that bound.

## Additional Findings

### WARN-1: `request` and `unit` are Option in `MeltQuoteBolt12Response` (spec shows them required)

The spec's melt quote response (lines 169-181) and melt response (lines 205-218) both define `request: <str>` and `unit: <str_enum[UNIT]>` as **required** fields. CDK models them as `Option<String>` and `Option<CurrencyUnit>` with `#[serde(skip_serializing_if = "Option::is_none")]` (`nut25.rs:139-145`).

The code itself flags this with two `// REVIEW:` comments:
```rust
// REVIEW: This is now required in the spec, we should remove the option once all mints update
#[serde(skip_serializing_if = "Option::is_none")]
pub request: Option<String>,
// REVIEW: This is now required in the spec, we should remove the option once all mints update
#[serde(skip_serializing_if = "Option::is_none")]
pub unit: Option<CurrencyUnit>,
```

**Impact:** Low. In practice the mint populates both fields when creating responses (the melt quote handler at `melt/mod.rs:431` destructures `request` and `unit` from the incoming request and they flow into the response). The Option is a backward-compat shim for interoperating with older mints that may omit them. A strict client validating against the spec schema would not break because CDK *can* emit the fields — it just doesn't *guarantee* they're present at the type level. This is a known, intentional, in-code-flagged deviation, not a defect.

**Severity rationale:** WARN rather than FAIL because (a) the deviation is acknowledged in source comments with a migration plan, (b) the fields are populated in actual mint operation, and (c) making them required would be a one-line change once upstream compatibility is no longer needed.

### INFO-1: Doc comments reference wrong NUT numbers

- `MintQuoteBolt12Request` is annotated `/// Mint quote request [NUT-24]` (`nut25.rs:29`). NUT-24 is "HTTP 402 Payment Required" — unrelated. Should be `[NUT-25]`.
- `MintQuoteBolt12Response` is annotated `/// Mint quote response [NUT-24]` (`nut25.rs:42`). Same error.
- `MeltQuoteBolt12Request` is annotated `/// Melt quote request [NUT-18]` (`nut25.rs:107`). NUT-18 is "Payment requests" — unrelated. Should be `[NUT-25]`.

These are cosmetic copy-paste errors from when the types were likely scaffolded. No behavioral impact.

### INFO-2: `Error` enum comment says "NUT18 Error"

`pub enum Error` (`nut25.rs:16`) carries the doc comment `/// NUT18 Error`. This should read `/// NUT25 Error`. The `PublickeyUndefined` variant (`nut25.rs:25-26`) exists for the M1 enforcement path, which is correct — just the label is wrong.

### INFO-3: Backend delegation for amountless equality (M3)

As detailed in M3, the "amountless.amount_msat MUST equal offer amount" check is delegated to the Lightning payment processor backend rather than enforced in the shared `cashu` crate. This is consistent with CDK's architecture (offer parsing is backend-specific: CLN, LND, LDK, etc. each parse BOLT12 differently). A backend that fails to enforce the equality would be non-conformant, but that is a per-backend concern outside the scope of `nut25.rs`. The `cashu` crate correctly transports the `amountless.amount_msat` value to the backend unmodified.
