## Observations (Non-Blocking)

### Observation 1: Struct naming diverges from spec (cosmetic)
- **Location**: nut03.rs:43 (`SwapRequest`), nut03.rs:122 (`SwapResponse`)
- **Description**: Spec uses `PostSwapRequest` / `PostSwapResponse` (L31, L71). CDK drops the `Post` prefix. This is purely a Rust type name — it never appears in JSON wire format. Zero interoperability impact. Nutshell also uses `PostSwapRequest` in Python. This is a common CDK convention (also seen in `MintQuoteRequest` vs `PostMintQuoteRequest` patterns).
- **Verdict**: Acceptable. No action needed.

### Observation 2: DLEQ stripping on programmatic construction
- **Location**: nut03.rs:54 (`inputs: inputs.without_dleqs()`)
- **Description**: `SwapRequest::new()` strips DLEQ proofs from inputs before constructing the request. This is correct: DLEQ data (NUT-12) is for client-side verification of blind signatures and is not part of the NUT-03 swap wire format. Sending it would needlessly bloat the request. Note: when the mint deserializes a `SwapRequest` from HTTP JSON, it goes through serde directly (not `new()`), so any DLEQ data in incoming proofs is preserved in the parsed struct. This asymmetry is benign — the mint doesn't use DLEQ data from swap inputs.
- **Verdict**: Correct design. No action needed.

### Observation 3: No empty-inputs/outputs validation in struct
- **Location**: nut03.rs:42-48
- **Description**: `SwapRequest` does not validate that `inputs` and `outputs` are non-empty at the struct level. A deserialized request with `"inputs": [], "outputs": []` would parse successfully. The mint layer is expected to reject such requests. NUT-03 does not explicitly require non-empty arrays (it describes swaps with "multiple inputs and outputs" in prose), so this is not a spec violation.
- **Verdict**: Acceptable. Mint-layer validation is the appropriate place.

### Observation 4: SpendingConditionVerification impl (NUT-10/11/21/22)
- **Location**: nut03.rs:94-118
- **Description**: `SwapRequest` implements `SpendingConditionVerification`, providing the SIG_ALL message format (`secret_0||C_0||...||secret_n||C_n||amount_0||B_0||...||amount_m||B_m`). This supports NUT-11 (P2PK SIG_ALL), NUT-21 (clear auth), and NUT-22 (blind auth) for authenticated swaps. This is beyond NUT-03 scope but fully compatible — NUT-03 does not restrict spending conditions on swap inputs.
- **Verdict**: Correct extension. No conflict with NUT-03.

### Observation 5: Utility methods for amount computation
- **Location**: nut03.rs:80-91 (`input_amount`, `output_amount`), nut03.rs:136-142 (`promises_amount`)
- **Description**: CDK provides methods to compute the total value of inputs, outputs, and response signatures. These use `Amount::try_sum` which correctly handles potential overflow. The mint uses these to enforce the value-preservation invariant (M8). No `is_balanced()` convenience method exists — the mint checks `input_amount == output_amount + fee` directly.
- **Verdict**: Good API design. No action needed.

## Findings

**No findings.** Zero FAILs, zero WARNs. NUT-03 is the thinnest mandatory spec in the Cashu NUT suite, and CDK's `nut03.rs` is a straightforward, correct implementation of its data model.
