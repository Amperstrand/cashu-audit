## Spec Context

NUT-12 ("Offline ecash signature validation") is an **optional** nut that extends Cashu's DHKE system with Discrete Log Equality (DLEQ) proofs. The DLEQ proof allows a user to verify that the mint used the same private key `a` for both its public key `A = a*G` (NUT-01) and its blind signature `C' = a*B'` (NUT-00), without requiring access to the mint's private keys. This enables offline verification: Alice can verify the mint's signature herself, and Carol (a third-party receiver) can verify it too using the blinding factor `r`.

The spec defines:
1. The DLEQ proof equations (generation by Bob/mint, verification by Alice/Carol)
2. A deterministic nonce derivation scheme using HMAC-SHA256 with rejection sampling
3. Extension of `BlindSignature` JSON with `{e, s}` and `Proof` JSON with `{e, s, r}`
4. A `hash_e` function: SHA256 over concatenated uncompressed public key hex encodings
5. Two wallet MUSTs: verify DLEQ when present in BlindSignatures (L128) and in received tokens (L150)
6. A mint MUST for CSPRNG nonces if using random nonces (L46), plus a SHOULD for deterministic nonces (L44)
7. NUT-06 capability advertisement: `{"12": {"supported": true}}`

## Cross-Cutting Observations

### Deterministic nonce — no reuse risk
The deterministic nonce `r = HMAC-SHA256(key=a, data="Cashu_DLEQ_R_v1" ‖ A ‖ B' ‖ C' ‖ ctr)` is unique per `(A, B', C')` triple. Since each `B'` (blinded message) is derived from a wallet-chosen blinding factor `r_wallet` and secret `x`, different proofs have different `B'` values, producing different nonces. The spec's warning about nonce reuse (`a = (s₁ - s₂) · (e₁ - e₂)⁻¹ mod n`) does not apply because the nonce is deterministic and bound to the specific `(B', C')` pair being signed. ✓

### SecretKey::from_slice handles rejection sampling implicitly
`derive_deterministic_nonce` (nut12.rs:134) uses `SecretKey::from_slice(&result_bytes)` which internally calls `secp256k1::SecretKey::from_slice`. This validates that the HMAC output is in the valid range `[1, n-1]` where `n` is the secp256k1 curve order. On failure (output is 0 or ≥ n), it returns `Err`, and the loop continues to the next counter byte. This exactly implements the spec's "increment and retry if r == 0 or r >= n" without an explicit range check. ✓

### SecretKey zeroization
`SecretKey` implements `Drop` with `non_secure_erase()` (secret_key.rs:160-165), zeroing the private key bytes from memory when dropped. This applies to DLEQ nonces, blinding factors, and mint secret keys used during DLEQ generation/verification. Defensive security practice not required by the spec. ✓

### Debug logging of DLEQ values
`verify_dleq` logs `e_bytes` and `hash_e` at `debug!` level on failure (nut12.rs:108-109). These are public hash values derived from the DLEQ proof itself (not the private key), so this is not a secret leakage. Standard debug diagnostics. ✓

### Blind auth path stricter than spec
The blind auth wallet (`auth_wallet.rs:472-479`) rejects missing DLEQ with `Error::DleqProofNotProvided`, while the regular wallet path tolerates it. This is a CDK design choice for NUT-22 (Blind Authentication) tokens, where DLEQ is mandatory. The spec's MUST ("if included") is met by both paths; the blind auth path is stricter. ✓

### Mutant testing coverage
CDK includes dedicated mutant-killing tests: `test_proof_dleq_wrong_mint_key` (rejects wrong key), `test_proof_dleq_missing` (rejects missing DLEQ), `test_blind_signature_dleq_wrong_key` (rejects wrong key on BlindSignature), `test_blind_signature_dleq_tampered` (rejects tampered e/s values), `test_add_dleq_proof` (verifies DLEQ is actually generated, not a no-op). These tests catch common implementation bugs. ✓

## Conclusion

CDK's NUT-12 implementation is **fully spec-compliant** with **zero FAILs and zero WARNs**:

- **DLEQ proof generation** (NUT12-E1): `calculate_dleq` implements the exact spec equations — HMAC-SHA256 deterministic nonce, R1/R2 computation, challenge hash, and response computation. Test vectors reproduced byte-for-byte.
- **DLEQ proof verification** (NUT12-E2, E3): Both Alice and Carol verification paths implement the spec equations correctly. Carol's reconstruction (`Y = hash_to_curve`, `C' = C + r*A`, `B' = Y + r*G`) is exact.
- **Hash function** (NUT12-E4): `hash_e` concatenates uncompressed (65-byte → 130-char hex) public key encodings and SHA256s them, matching the spec Python reference.
- **Deterministic nonce** (NUT12-S1): HMAC-SHA256 with rejection sampling via `SecretKey::from_slice` range validation. Counter 0–255 (256 tries). HMAC key is `a` (raw private key), message includes `A` (public key), `B'`, `C'`, and counter byte.
- **Wallet MUSTs** (NUT12-W1, W2): Wallet verifies DLEQ on BlindSignatures from mint (Alice path) and on Proofs from other users (Carol path), exactly as the spec requires. Invalid proofs are hard-rejected.
- **Wire format** (NUT12-F1, F2): BlindSignature DLEQ serializes as `{"e": <hex>, "s": <hex>}`; Proof DLEQ as `{"e": <hex>, "s": <hex>, "r": <hex>}`. SecretKey serializes as lowercase hex in JSON.
- **Privacy** (NUT12-P1): `without_dleqs()` strips DLEQ (including `r`) before proofs are sent to the mint in swap and melt requests.
- **Capability advertisement** (NUT12-C1): `"12": {"supported": <bool>}` in NUT-06 info.
- **Test vectors** (NUT12-TV1, TV2): Deterministic nonce vector (`a=2`, expected `e=2a16ffee…`, `s=9df27731…`) reproduced exactly. Verification passes on all spec test vectors.

No corrections required. The implementation is clean, well-tested (including mutant-killing tests), and handles all edge cases correctly.
