## 2. Findings

### Finding 1: No TollGate-Level Spending Condition Validation (HIGH)
- **Severity**: HIGH
- **Location**: tollwallet.go:132 — `wallet.Receive(token, swapToTrusted)`
- **Description**: TollGate does zero validation of spending conditions before crediting a user. When a token is received:
  1. The token is passed directly to gonuts `wallet.Receive()`
  2. If gonuts accepts it, the user is credited
  3. No check for: P2PK locks, HTLC conditions, witness signatures, duplicate tags
- **Impact**: A malicious user could craft a token with:
  - P2PK lock requiring a signature the gateway can't produce → gateway credits user but can't spend the token later
  - HTLC condition with preimage the gateway doesn't know → same result
  - Duplicate P2PK tags (gonuts bug) → weakened lock conditions
- **Recommendation**: After `wallet.Receive()`, validate the token has no spending conditions before crediting. If conditions exist, either reject the token or verify the gateway can satisfy them.

### Finding 2: Inherited gonuts FAIL — Duplicate P2PK Tags (HIGH)
- **Severity**: HIGH (inherited from gonuts)
- **Location**: gonuts-tollgate (NUT-11 audit, FINDING NUT11-F1)
- **Description**: gonuts silently overwrites duplicate P2PK tags instead of rejecting. NUT-11 says: "If a tag appears more than once, the P2PK secret is malformed and the Proof MUST be rejected as unspendable."
- **Impact**: An attacker could craft a token with duplicate tags that weaken the locking condition, then spend it fraudulently.

### Finding 3: Inherited gonuts FAIL — HTLC Signature Bypass (HIGH)
- **Severity**: HIGH (inherited from gonuts)
- **Location**: gonuts-tollgate (NUT-14 audit, FINDING NUT14-F1)
- **Description**: gonuts allows spending HTLC-locked proofs that have `pubkeys` tag but no `n_sigs` tag, skipping required signature verification.
- **Impact**: An attacker could spend HTLC-locked tokens without the required signatures.

---

## 3. Attack Scenario

```
1. Attacker creates a Cashu token with P2PK lock requiring their own signature
2. Attuster POSTs token to TollGate :2121/ as payment
3. TollGate calls wallet.Receive() → gonuts accepts (P2PK check is at spend time, not receive time)
4. TollGate credits attacker with internet access
5. Later, TollGate tries to spend the token (pay upstream or drain)
6. gonuts can't produce the required P2PK signature → token unspendable
7. TollGate has given away internet access for tokens it can never use
```

This attack is possible because TollGate doesn't validate that received tokens are spendable by the gateway before crediting the user.

---

## 4. Recommendation

**Short-term**: After `wallet.Receive()` succeeds, check if the token's proofs contain spending conditions. If any proof has a P2PK or HTLC secret, reject the payment with `"payment-error-locked-token"`.

**Long-term**: CDK migration (#305) may handle this at the library level.

## Post-Fix Update (2026-07-28 15:00)

### Finding TG-NUT11-F1 (No spending condition validation) → ✅ FIXED

**Fix**: PR #330 adds `hasLockedProofs()` check in `tollwallet.Receive()`. Before calling `wallet.Receive()`, each proof's secret is deserialized via `nut10.DeserializeSecret()`. If the kind is P2PK or HTLC (not AnyoneCanSpend), the token is rejected with `ErrLockedToken`.

**Tests**: 6 new tests in `spending_conditions_test.go`:
- Plain secret → accepted (no lock) ✅
- P2PK secret → rejected ✅
- HTLC secret → rejected ✅
- Mixed proofs → rejected ✅
- Sentinel error works with `errors.Is` ✅

**Updated verdict**: PASS ✅
